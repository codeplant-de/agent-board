# Machine API

The spec between the CLI and the board, API version 9. The CLI calls the board's machine API from its own process (`apps/cli/src/backend.mts` over HTTP, `apps/cli/src/sealing.mts` for the encryption); `apps/backend/src/machine-api.ts` serves it. Nothing else implements it. Everything below describes the wire, where sealed fields hold envelopes; the CLI's own `Backend` interface (`packages/shared/src/contract.mts`) is the plaintext view of it.

`POST <url>/api/machine/<command>` with `Authorization: Bearer <machine token>`, an optional `X-Board-Features` header (see [Features](#features)) and a JSON body `{"id"?, "all"?, "machine"?, "author"?, "body"?}`: `id` is the task, `body` is the command's payload (JSON, with the sealed values). The answer is `{"result": ...}` with status 200, or `{"error": "one line"}` with a non-200 status. The token names the machine; it never appears in an error message. A call times out after 45 seconds.

### Version handshake

`version` answers `{"contract": 9, "owner", "keyId", "api": {"version": 9, "minClient": 9}, "features": [...], "cli"?}`.

- `api.version` is the break level this server speaks (`API_VERSION`) and `api.minClient` the oldest client break level it serves (`MIN_CLIENT`). Neither counts changes: both rise only with a **breaking** change, never with an additive one (see [Wire rules](#wire-rules)). A CLI has the same `API_VERSION` and `MIN_SERVER`, the oldest server break level it works with. All three are in `packages/shared/src/contract.mts`. They start at 9, the contract number the servers and CLIs out there already have, so a server that answers no `api` (its `contract` is taken as both ends) fits.
- `contract` is the legacy number CLIs up to 0.7.0 compare exactly. The server reports `max(LEGACY_CONTRACT, minClient)`: it stays 9 until the first breaking change raises `minClient` above 9, and then stops those CLIs too, with their own "this CLI is older" message.
- A client reads `api` when it is there and otherwise takes `contract` as both `version` and `minClient`. `api` is refused when its numbers are not whole numbers or `minClient` is above `version`.
- The CLI is **too old** when its `API_VERSION` is below `api.minClient`: it stops with a message saying which side to update (`board self-update` for a binary). The server is **too old** when `api.version` is below the CLI's `MIN_SERVER`: it stops with a message to update the server. Nothing else stops it.
- Server too old is a state of a rollout, so an unattended entry point waits it out: the dispatch and intake ticks log one line and exit 0, without a failure or an alert, and the listener logs it once and keeps reconnecting. A command typed at a prompt (`board tasks`) fails with the message on either side. A CLI that is too old still makes the listener exit (systemd restarts it) and the ticks fail.
- The CLI also names itself in every request, the event stream's included: `X-Board-Client` (its version) and `X-Board-Client-Api` (its `API_VERSION`). The server stores them on the machine from `version` calls only, and Settings and the board's banner judge the machine from them: a machine is **incompatible** when its level is below `MIN_CLIENT`. The `version` answer carries `cli`, the newest CLI release the server knows of (`CLI_VERSION`), left out when it knows none. See [Updating the CLI](setup.md#updating-the-cli).
- `board --version` prints `(api 9)`; `board doctor` shows the CLI's break level, the server's range and the features the server lacks.

### Features

Capabilities and vocabulary have names, so that an additive change needs no version number and two branches never collide on one.

- **Server features.** `features` in the `version` answer lists what the server can do: `attach-session`, `events` (the event stream), `note.polish`, `note.suggestion` (the `suggestion` key of `add-note`), `task.model` (the `model` key of `add-task` and `add-schedule`), `task.pr` (the `set-pr` command and the task's `pr` field), `task.pr-state` (the `set-pr-state` command and the task's `prState` field), `run-inbox` (the `run-inbox`, `ack-messages` and `stopped` commands, and the `stopRequested`, `pending`, `queued` and `deliveredAt` fields) and `wait` (the `wait` and `wake` commands). The CLI checks the one name a command needs (`features.includes(name)`), never a version. A server that lacks it makes that command refuse with "the board server does not support <what> yet; update the board server" and nothing else: dispatch, intake and the other commands go on, the listener says so once and keeps reconnecting, and a comment with `--suggest` is posted without the suggestion and says so on stderr. A server that answers no `features` key is taken to have the baseline, which is every name above except `task.model`, `task.pr`, `task.pr-state` and `run-inbox` (what the server of contract 9 has). `board doctor` warns about each feature the server lacks. The names and what they say are in `packages/shared/src/features.mts`: a new server capability appends its name to `ADDED_SERVER_FEATURES` in the same commit that implements it.
- **Client vocabulary.** The CLI sends `X-Board-Features: <names>` on every machine API request: the features of the enum values it understands. `VOCABULARY_FEATURES` in the same file maps an enum value (a `status`, `priority`, `next`, `createdBy` of a task or schedule, an `author` or `kind` of a note) added **after** the baseline to such a feature; every value there is today is the baseline that every CLI from 0.7.0 on knows, so the table is empty and the header is too. The server leaves out of `list-tasks`, `read-notes` and `list-schedules` any item with a value whose feature the request did not name. A single task or schedule it cannot show (`get-task`, `claim-task`, and the result of any write) is answered with 422, `this task uses status "x", which this CLI does not know; update the CLI`, and the write is rolled back with the request. A CLI of 0.8.0 or newer that meets the refusal goes on: intake skips that PR with one line, the dispatcher keeps the stored check of a task it cannot read instead of dropping it, and a worker whose task became unreadable logs it and keeps its run files. 0.7.0 does not: its intake lets the 422 of `add-task` (which dedupes to the hidden task) end the run, so every later PR is skipped on every tick, and its dispatcher drops the stored check of a task the list leaves out. The first row of `VOCABULARY_FEATURES` therefore waits until every machine runs 0.8.0 or newer, or comes with a raised `MIN_CLIENT`. A request without the header (a CLI up to 0.7.0) knows the baseline only. The header is read leniently: it is cut at 1024 characters and 64 names, anything that is not a feature name is ignored, and it never makes a request fail.
- A change to the server's own vocabulary needs both halves in the same pull request: the row in `VOCABULARY_FEATURES` and the CLI sending the new name (it does so by being in the table).

### Wire rules

- Responses may gain keys. A client ignores unknown keys.
- A new enum value in a response is **additive if it gets a vocabulary feature**: the row in `VOCABULARY_FEATURES` makes the server withhold it from a CLI that does not name the feature (see [Features](#features)), so an older CLI never meets it. Without the row it is breaking, as is any change that alters the **meaning** of an existing value: release a CLI that knows the value first, and raise `API_VERSION` and `MIN_CLIENT` when the server starts producing it. The tolerant list reader is only a safety net behind the filter: a CLI skips a task, note or schedule with an enum value it does not know (`status`, `priority`, `next`, `createdBy` of a task, `author` or `kind` of a note, `priority` of a schedule) instead of failing the whole list, and warns once per field and value on stderr. Every other shape error still fails the call.
- A new enum value the CLI can **send** (a status for `board move`, a `--priority`) also needs a server feature: the server accepts it only with that feature, and the CLI sends it only when `features` names the feature (`SENDABLE_SERVER_FEATURES` in `packages/shared/src/features.mts`; `update-task`, `add-task` and `add-schedule` refuse otherwise, with "the board server does not support <what> yet"). The table is empty today. What the choices and the shell completion offer is not filtered by it: they list every value of this build.
- A new request key must be optional, and the CLI sends it only when the server's `features` name it (or, for an advisory key, without it and with a notice). The server stays strict: it refuses an unknown key or value with 400.
- **An additive change adds a feature name and bumps no number.** That covers a new endpoint, a new optional key, a new enum value with its vocabulary row. Only removing or renaming a field, changing its meaning, or a client depending on something it cannot detect is breaking: raise `API_VERSION`, then `MIN_CLIENT` to it when older CLIs cannot cope, and `MIN_SERVER` to it when the CLI needs the newer server (`MIN_CLIENT` can never be above `API_VERSION`: a server's `version` answer is refused when it is). That needs a CLI release, in the order of [Upgrading](#upgrading). CI checks it twice against the newest `cli-v*` release: when that release is below `MIN_CLIENT` of the pull request, the CLI version in `apps/cli/package.json` must be above the release's; when it is not, the release binary is run against the pull request's server (`scripts/previous-cli-smoke.sh`).
- A later step, not taken: a minimum level per command, for the day one command breaks while the rest does not.

## Events

`GET <url>/api/machine/events` with the same bearer token is a stream of server-sent events (`content-type: text/event-stream`, `cache-control: no-cache`, `x-accel-buffering: no`). A missing, unknown or revoked token is a 401 JSON error before any stream starts. It says "look at the board again" and carries no data; the CLI then reads with `list-tasks` as always.

- On connect the server sends the comment `: connected`, and every 25 seconds `: ping`. At each ping it checks the token again and ends the stream when it was revoked. The CLI treats 60 seconds without a byte as a dead connection.
- `event: tasks` with an empty `data:` follows a committed change to a task or a schedule: any write command except the ones below, and any change to a task or schedule from the UI. A failed or rolled back call sends nothing.
- `heartbeat` and `transcript` send nothing (every running task sends them every 15 seconds, and they change no dispatch decision), nor do the reads (`version`, `list-tasks`, `get-task`, `read-notes`, `list-schedules`) or the UI's changes to machines and keys. Nothing is sent when the hourly cleanup closes old Done tasks or deletes old transcripts; the timer covers those.
- Changes of one owner are held back 500 ms and sent as one event, so a burst gives one. An event reaches only the streams of tokens that belong to the same owner.
- The signal lives in the backend process, which is enough for one replica. A stream that was down misses events; the CLI runs one tick after every connect. Behind the board's web proxy the stream arrives as `application/json` and without the headers above, though its chunks still pass as they come: a client must not rely on the stream's response headers.

## Rules

- Every command is atomic under concurrent calls: the dispatcher and intake of several machines, workers and people call at the same time.
- A write is visible to the next read.
- The server refuses an unsafe id or machine name with 400 and writes nothing; the CLI refuses it before it sends anything.
- `claim-task` answers 409 when the task is not free for this machine ("lost"). The CLI treats that as an answer and moves on to the next task; every other non-200 answer is a failure.
- Every machine API request, the event stream's included, carries `X-Board-Client: <cli version>` (`x.y.z`, or `x.y.z-dev` from a checkout) and `X-Board-Client-Api: <level>` (an integer, the CLI's `API_VERSION`) and, from the same place in the code, `X-Board-Features` (see [Features](#features)). The server reads both leniently (the version as `^\d+\.\d+\.\d+(-[0-9A-Za-z.]{1,20})?$` of at most 40 characters, the level as an integer from 1 to 10000; anything else is ignored, never a 400) and stores them on the machine from `version` calls only, writing only when they changed: a worker that started before an update keeps sending old headers with its heartbeats, and those must not undo what the machine's next `version` call reported. The headers and the `cli` field of `version` are additive: older CLIs and servers ignore them, so no number moved.
- The CLI sends `version` once per process, before its first other call, and stops when the version handshake says the CLI or the server is too old (see above). It then derives its keys for the `owner` the server names, and stops when the board has no data key yet (`keyId: null`: set up encryption in the browser first) or its key's id differs from `keyId`.
- A sealed value comes back verbatim. The core parses `agent-board: started <iso>` notes (the start marker) and the first line of a review task's `input` (the PR URL) after opening them; the PR head is the `head` field, a blind index.
- A task an agent proposed (`createdBy: agent`) is the user's to start: the server refuses `update-task` with a new status and loses `claim-task` for it, whoever asks. The user starts it in the browser, which moves it into Todo with its prompt sealed again for the creator `user`; the board then stores that prompt and sets `createdBy` to `user`. The core never runs a task whose `createdBy` is `agent`.
- The board sends no link to a task. The CLI builds links itself from the `url` of its `web.json`.
- The core never writes to a task that is `closed`. A worker that finds its task closed after the run, or running again with another `runStartedAt` than it started with (taken back and run on another machine), drops its result. Any other outcome is judged on the task's `status` after the run: anything but `running` counts as reported (the agent reported, you answered while it was still ending its turn, or the task was taken back). A todo task whose worker unit is still active is not started again until the unit is gone.

## Task

```json
{
  "id": "Ab3dEf9x",
  "title": "abe1.…",
  "input": "abe1.…",
  "status": "needs-me",
  "createdBy": "intake",
  "priority": "normal",
  "model": null,
  "closed": false,
  "machine": "laptop",
  "sessionId": "591d2ec1-d4ab-4e26-ac04-ed303f8fa44a",
  "workdir": "abe1.…",
  "pr": null,
  "prState": null,
  "next": "fresh",
  "head": "abh1.…",
  "openQuestion": true,
  "lane": null,
  "borrowed": false,
  "lastActiveAt": null,
  "runStartedAt": null,
  "paused": false,
  "notBefore": null,
  "scheduleId": null,
  "wakeAt": null,
  "waitCheck": false,
  "woken": false
}
```

All twenty-six fields are required, except that a missing `model` (a server without `task.model`) reads as `null`, a server without the `task.pr` feature leaves `pr` out and one without `task.pr-state` leaves `prState` out; `stopRequested` is optional (a server without `run-inbox` does not send it, and a client reads absent as `false`). The CLI's plaintext `Task` adds `labels` and `unreadable`.

| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`            | Opaque string, stable for the life of the task, chosen by the client that makes it (12 random characters), because the sealed fields are bound to it. It ends up in a systemd unit name, a log file name and argv, so the core refuses any id that does not match `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, and the ids `dispatch` and `intake`.                                                                                                                                                           |
| `title`         | Sealed, for the task (an occurrence: for its schedule). One line, shown in lists.                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `input`         | Sealed, for the task and its creator (an occurrence: for its schedule and `user`). What to work on.                                                                                                                                                                                                                                                                                                                                                                                                  |
| `createdBy`     | `intake`, `user` or `agent`. Intake's tasks are restricted: they run with the narrow permissions of the `skills` profile of their prompt's skill (and not at all without one) and in the profile's directory or the checkout of the PR their prompt names as its first argument. Part of the context of `input`, so a changed value makes the task unreadable. `agent` is a proposal the user has not started: no worker runs it, and starting it changes it to `user` with the prompt sealed again. |
| `status`        | One of `backlog`, `todo`, `running`, `waiting`, `needs-me`, `done`.                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `priority`      | One of `urgent`, `high`, `normal`, `low`.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

Clear, not sealed: it is a choice, not content. `^[A-Za-z0-9][A-Za-z0-9._\-\[\]]{0,63}$`, else the CLI refuses the answer, and the worker checks it again before it reaches argv. A schedule's occurrences all take the schedule's.                                                  |
| `closed`        | `true` for a task out of the workflow. Closed tasks are only listed with `all`; the core never starts, requeues or writes to one.                                                                                                                                                                                                                                                                                                                                                                    |
| `machine`       | The machine that claimed it last, or `null`. A resume runs only there.                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `sessionId`     | The Claude session of the last skill run, or `null`. A UUID (anything else is refused by the parser: it goes into `--resume=<id>`), and a worker resumes only one it started itself for the task.                                                                                                                                                                                                                                                                                                    |
| `workdir`       | Sealed, or `null`: an absolute path without control characters. The directory that session was in when it last stopped, on `machine`, or `null`. A resume starts there (see [Where a task runs](workers.md#where-a-task-runs)).                                                                                                                                                                                                                                                                      |
| `pr`            | Sealed, or `null`: the URL of the pull request the task's agent reported with `set-pr`, sealed for the task and its agent (`task:<id>:agent`). A server without the `task.pr` feature leaves the key out, and a client reads that as `null`. A client shows it only when it opens under that binding to `https://github.com/<owner>/<repo>/pull/<number>`.                                                                                                                                           |

| `openQuestion`  | The agent's last question has no answer yet.                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `lane`          | While running: the lane that runs it, from the last heartbeat; otherwise `null`. | `borrowed`      | While running: the lane borrowed it; otherwise `false`.                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `lastActiveAt`  | While running: the last heartbeat, ISO 8601; otherwise `null`.                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `runStartedAt`  | While running: when the worker claimed it, ISO 8601; otherwise `null`.                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `paused`        | The last run gave up its slot (`pause`) and the task has not run since. Unlike the board's "Paused" badge, which shows it only in Todo, it stays `true` through the claim, so the worker that resumes the task can tell the agent; the worker's first `update-task` of the run clears it, as does the task leaving Running another way.                                                                                                                                                              |
| `notBefore`     | Todo only: no machine may claim the task before this time, ISO 8601; otherwise `null`. The server clears it whenever the task leaves Todo, the claim included.                                                                                                                                                                                                                                                                                                                                       |
| `scheduleId`    | The schedule the task is an occurrence of, or `null`. Set by the server when a schedule makes the task; no draft or patch can set it. It stays when the schedule is removed, because the occurrence's sealed fields are bound to it.                                                                                                                                                                                                                                                                 |
| `wakeAt`        | Waiting only: when the wait ends at the latest (a timer's end, a check's timeout), ISO 8601; otherwise `null`. The server clears it whenever the task leaves Waiting.                                                                                                                                                                                                                                                                                                                                |
| `waitCheck`     | Waiting only: a check on `machine` may end the wait earlier; otherwise `false`. The check's command is never sent to the board.                                                                                                                                                                                                                                                                                                                                                                      |
| `stopRequested` | Optional, absent from a server without `run-inbox`. While running: the user asked for the run to be interrupted and no worker has acknowledged it yet (`ack-messages` with `stop`); otherwise `false`. A CLI treats absent as `false`.                                                                                                                                                                                                                                                               |
| `woken`         | The task's wait ended into Todo (by `wake`, Wake now, a reply or a drag) and it has not run since. Like `paused`, it stays `true` through the claim, so the worker that resumes the task can tell the agent; the worker's first `update-task` of the run clears it, as does the task leaving Todo or Running another way.                                                                                                                                                                            |

Pickup order is the order of the array that `list-tasks` returns: within a status, the first task is the top. In Todo the store lists resumes (`next: resume`) first, then by `priority`, then by manual order; the lanes pick from that order. Delayed tasks (`notBefore` in the future) come last in Todo, by `notBefore`; once due they sort like any other. The dispatcher does not try to claim a delayed task. Waiting lists the wait that ends first on top; nothing claims a task there.

## Schedule

```json
{
  "id": "Sc3dEf9x",
  "title": "abe1.…",
  "input": "abe1.…",
  "priority": "normal",
  "model": null,
  "machine": "laptop",
  "workdir": "abe1.…",
  "everyMs": 7200000,
  "cron": null,
  "timezone": null,
  "anchorAt": "2027-01-01T08:00:00.000Z",
  "nextRunAt": "2027-01-01T10:00:00.000Z",
  "remaining": 3,
  "until": null,
  "paused": false,
  "ended": false,
  "occurrenceTaskId": "Ab3dEf9x",
  "createdAt": "2026-11-14T10:00:00.000Z"
}
```

All eighteen fields are required, except that a missing `model` (a server without `task.model`) reads as `null` (`title`, `input` and `workdir` sealed for the schedule; `id` is chosen by the client). Exactly one of `everyMs` (an interval in ms, at least one minute, on the grid `anchorAt + k * everyMs`) and `cron` (5 fields, read in the IANA zone `timezone`, which a cron rule needs) is set. `anchorAt` is the first run of an interval, or the time a cron rule matches from. `nextRunAt` is the start time of the pending occurrence (read from its task, so a changed delay shows), `occurrenceTaskId` its task; both are `null` while the schedule is paused with nothing waiting, and once it has ended. `nextRunAt` is also `null` while `occurrenceTaskId` is set when the pending task has no start time any more (it was told to run now): it is due now. `remaining` is the number of occurrences still to be made after the pending one (`null`: forever), `until` the last time an occurrence may start. `machine` and `workdir` pin the occurrences, or are both `null`.

A schedule always has at most one pending occurrence, a task in Todo with `scheduleId` set and `notBefore` at `nextRunAt` (until someone changes it); its `createdBy` is `user`, and its `title`, `input` and `workdir` are the schedule's ciphertext, copied unchanged and opened against the schedule's id (the worker may later replace the directory with one sealed for the occurrence and its schedule; see [Encryption](encryption.md#encryption)). When that task leaves Todo (a claim, `update-task`, a move, a close), in the same transaction the server makes the next one: the first match of the rule after the previous occurrence's time that is not in the past, so missed runs are skipped. With nothing left (`remaining` used up, or the next match after `until`) the schedule ends (`ended: true`) and makes no more. A task that was an occurrence and returns to Todo later does not trigger another; only the pending one does.

## Note

```json
{
  "id": "n1",
  "body": "abe1.…",
  "preview": "abe1.…",
  "createdAt": "2026-11-13T10:00:00Z",
  "author": "agent",
  "kind": "comment"
}
```

A message the user sent to a running agent (`Send`, `Stop & send`) adds `pending: true` until a worker acknowledges it with `ack-messages` (or the run ends: see `run-inbox`), and after that `deliveredAt` (ISO 8601) when a worker handed it over mid-run. Both are optional and absent from a server without `run-inbox`. `queued: true` marks every note written to a running agent and is never cleared. A resume prompt leaves out a note with `deliveredAt` (the agent has it already) and, besides what the user wrote since the agent last spoke, carries the `queued` notes without `deliveredAt` written since the previous run started, wherever they fall in the thread.

`author` is `agent`, `user`, `system` or `server`; `kind` is `comment`, `question`, `answer`, `event` or `polish`. `body` is sealed for its task, author and kind, except on an `author: "server"` note, whose body is plain text and one of the fixed event texts (see [Encryption](encryption.md#encryption)); `preview` is a sealed preview or `null`. A comment by the agent may add `suggestion`, a sealed reply drafted for the user. A question note adds `questions` and an answer note `answers` (both sealed JSON: the list `ask` took, and `{"questions": [...], "answers": [...]}` with one `{"selected": [labels], "other"?: text}` per question) and `questionNoteId`, which only informs. The CLI's plaintext `Note` has `text` instead of `body`, keeps a server event as `author: "server"`, gives an answer note the `questions` from its own envelope, and adds `unreadable`. A resume prompt is built from the `user` notes after the last `agent` note.

- `version`: see the rules above.
- `add-task`: `id` is the client's (the safe shape above; a taken id is 409, whoever holds it, with the same message), `title` and `input` are sealed (an empty input is sealed too), `workdir` sealed, `dedupeKey` the blind index of the key (`abh1.…`, else 400), `status` is `backlog`, `todo` (the default) or `needs-me` (a task gets into `running`, `waiting` and `done` only through `claim-task`, `wait` and a close; anything else is 400), `priority` to the parent's with a `parentId` and to `normal` without, `model` (a name of the shape above, else 400; the key is only for a CLI whose server lists `task.model`) to none, which is claude's default, `createdBy` (`intake`, `user`, `agent`) to `user`. `machine` and `workdir` come together and pin the task there. The new task goes to the bottom of its status. A plain-text `title`, `input` or `workdir` is refused with 400. With a `dedupeKey` that a task already has, nothing is created: the answer is that task with `created: false`. `createdBy: agent` makes the task a proposal: it lands in `needs-me` whatever start `status` the draft names. `head` is the blind index of the sha (`abh1.…`, else 400). `notBefore` (ISO 8601) is accepted only with status `todo` (else 400).
- `update-task`: at least one key; unknown keys are a failure. `input` and `workdir` are sealed. A status or priority change puts the task at the bottom of its new place. A status change of a proposal is refused with 403. Leaving `needs-me` for `todo` or `done` clears `openQuestion`. `head` is a blind index, or `null` to clear it. `sessionId` is a UUID or `null`. `expect` is a status and not a change: when the task's status differs under the update's lock, nothing is written and the answer is 409 (intake uses it, so a close or requeue planned from an earlier listing cannot hit a task a dispatcher claimed since). It does not count as a key. `notBefore` is an ISO 8601 time, or `null` to clear it; a time is refused with 409 unless the task ends up in `todo`.
- `claim-task`: `todo` to `running` for the machine, at the bottom of running, in one atomic step. Lost when the task is not in `todo` (a `backlog` task is never claimed), or when it is a resume (`next: resume` with a session) pinned to another machine. A token claims for its own machine only. Lost for a proposal (and for any task whose `createdBy` is `agent`). Sets `runStartedAt`; `paused` stays as it is. Lost while `notBefore` is in the future.
- `add-schedule`: `id` is the client's, as for `add-task` (409 when taken). Exactly one of `everyMs` and `cron`; `cron` needs its `timezone`, and `timezone` goes only with `cron`. `title`, `input` and `workdir` are sealed. `machine` and `workdir` come together. `startAt` (ISO 8601; default now) is the first run of an interval and the earliest match of a cron rule. `times` (a positive integer up to 2147483647, the number of occurrences in all) and `until` (ISO 8601) exclude each other; neither means forever. The answer is 400 for a cron expression the server cannot read (6-field patterns included), an unknown time zone, an interval under a minute or over 10 years (`MAX_INTERVAL_MS`), or a rule with no run before `until`, and nothing is written. The schedule and its first card are made in one transaction.
- `update-schedule`: `paused: true` takes the pending occurrence off the board when it never ran (still in Todo, no session, no run) and gives its run back to `remaining`; `paused: false` makes the next occurrence at the first match from now. 409 for an ended schedule. Pausing a paused schedule, or resuming a running one, changes nothing.
- `remove-schedule`: deletes the schedule and a pending occurrence that never ran; tasks that ran stay, keeping their `scheduleId`. 404 for an unknown schedule.
- `add-note`: author `agent` makes a `comment` (or, with `kind: "polish"`, a `polish` note: the sealed body is the JSON `{"target", "title", "prompt"}` and the preview the start of the prompt), `system` an `event`; a polish note from `system`, or any other `kind`, is 400; both bodies are sealed (else 400), and the CLI refuses an empty text before sealing. `preview` is the sealed start of the text, or absent. `suggestion` is a sealed reply for the user and only author `agent` may send one (else 400).
- `set-pr`: needs the `task.pr` feature (the CLI refuses without it). Stores the sealed `pr` on the task, replacing an earlier one (the last wins); there is no way to clear it. 400 for a value that is not an envelope or is over its limit (`SEALED_LIMITS.pr`) and for any other key, 404 for an unknown task. Like `add-note`, any token of the owner may call it: the binding, not the token, says whose value it is. The CLI checks that the URL is a GitHub pull request before sealing.
- `set-pr-state`: needs the `task.pr-state` feature (the CLI refuses without it). Body `{ "prState": "open" | "merged" | "closed" }`; stores it on the task and changes nothing else (not the status, `updatedAt` or a running task's pause), so a run is never disturbed. There is no way to clear it; `set-pr` resets it. 400 for any other value or key, 404 for an unknown task. Only intake calls it (see [Workers](workers.md#how-it-decides)).
- `heartbeat`: sets `lastActiveAt` to now with the lane, on a running task only; on any other it changes nothing.
- `transcript`: appends a run's condensed events (see `packages/shared/src/transcript.mts`; at most 5000 per call, each with an integer `seq` from 0 to 2147483647, a parseable `at` and a `parent` that is `null` or a tool use id of up to 256 letters, digits, `_` and `-`, or the call fails with 400; the batch's `sessionId` is a UUID or `null`; the CLI drops a `parent` of any other shape to `null` before sending). `data` is the sealed JSON of the event without its output. A `tool_result` also carries the sealed `output` and `outputSize`, its length in characters counted by the client (the server cannot read it; it is bounded, nothing more); any other event carries neither. an event already stored (same run and `seq`) stays as it is, so a retried batch is harmless.
- `pause`: a running task only. Adds the sealed note as a `system` event, then moves the task to Todo with `next: resume` (`fresh` without a session), at the top, and sets `paused`.
- `run-inbox`: for a running task of the token's machine only (409 when it is not running, 403 when another machine claimed it). A call also marks the run as one that reads its inbox. `stop` is true while the user's stop request stands. With `stopMessage` (the id of one of `messages`) it is Stop & send: the worker interrupts, hands over all the messages and the run carries on. Without it the stop is plain: the worker interrupts and ends the run and hands nothing over, so earlier pending messages stay pending; `messages` are the user's notes with `pending: true`, sealed as any note. The worker reads it every watch tick and whenever the event stream says tasks changed, and answers with `ack-messages`.
- `ack-messages`: same rule as `run-inbox`. The listed pending notes of the task stop being pending and get `deliveredAt`; unknown ids and notes that are no longer pending are ignored. With `stop: true` the stop request (and its `stopMessage`) is cleared, so a request is acted on once. At most 100 ids; the ids may be empty.
- `stopped`: the worker ended the run on the user's request, with nothing to carry on with. Same rule as `run-inbox`. Adds the sealed note as a `system` event and moves the task to `needs-me` as the user asked, clearing the stop request. It is exempt from the redirect below: pending notes just become replies (`pending: false`), so the next Send & continue carries them.
- A run that ends while the user's messages are still pending (the worker never got to them: it had closed the agent's stdin or crashed) must not lose them, and the server does it in one place for every way out of Running (`update-task`, `ask`, `wait`, `pause`, `fail`). This applies only to a run whose worker has read `run-inbox` (the server remembers that for the run, the worker looks once right after the process starts): a CLI before 0.9 never would find the message in a resume prompt. For any other run, and for the user's own stops (`stopped`, Take back), the pending notes just become plain replies and the task goes where it was going. The pending notes stop being pending (they are replies now, with no `deliveredAt`, so the resume prompt carries them), and a task that would have gone to `needs-me`, `done` or `waiting` goes instead to the top of Todo with `next: resume` (`fresh` without a session); the open question and the wait go, and a server event "Your message reached the agent after its run ended; resuming with it." goes into the thread. Leaving Running always clears the stop request.
- `wait`: a running, open task only (else 409). Adds the sealed note as the agent's `comment` (sealed for author `agent`, kind `comment`), then moves the task to `waiting` with `wakeAt` (ISO 8601, in the future and at most 7 days ahead, else 400), `waitCheck` from `check`, and `next: resume` (`fresh` without a session). `runStartedAt` and the run details go, as for any task that leaves Running.
- `wake`: in one step, if the task is still `waiting` and not closed, adds the sealed note as a `system` event and moves the task to the top of Todo with `next: resume` (`fresh` without a session) and `woken: true`, and answers `applied: true`; otherwise it changes nothing and answers `applied: false`. The note starts with `agent-board: wait over:`, and the worker hands the rest of the newest such note since the agent last spoke to the resumed agent.
- No other command takes a task into `waiting`: `update-task` with that status and `add-task` with it are 400. A task that leaves `waiting` for `todo` by a drag or a reply is woken (`woken: true`, `next` as for `wake`); one that leaves it for another status just loses its wait.
- `fail`: in one step, if the task is still `running` and not closed, adds the sealed note as a `system` event and moves the task to `needs-me`, and answers `applied: true`; otherwise it changes nothing and answers `applied: false` with the task as it is.
- `ask`: adds a question note with the sealed questions, and moves the task to `needs-me` with `openQuestion: true`. Refused with 403 for a proposal. The CLI validates the questions before sealing (1 to 4; a header of at most 16 characters; 2 to 4 options with different labels, at most one `recommended`); the server cannot.
