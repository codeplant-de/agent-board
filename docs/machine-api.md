# Machine API

The spec between the CLI and the board, API version 9. The CLI calls the board's machine API from its own process (`apps/cli/src/backend/backend.mts` and `web-backend.mts` over HTTP, `contract-check.mts` for the version check, `sealing.mts` for the encryption); `apps/backend/src/machine-api.ts` serves it. Nothing else implements it. Everything below describes the wire, where sealed fields hold envelopes; the CLI's own `Backend` interface (`packages/shared/src/contract.mts`) is the plaintext view of it.

`POST <url>/api/machine/<command>` with `Authorization: Bearer <machine token>`, an optional `X-Board-Features` header (see [Features](#features)) and a JSON body `{"id"?, "all"?, "machine"?, "author"?, "run"?, "body"?}`: `id` is the task, `run` the run the call comes from (see [Runs](#runs)), `body` is the command's payload (JSON, with the sealed values). The answer is `{"result": ...}` with status 200, or `{"error": "one line"}` with a non-200 status. The token names the machine; it never appears in an error message. The server checks the token before it reads the body, so a bad or missing token is a 401 whatever the body is. A body over 2 MiB is a 413, except for `transcript`, which takes up to 16 MiB (the largest sealed field of any other command, a task's input, is about 1 MiB as an envelope). A call times out after 45 seconds.

### Version handshake

`version` answers `{"contract": 9, "owner", "keyId", "api": {"version": 9, "minClient": 9}, "features": [...], "cli"?, "dirsIndex"?, "catalogIndex"?}`. `dirsIndex` is the blind index of the directory list the calling machine last sent with `set-dirs` (`null` when it sent none; a server without `machine.dirs` leaves the key out). A client reads it leniently: anything that is not a blind index counts as `null`, never as an error. `catalogIndex` is the same for the catalogue of skills and models the machine last sent with `set-catalog` (a server without `machine.catalog` leaves the key out).

- `api.version` is the break level this server speaks (`API_VERSION`) and `api.minClient` the oldest client break level it serves (`MIN_CLIENT`). Neither counts changes: both rise only with a **breaking** change, never with an additive one (see [Wire rules](#wire-rules)). A CLI has the same `API_VERSION` and `MIN_SERVER`, the oldest server break level it works with. All three are in `packages/shared/src/contract.mts`. They start at 9, the contract number the servers and CLIs out there already have, so a server that answers no `api` (its `contract` is taken as both ends) fits.
- `contract` is the legacy number CLIs up to 0.7.0 compare exactly. The server reports `max(LEGACY_CONTRACT, minClient)`: it stays 9 until the first breaking change raises `minClient` above 9, and then stops those CLIs too, with their own "this CLI is older" message.
- A client reads `api` when it is there and otherwise takes `contract` as both `version` and `minClient`. `api` is refused when its numbers are not whole numbers or `minClient` is above `version`.
- The CLI is **too old** when its `API_VERSION` is below `api.minClient`: it stops with a message saying which side to update (`board self-update` for a binary). The server is **too old** when `api.version` is below the CLI's `MIN_SERVER`: it stops with a message to update the server. Nothing else stops it.
- Server too old is a state of a rollout, so an unattended entry point waits it out: the dispatch tick logs one line and exit 0, without a failure or an alert, and the listener logs it once and keeps reconnecting. A command typed at a prompt (`board tasks`) fails with the message on either side. A CLI that is too old still makes the listener exit (systemd restarts it) and the ticks fail.
- The CLI also names itself in every request, the event stream's included: `X-Board-Client` (its version) and `X-Board-Client-Api` (its `API_VERSION`). The server stores them on the machine from `version` calls only, and Settings and the board's banner judge the machine from them: a machine is **incompatible** when its level is below `MIN_CLIENT`. The `version` answer carries `cli`, the newest CLI release the server knows of (`CLI_VERSION`), left out when it knows none. See [Updating the CLI](setup.md#updating-the-cli).
- `board --version` prints `(api 9)`; `board doctor` shows the CLI's break level, the server's range and the features the server lacks.

### Features

Capabilities and vocabulary have names, so that an additive change needs no version number and two branches never collide on one.

- **Server features.** `features` in the `version` answer lists what the server can do: `attach-session`, `events` (the event stream), `note.polish`, `note.suggestion` (the `suggestion` key of `add-note`), `task.model` (the `model` key of `add-task` and `add-schedule`), `task.pr` (the `set-pr` command and the task's `pr` field), `task.pr-state` (the `set-pr-state` command and the task's `prState` field), `task.prs` (a task holds several PRs: the `add-pr` and `set-pr-states` commands, and the `prs` and `promptPrState` fields), `task.pr-remove` (the `remove-pr` command), `run-inbox` (the `run-inbox`, `ack-messages` and `stopped` commands, and the `stopRequested`, `pending`, `queued` and `deliveredAt` fields) `machine.dirs` (the `set-dirs` command and `dirsIndex` in the `version` answer), `machine.catalog` (the `set-catalog` command and `catalogIndex` in the `version` answer), `machine.usage` (the `set-usage` command and `usageIndex` in the `version` answer), `task.agent` (the sealed `agent` key of `add-task` and `add-schedule`, and of a task and a schedule), `task.run` (the task's `run` field and the `run` key of a request, see [Runs](#runs)), `task.configure` (the `configure-task` command), `task.note-count` (the task's `noteCount` field), and `wait` (the `wait` and `wake` commands). The CLI checks the one name a command needs (`features.includes(name)`), never a version. A server that lacks it makes that command refuse with "the board server does not support <what> yet; update the board server" and nothing else: dispatch and the other commands go on, the listener says so once and keeps reconnecting, and a comment with `--suggest` is posted without the suggestion and says so on stderr. A server that answers no `features` key is taken to have the baseline, which is every name above except `task.model`, `task.pr`, `task.pr-state`, `task.prs`, `task.pr-remove`, `run-inbox`, `machine.dirs`, `machine.catalog`, `machine.usage`, `task.agent`, `task.run`, `task.configure` and `task.note-count` (what the server of contract 9 has). `board doctor` warns about each feature the server lacks. The names and what they say are in `packages/shared/src/features.mts`: a new server capability appends its name to `ADDED_SERVER_FEATURES` in the same commit that implements it.
- **Client vocabulary.** The CLI sends `X-Board-Features: <names>` on every machine API request: the features of the enum values it understands. `VOCABULARY_FEATURES` in the same file maps an enum value (a `status`, `priority`, `next`, `createdBy` of a task or schedule, an `author` or `kind` of a note) added **after** the baseline to such a feature; every value there is today is the baseline that every CLI from 0.7.0 on knows, so the table is empty and the header is too. The server leaves out of `list-tasks`, `read-notes` and `list-schedules` any item with a value whose feature the request did not name. A single task or schedule it cannot show (`get-task`, `claim-task`, and the result of any write) is answered with 422, `this task uses status "x", which this CLI does not know; update the CLI`, and the write is rolled back with the request. A CLI of 0.8.0 or newer that meets the refusal goes on: `board schedule --key` fails for that task alone (a script such as github-reviews logs it and goes on), the dispatcher keeps the stored check of a task it cannot read instead of dropping it, and a worker whose task became unreadable logs it and keeps its run files. 0.7.0 does not: its intake lets the 422 of `add-task` (which dedupes to the hidden task) end the run, so every later PR is skipped on every tick, and its dispatcher drops the stored check of a task the list leaves out. A row for a note `author` or `kind` must also make the server's `noteCount` leave out the notes `read-notes` leaves out. The first row of `VOCABULARY_FEATURES` therefore waits until every machine runs 0.8.0 or newer, or comes with a raised `MIN_CLIENT`. A request without the header (a CLI up to 0.7.0) knows the baseline only. The header is read leniently: it is cut at 1024 characters and 64 names, anything that is not a feature name is ignored, and it never makes a request fail.
- A change to the server's own vocabulary needs both halves in the same pull request: the row in `VOCABULARY_FEATURES` and the CLI sending the new name (it does so by being in the table).

### Wire rules

- Responses may gain keys. A client ignores unknown keys.
- A new enum value in a response is **additive if it gets a vocabulary feature**: the row in `VOCABULARY_FEATURES` makes the server withhold it from a CLI that does not name the feature (see [Features](#features)), so an older CLI never meets it. Without the row it is breaking, as is any change that alters the **meaning** of an existing value: release a CLI that knows the value first, and raise `API_VERSION` and `MIN_CLIENT` when the server starts producing it. The tolerant list reader is only a safety net behind the filter: a CLI skips a task, note or schedule with an enum value it does not know (`status`, `priority`, `next`, `createdBy` of a task, `author` or `kind` of a note, `priority` of a schedule) instead of failing the whole list, and warns once per field and value on stderr. Every other shape error still fails the call.
- A new enum value the CLI can **send** (a status for `board move`, a `--priority`) also needs a server feature: the server accepts it only with that feature, and the CLI sends it only when `features` names the feature (`SENDABLE_SERVER_FEATURES` in `packages/shared/src/features.mts`; `update-task`, `add-task` and `add-schedule` refuse otherwise, with "the board server does not support <what> yet"). The table is empty today. What the choices and the shell completion offer is not filtered by it: they list every value of this build.
- A new request key must be optional, and the CLI sends it only when the server's `features` name it (or, for an advisory key, without it and with a notice). The server stays strict: it refuses an unknown key or value with 400.
- **An additive change adds a feature name and bumps no number.** That covers a new endpoint, a new optional key, a new enum value with its vocabulary row. Only removing or renaming a field, changing its meaning, or a client depending on something it cannot detect is breaking: raise `API_VERSION`, then `MIN_CLIENT` to it when older CLIs cannot cope, and `MIN_SERVER` to it when the CLI needs the newer server (`MIN_CLIENT` can never be above `API_VERSION`: a server's `version` answer is refused when it is). That needs a CLI release, in the order of [Upgrading](#upgrading). CI checks it twice against the newest `cli-v*` release: when that release is below `MIN_CLIENT` of the pull request, the CLI version in `apps/cli/package.json` must be above the release's; when it is not, the release binary is run against the pull request's server (`scripts/previous-cli-smoke.sh`).
- A later step, not taken: a minimum level per command, for the day one command breaks while the rest does not.

## Events

`GET <url>/api/machine/events` with the same bearer token is a stream of server-sent events (`content-type: text/event-stream`, `cache-control: no-cache`, `x-accel-buffering: no`). A missing, unknown or revoked token is a 401 JSON error before any stream starts. It says "look at the board again" and carries no data; the CLI then reads with `list-tasks` as always. The listener, a worker's change watch and `board events` read the stream; `board events` finds what changed by comparing two `list-tasks` answers, using `noteCount` to see which threads grew.

- On connect the server sends the comment `: connected`, and every 25 seconds `: ping`. At each ping it checks the token again and ends the stream when it was revoked. The CLI treats 60 seconds without a byte as a dead connection.
- `event: tasks` with an empty `data:` follows a committed change to a task or a schedule: any write command except the ones below, and any change to a task or schedule from the UI. A failed or rolled back call sends nothing.
- `heartbeat`, `transcript`, `set-dirs` and `set-catalog` send nothing (every running task sends the first two every 15 seconds, and none of the four changes a dispatch decision), nor do the reads (`version`, `list-tasks`, `get-task`, `read-notes`, `list-schedules`) or the UI's changes to machines and keys. Nothing is sent when the hourly cleanup closes old Done tasks or deletes old transcripts; the timer covers those.
- Changes of one owner are held back 500 ms and sent as one event, so a burst gives one. An event reaches only the streams of tokens that belong to the same owner.
- The signal lives in the backend process, which is enough for one replica. A stream that was down misses events; the CLI runs one tick after every connect. Behind the board's web proxy the stream arrives as `application/json` and without the headers above, though its chunks still pass as they come: a client must not rely on the stream's response headers.

## Rules

- Every command is atomic under concurrent calls: the dispatchers of several machines, scripts, workers and people call at the same time.
- A write is visible to the next read.
- The server refuses an unsafe id or machine name with 400 and writes nothing; the CLI refuses it before it sends anything.
- `claim-task` answers 409 when the task is not free for this machine ("lost"): not in Todo, not due yet, a proposal, or pinned to another machine, by its session (a resume) or by its directory (`workdir` set and `machine` another one), so a claim planned before the user moved the task loses. The CLI treats that as an answer and moves on to the next task; every other non-200 answer is a failure.
- Every machine API request, the event stream's included, carries `X-Board-Client: <cli version>` (`x.y.z`, or `x.y.z-dev` from a checkout) and `X-Board-Client-Api: <level>` (an integer, the CLI's `API_VERSION`) and, from the same place in the code, `X-Board-Features` (see [Features](#features)). The server reads both leniently (the version as `^\d+\.\d+\.\d+(-[0-9A-Za-z.]{1,20})?$` of at most 40 characters, the level as an integer from 1 to 10000; anything else is ignored, never a 400) and stores them on the machine from `version` calls only, writing only when they changed: a worker that started before an update keeps sending old headers with its heartbeats, and those must not undo what the machine's next `version` call reported. The headers and the `cli` field of `version` are additive: older CLIs and servers ignore them, so no number moved.
- The CLI sends `version` once per process, before its first other call, and stops when the version handshake says the CLI or the server is too old (see above). It then derives its keys for the `owner` the server names, and stops when the board has no data key yet (`keyId: null`: set up encryption in the browser first) or its key's id differs from `keyId`.
- A sealed value comes back verbatim. The core parses `agent-board: started <iso>` notes (the start marker) and the first line of a review task's `input` (the PR URL) after opening them; the PR head is the `head` field, a blind index.
- A task an agent proposed (`createdBy: agent`) is the user's to start: the server refuses `update-task` with a new status and loses `claim-task` for it, whoever asks. The user starts it in the browser, which moves it into Todo with its prompt sealed again for the creator `user`; the board then stores that prompt and sets `createdBy` to `user`. The core never runs a task whose `createdBy` is `agent`.
- The board sends no link to a task. The CLI builds links itself from the `url` of its `web.json`.
- The core never writes to a task that is `closed`. A worker that finds its task closed after the run, or running again in another run (another `run` than it started with, or from a server without `task.run` another `runStartedAt`: taken back and run again, on this machine or another), drops its result. Any other outcome is judged on the task's `status` after the run: anything but `running` counts as reported (the agent reported, you answered while it was still ending its turn, or the task was taken back). A todo task whose worker unit is still active is not started again until the unit is gone.

### Runs

The machine fence (`machine`) cannot tell two runs on the same machine apart: when a run is taken back and the same machine claims the task again, an agent left over from the old run, its process still alive, would pass every check. A server with `task.run` gives every claim a run id, the task's `run` while it runs, and checks it on the calls a run makes for its own task.

- `claim-task` makes a new `run` and the task drops it whenever it leaves `running`.
- The worker reads it from its task, sends it as `run` with its own calls for the task, and hands it to the agent as `AGENT_BOARD_RUN` next to `AGENT_BOARD_TASK`. The agent's `board` sends it with its calls for that task (not for any other). Both send it only to a server whose `features` name `task.run`.
- `heartbeat`, `pause`, `wait`, `fail`, `ask`, `stopped`, `run-inbox` and `ack-messages` with `run` act only while the task runs in that run. Another run gets the answer the command gives a task that is not running (or, for `heartbeat` and `fail`, changes nothing): 409 `the task is running in a later run, not in this one`, `applied: false`, or nothing. The machine is checked first, so another machine still gets its own answer (403 for `run-inbox`, `ack-messages` and `stopped`).
- `update-task` with `run` is refused with 409 while the task runs in another run. A status change with `run` also needs the run to hold the task: once the task left `running` (the agent asked, the user took it back or moved it) it is 409 `the task is <status>, no longer running in this run`, and nothing changes. The other keys still go through on a task that left `running`, so the worker can store the directory the session ended in. `board move` from inside a run, on its own task, reports the 409 as a usage error that tells the agent not to move it again and to end its turn.
- A `run` that is not a run id is 400. A call without `run` is checked as before, by status and machine: older CLIs, the browser, `board move` from outside a run, and runs that started before the server had `task.run`.

## Task

```json
{
  "id": "Ab3dEf9x",
  "title": "abe1.…",
  "input": "abe1.…",
  "status": "needs-me",
  "createdBy": "user",
  "priority": "normal",
  "model": null,
  "closed": false,
  "machine": "laptop",
  "sessionId": "591d2ec1-d4ab-4e26-ac04-ed303f8fa44a",
  "workdir": "abe1.…",
  "pr": null,
  "prState": null,
  "prs": [],
  "promptPrState": null,
  "next": "fresh",
  "head": "abh1.…",
  "openQuestion": true,
  "lane": null,
  "borrowed": false,
  "lastActiveAt": null,
  "runStartedAt": null,
  "paused": false,
  "notBefore": null,
  "scheduleId": null,
  "wakeAt": null,
  "waitCheck": false,
  "woken": false
}
```

All twenty-eight fields are required, except that a missing `model` (a server without `task.model`) reads as `null`, a server without the `task.pr` feature leaves `pr` out, one without `task.pr-state` leaves `prState` out and one without `task.prs` leaves `prs` and `promptPrState` out; `stopRequested` is optional (a server without `run-inbox` does not send it, and a client reads absent as `false`), and so is `run` (absent unless the task is running on a server with `task.run`) and `noteCount` (absent from a server without `task.note-count`). A task without an agent has no `agent` key. The CLI's plaintext `Task` adds `labels` and `unreadable`.

| `wakeAt`        | Waiting only: when the wait ends at the latest (a timer's end, a check's timeout), ISO 8601; otherwise `null`. The server clears it whenever the task leaves Waiting.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `waitCheck`     | Waiting only: a check on `machine` may end the wait earlier; otherwise `false`. | `stopRequested` | Optional, absent from a server without `run-inbox`. | `woken`         | The task's wait ended into Todo (by `wake`, Wake now, a reply or a drag) and it has not run since. Answered by `list-tasks`, `get-task` and the answer of every command that returns a task; the browser's own API does not carry it.                                                                                                                                                                                                                                                                                                            |

Pickup order is the order of the array that `list-tasks` returns: within a status, the first task is the top. In Todo the store lists resumes (`next: resume`) first, then by `priority`, then by manual order; the lanes pick from that order. Delayed tasks (`notBefore` in the future) come last in Todo, by `notBefore`; once due they sort like any other. The dispatcher does not try to claim a delayed task. Waiting lists the wait that ends first on top; nothing claims a task there.

## Schedule

```json
{
  "id": "Sc3dEf9x",
  "title": "abe1.…",
  "input": "abe1.…",
  "priority": "normal",
  "model": null,
  "machine": "laptop",
  "workdir": "abe1.…",
  "everyMs": 7200000,
  "cron": null,
  "timezone": null,
  "anchorAt": "2027-01-01T08:00:00.000Z",
  "nextRunAt": "2027-01-01T10:00:00.000Z",
  "remaining": 3,
  "until": null,
  "paused": false,
  "ended": false,
  "occurrenceTaskId": "Ab3dEf9x",
  "createdAt": "2026-11-14T10:00:00.000Z"
}
```

All eighteen fields are required, except that a missing `model` (a server without `task.model`) reads as `null` (`title`, `input` and `workdir` sealed for the schedule, and `agent` when it has one, which a server without `task.agent` leaves out; `id` is chosen by the client). Exactly one of `everyMs` (an interval in ms, at least one minute, on the grid `anchorAt + k * everyMs`) and `cron` (5 fields, read in the IANA zone `timezone`, which a cron rule needs) is set. `anchorAt` is the first run of an interval, or the time a cron rule matches from. `nextRunAt` is the start time of the pending occurrence (read from its task, so a changed delay shows), `occurrenceTaskId` its task; both are `null` while the schedule is paused with nothing waiting, and once it has ended. `nextRunAt` is also `null` while `occurrenceTaskId` is set when the pending task has no start time any more (it was told to run now): it is due now. `remaining` is the number of occurrences still to be made after the pending one (`null`: forever), `until` the last time an occurrence may start. `machine` and `workdir` pin the occurrences, or are both `null`.

A schedule always has at most one pending occurrence, a task in Todo with `scheduleId` set and `notBefore` at `nextRunAt` (until someone changes it); its `createdBy` is `user`, and its `title`, `input`, `workdir` and `agent` are the schedule's ciphertext, copied unchanged and opened against the schedule's id (the worker may later replace the directory with one sealed for the occurrence and its schedule; see [Encryption](encryption.md#encryption)). When that task leaves Todo (a claim, `update-task`, a move, a close), in the same transaction the server makes the next one: the first match of the rule after the previous occurrence's time that is not in the past, so missed runs are skipped. With nothing left (`remaining` used up, or the next match after `until`) the schedule ends (`ended: true`) and makes no more. A task that was an occurrence and returns to Todo later does not trigger another; only the pending one does.

## Note

```json
{
  "id": "n1",
  "body": "abe1.…",
  "preview": "abe1.…",
  "createdAt": "2026-11-13T10:00:00Z",
  "author": "agent",
  "kind": "comment"
}
```

A message the user sent to a running agent (`Send`, `Stop & send`) adds `pending: true` until a worker acknowledges it with `ack-messages` (or the run ends: see `run-inbox`), and after that `deliveredAt` (ISO 8601) when a worker handed it over mid-run. Both are optional and absent from a server without `run-inbox`. `queued: true` marks every note written to a running agent and is never cleared. A resume prompt leaves out a note with `deliveredAt` (the agent has it already) and, besides what the user wrote since the agent last spoke, carries the `queued` notes without `deliveredAt` written since the previous run started, wherever they fall in the thread.

`author` is `agent`, `user`, `system` or `server`; `kind` is `comment`, `question`, `answer`, `event` or `polish`. `body` is sealed for its task, author and kind, except on an `author: "server"` note, whose body is plain text and one of the fixed event texts (see [Encryption](encryption.md#encryption)); `preview` is a sealed preview or `null`. A comment by the agent may add `suggestion`, a sealed reply drafted for the user. A question note adds `questions` and an answer note `answers` (both sealed JSON: the list `ask` took, and `{"questions": [...], "answers": [...]}` with one `{"selected": [labels], "other"?: text}` per question) and `questionNoteId`, which only informs. The CLI's plaintext `Note` has `text` instead of `body`, keeps a server event as `author: "server"`, gives an answer note the `questions` from its own envelope, and adds `unreadable`. A resume prompt is built from the `user` notes after the last `agent` note.

- `version`: see the rules above.
- `add-task`: `id` is the client's (the safe shape above; a taken id is 409, whoever holds it, with the same message), `title` and `input` are sealed (an empty input is sealed too), `workdir` sealed, `agent` sealed (the key is only for a CLI whose server lists `task.agent`, which refuses to send it otherwise; a plain-text value is 400), `dedupeKey` the blind index of the key (`abh1.…`, else 400), `status` is `backlog`, `todo` (the default) or `needs-me` (a task gets into `running`, `waiting` and `done` only through `claim-task`, `wait` and a close; anything else is 400), `priority` to the parent's with a `parentId` and to `normal` without, `model` (a name of the shape above, else 400; the key is only for a CLI whose server lists `task.model`) to none, which is claude's default, `createdBy` (`intake`, `user`, `agent`) to `user`. `machine` and `workdir` come together and pin the task there. The new task goes to the bottom of its status. A plain-text `title`, `input` or `workdir` is refused with 400. With a `dedupeKey` that a task already has, nothing is created: the answer is that task with `created: false`. `createdBy: agent` makes the task a proposal: it lands in `backlog` whatever start `status` the draft names. `head` is the blind index of the sha (`abh1.…`, else 400). `notBefore` (ISO 8601) is accepted only with status `todo` (else 400).
- `update-task`: at least one key; unknown keys are a failure. `input` and `workdir` are sealed. A status or priority change puts the task at the bottom of its new place. A status change of a proposal is refused with 403. Leaving `needs-me` for `todo` or `done` clears `openQuestion`. `head` is a blind index, or `null` to clear it. `sessionId` is a UUID or `null`. `expect` is a status and not a change: when the task's status differs under the update's lock, nothing is written and the answer is 409 (`board move --expect` and the requeue of `board schedule --key` use it, so a move planned from an earlier listing cannot hit a task a dispatcher claimed since). It does not count as a key. `notBefore` is an ISO 8601 time, or `null` to clear it; a time is refused with 409 unless the task ends up in `todo`.
- `configure-task`: needs the `task.configure` feature (the CLI refuses without it). The user's edit of a task's settings, in one atomic step; at least one key, and an unknown key or value is 400. `priority` works as the board's priority picker does: the task goes to the bottom of its new band and the `Priority a → b.` note is written (the one server event text that exists for it); the same priority changes nothing. `model` is a model name (`isModelName`) or `null` for claude's default, applies from the next run on, and is allowed in any status. `place` is `{"workdir": <sealed>}` or `null`. The directory is sealed under the task's `workdir` binding, and the machine is the token's own, never read from the body (a `machine` key is 400): a machine pins a task to itself only. The server sets `workdir` and `home_workdir` (what Re-run fresh restores) to the new envelope, `machine` to the token's machine, and drops the session (`sessionId` null, `next` `fresh`, no pause or wake); `null` clears `workdir`, `home_workdir` and `machine` and drops the session the same way. The status stays, so an open question in Needs me stays open. A request with `place` on a `running` or `waiting` task is refused whole with 409 and nothing is written, `priority` and `model` in it included; without `place`, model and priority go through in any status. No `run` fence: a run is not a caller of this command, and the CLI refuses it inside one. No note is written for a model or directory change, because a server event text unknown to an installed CLI would not pass its check. The browser makes the same change with `tasks.configure`.
- `claim-task`: `todo` to `running` for the machine, at the bottom of running, in one atomic step. Lost when the task is not in `todo` (a `backlog` task is never claimed), or when it is a resume (`next: resume` with a session) pinned to another machine. A token claims for its own machine only. Lost for a proposal (and for any task whose `createdBy` is `agent`). Sets `runStartedAt` and a new `run`; `paused` stays as it is. Lost while `notBefore` is in the future.
- `add-schedule`: `id` is the client's, as for `add-task` (409 when taken). Exactly one of `everyMs` and `cron`; `cron` needs its `timezone`, and `timezone` goes only with `cron`. `title`, `input` and `workdir` are sealed, and so is `agent` (the key is only for a CLI whose server lists `task.agent`); the server copies `agent` into every occurrence next to the prompt. `machine` and `workdir` come together. `startAt` (ISO 8601; default now) is the first run of an interval and the earliest match of a cron rule. `times` (a positive integer up to 2147483647, the number of occurrences in all) and `until` (ISO 8601) exclude each other; neither means forever. The answer is 400 for a cron expression the server cannot read (6-field patterns included), an unknown time zone, an interval under a minute or over 10 years (`MAX_INTERVAL_MS`), or a rule with no run before `until`, and nothing is written. The schedule and its first card are made in one transaction.
- `update-schedule`: `paused: true` takes the pending occurrence off the board when it never ran (still in Todo, no session, no run) and gives its run back to `remaining`; `paused: false` makes the next occurrence at the first match from now. 409 for an ended schedule. Pausing a paused schedule, or resuming a running one, changes nothing.
- `remove-schedule`: deletes the schedule and a pending occurrence that never ran; tasks that ran stay, keeping their `scheduleId`. 404 for an unknown schedule.
- `add-note`: author `agent` makes a `comment` (or, with `kind: "polish"`, a `polish` note: the sealed body is the JSON `{"target", "title", "prompt"}` and the preview the start of the prompt), `system` an `event`; a polish note from `system`, or any other `kind`, is 400; both bodies are sealed (else 400), and the CLI refuses an empty text before sealing. `preview` is the sealed start of the text, or absent. `suggestion` is a sealed reply for the user and only author `agent` may send one (else 400).
- `add-pr`: needs the `task.prs` feature (the CLI sends `set-pr` instead when the server lacks it, so a later PR replaces the earlier one there). Appends the sealed `pr` to the task's `prs` with an unknown state, and sets `updatedAt` and sends the change notification, as `set-pr` does. The server cannot read the URL and so cannot see that it repeats one; `board pr` reads the task first and sends nothing for a URL it already lists. A task holds at most 20 PRs: the 21st is 400. 400 for a value that is not an envelope or is over its limit (`SEALED_LIMITS.pr`) and for any other key, 404 for an unknown task. Like `add-note`, any token of the owner may call it: the binding, not the token, says whose value it is. The CLI checks that the URL is a GitHub pull request before sealing.
- `remove-pr`: needs the `task.pr-remove` feature (the CLI refuses without it, and does not fall back). Body `{ "pr": string }`, the `id` of an entry of the task's `prs`, which is what `board pr --remove` reads from `get-task` after matching the URL. It deletes that entry, and only if it belongs to this task, and sets `updatedAt` and sends the change notification, as `add-pr` does. An id the task does not list changes nothing and is still 200, so a retry is safe; the PR the prompt names is not an entry and cannot be removed. The task's legacy `pr` and `prState` follow from the entries left. 400 for a value that is not a safe id and for any other key, 404 for an unknown task. Any token of the owner may call it, and the browser removes an entry the same way (it deletes a row and seals nothing).
- `set-pr`: needs the `task.pr` feature (the CLI refuses without it), and is what a CLI without `task.prs` sends. It makes the sealed `pr` the task's only entry in `prs`, with an unknown state, replacing the entries it had (the last wins); `promptPrState` stays as it is. Same errors and the same `updatedAt` as `add-pr`.
- `set-dirs`: needs the `machine.dirs` feature (the CLI refuses without it). Replaces the directory list of the token's own machine, which is the only row it touches (the token names the machine, and a `machine` key is not read): `dirs` is the sealed list (`machine.dirs`, bound to `machine:<name>`: one JSON document `{"dirs":[{"path":"/abs/path","label":"Board"}]}`, `label` only when the directory has one, at most 256 KiB), `index` the blind index (`abh1.`) of `dirs:<machine>:<that document>`, and the server stores both with the time. 400 for a value that is not an envelope or a blind index, one that is too long, a missing key or an unknown key, and nothing is stored. It sends no `tasks` event. The list is advice for the New task form's Working directory field: no CLI reads it back, and the machine's own `config.json` is what workers enforce. A CLI calls it when `config.json` has a `dirs` key and the index in its `version` answer differs from the index of the list it would send: at the start of every dispatch tick, and after `board dirs add` and `rm`. Revoking a machine or issuing it a new token clears the list.
- `set-catalog`: needs the `machine.catalog` feature (the CLI refuses without it). Replaces the catalogue of the token's own machine, as `set-dirs` does for its list (the token names the machine, and a `machine` key is not read): `catalog` is the sealed catalogue (`machine.catalog`, bound to `machine:<name>`, so it opens neither as another machine's nor as a directory list; one JSON document of at most 256 KiB), `index` the blind index (`abh1.`) of `catalog:<machine>:<that document>`, and the server stores both with the time. The document is `{"claude":"2.1.326","models":[{"value","label","description"?}],"skills":[{"name","description"?,"argumentHint"?}],"dirs":{"/abs/path":[{"name",...}]}}`: `skills` are the skills every directory the machine asked about has, and `dirs` lists, per directory, those only it has. At most 50 models, 500 skills, 200 directories and 200 skills in one; a skill name is letters, digits and `_ . : -`, starting with a letter or digit, at most 100 characters; a description is one line of at most 200 characters and an argument hint of at most 100. A reader opens it with `parseMachineCatalog` in `packages/shared/src/catalog.mts`: an entry of the wrong shape is dropped and the rest is kept, a list over its cap makes the whole document unreadable, and other keys are ignored so that a later CLI can add some. 400 for a value that is not an envelope or a blind index, one that is too long, a missing key or an unknown key, and nothing is stored. It sends no `tasks` event. The catalogue is advice for completing `/skill` in a prompt or reply and for offering the machine's models: no CLI reads it back, and no run depends on it. A CLI calls it when the index in its `version` answer differs from the index of the catalogue it composed from what it has asked `claude`, at most one directory per dispatch tick (see [Skills and models](workers.md#skills-and-models-on-the-board)). Revoking a machine or issuing it a new token clears it. The browser reads catalogues with `machines.catalogs`, a call of its own that returns, for each machine that has one and is not revoked, its `name`, the sealed `catalog` and `catalogUpdatedAt`; it is not part of `machines.list`, which the board page polls.
- `set-pr-states`: needs the `task.prs` feature (the CLI falls back to `set-pr-state` without it, for the one PR that server states). Body `{ "prompt"?: "open" | "merged" | "closed", "prs"?: [{ "id": string, "state": "open" | "merged" | "closed" }] }` with at least one of the two keys and at most 20 entries in `prs`: `prompt` becomes `promptPrState`, and each entry sets the `state` of the entry of `prs` with that `id`. An `id` that is not one of this task's entries is ignored, so the call is safe to repeat, and an entry of another task is never touched. It changes nothing else (not the status, `updatedAt` or a running task's pause), so a run is never disturbed. There is no way to clear a state; `set-pr` resets the one it makes. 400 for any other value or key, an unsafe id or too long a list, 404 for an unknown task. Only the dispatcher calls it (see [Workers](workers.md#how-it-decides)).
- `set-pr-state`: needs the `task.pr-state` feature (the CLI refuses without it), and is what a CLI without `task.prs` sends. Body `{ "prState": "open" | "merged" | "closed" }`; it sets the `state` of the newest entry of `prs` when the task has entries, else `promptPrState`, which is the PR that CLI states (`pr`, else the one the prompt names). Like `set-pr-states` it changes nothing else. There is no way to clear it. 400 for any other value or key, 404 for an unknown task.
- `heartbeat`: sets `lastActiveAt` to now with the lane, on a task running on the token's machine only; on any other it changes nothing.
- `heartbeat`, `pause`, `fail`, `wait` and `wake` act only for the token's machine, the one whose claim holds the task (`machine`). A call from another machine gets the answer it would get had the task left `running` (or `waiting`): a worker whose run was taken back and claimed elsewhere cannot touch the new run.
- With `run` (see [Runs](#runs)) the same commands, and `ask`, `stopped`, `run-inbox`, `ack-messages` and `update-task`, also act only for that run: an earlier run on the same machine gets the answer another machine would get.
- These checks keep workers from tripping over each other; they are not a boundary between machines. Every token of an owner can act on that owner's whole board: `add-task`, schedules, notes, `add-pr`, `remove-pr` and `set-pr` by design, and `update-task` without `run` on any task, a running one included, so that `board move` works from any machine. A leaked token, with the data key from the same `env` file, controls the whole board until it is revoked on the Settings page.
- `transcript`: appends a run's condensed events (see `packages/shared/src/transcript.mts`; at most 5000 per call, each with an integer `seq` from 0 to 2147483647, a parseable `at` and a `parent` that is `null` or a tool use id of up to 256 letters, digits, `_` and `-`, or the call fails with 400; the batch's `sessionId` is a UUID or `null`; the CLI drops a `parent` of any other shape to `null` before sending). `data` is the sealed JSON of the event without its output. A `tool_result` also carries the sealed `output` and `outputSize`, its length in characters counted by the client (the server cannot read it; it is bounded, nothing more); any other event carries neither. an event already stored (same run and `seq`) stays as it is, so a retried batch is harmless.
- `pause`: a running task of the token's machine only (else 409). Adds the sealed note as a `system` event, then moves the task to Todo with `next: resume` (`fresh` without a session), at the top, and sets `paused`.
- `run-inbox`: for a running task of the token's machine only (409 when it is not running, 403 when another machine claimed it). A call also marks the run as one that reads its inbox. `stop` is true while the user's stop request stands. With `stopMessage` (the id of one of `messages`) it is Stop & send: the worker interrupts, hands over all the messages and the run carries on. Without it the stop is plain: the worker interrupts and ends the run and hands nothing over, so earlier pending messages stay pending; `messages` are the user's notes with `pending: true`, sealed as any note. The worker reads it every watch tick and whenever the event stream says tasks changed, and answers with `ack-messages`.
- `ack-messages`: same rule as `run-inbox`. The listed pending notes of the task stop being pending and get `deliveredAt`; unknown ids and notes that are no longer pending are ignored. With `stop: true` the stop request (and its `stopMessage`) is cleared, so a request is acted on once. At most 100 ids; the ids may be empty.
- `stopped`: the worker ended the run on the user's request, with nothing to carry on with. Same rule as `run-inbox`. Adds the sealed note as a `system` event and moves the task to `needs-me` as the user asked, clearing the stop request. It is exempt from the redirect below: pending notes just become replies (`pending: false`), so the next Send & continue carries them.
- A run that ends while the user's messages are still pending (the worker never got to them: it had closed the agent's stdin or crashed) must not lose them, and the server does it in one place for every way out of Running (`update-task`, `ask`, `wait`, `pause`, `fail`). This applies only to a run whose worker has read `run-inbox` (the server remembers that for the run, the worker looks once right after the process starts): a CLI before 0.9 never would find the message in a resume prompt. For any other run, and for the user's own stops (`stopped`, Take back), the pending notes just become plain replies and the task goes where it was going. The pending notes stop being pending (they are replies now, with no `deliveredAt`, so the resume prompt carries them), and a task that would have gone to `needs-me`, `done` or `waiting` goes instead to the top of Todo with `next: resume` (`fresh` without a session); the open question and the wait go, and a server event "Your message reached the agent after its run ended; resuming with it." goes into the thread. Leaving Running always clears the stop request.
- `wait`: a running, open task of the token's machine only (else 409). Adds the sealed note as the agent's `comment` (sealed for author `agent`, kind `comment`), then moves the task to `waiting` with `wakeAt` (ISO 8601, in the future and at most 7 days ahead, else 400), `waitCheck` from `check`, and `next: resume` (`fresh` without a session). `runStartedAt` and the run details go, as for any task that leaves Running.
- `wake`: in one step, if the task is still `waiting` on the token's machine and not closed, adds the sealed note as a `system` event and moves the task to the top of Todo with `next: resume` (`fresh` without a session) and `woken: true`, and answers `applied: true`; otherwise it changes nothing and answers `applied: false`. The note starts with `agent-board: wait over:`, and the worker hands the rest of the newest such note since the agent last spoke to the resumed agent.
- No other command takes a task into `waiting`: `update-task` with that status and `add-task` with it are 400. A task that leaves `waiting` for `todo` by a drag or a reply is woken (`woken: true`, `next` as for `wake`); one that leaves it for another status just loses its wait.
- `fail`: in one step, if the task is still `running` on the token's machine and not closed, adds the sealed note as a `system` event and moves the task to `needs-me`, and answers `applied: true`; otherwise it changes nothing and answers `applied: false` with the task as it is.
- `ask`: a running task of the token's machine only (else 409, with nothing written). Adds a question note with the sealed questions, and moves the task to `needs-me` with `openQuestion: true`. Refused with 403 for a proposal. The 409 stops a stale agent (its run taken back, the task finished, or run again on another machine) from pulling the task into Needs me with a question; `board ask` reports it as a usage error that tells the agent not to ask again and to end its turn. With `run`, a later run of the task on the same machine is refused the same way. The CLI validates the questions before sealing (1 to 4; a header of at most 16 characters; 2 to 4 options with different labels, at most one `recommended`); the server cannot.
