# Architecture

This document explains how agent-board is put together and why, and which rules a change has to keep. The other files in `docs/` are the detailed reference for each part.

## The idea

The board started as a replacement for a Trello board fed by headless PR reviews. Trello centred cards on their description rather than the conversation, had thin formatting, and had no clear "your turn" step and no way to pick from options. So agent-board puts the thread first. A run that reports, asks or fails ends in `needs-me`, and the next step is always a button: answer, reply, re-run, done.

PR review was the first use. A task is any prompt you would type into Claude Code, and its leading `/skill` decides which lane runs it.

## Components

```
              ┌─────────────────────────────── board server ──────────────────────────────┐
 browser ───▶ auth proxy: login, sets Remote-User ──▶ Caddy ── /trpc ──────────▶ backend ──▶ Postgres
 workers ───▶ auth proxy: bearer route, no login ───▶ Caddy ── /api/machine/* ─▶ backend
              └───────────────────────────────────────────────────────────────────────────┘
                    ▲ machine API (POST, sealed)        │ SSE "tasks changed"
                    │                                   ▼
 worker machine:  board internal listen ──▶ dispatch tick ──▶ systemd-run (macOS: detached process) ──▶ worker ──▶ claude -p
                  timer: dispatch (2 min)                                     agent ──▶ board comment / ask / wait
```

## A task's life

1. **Created.** `board schedule` (bound to this machine and directory), the New task form, a script that calls `board schedule --key` (a review request on GitHub, say), a schedule's next occurrence, or an agent's `board add` proposal. A client that creates a task picks its 12-character id and seals title, prompt and directory against it. The server creates a schedule's occurrence itself, with a copy of the schedule's ciphertext bound to `schedule:<id>`.
2. **Todo.** The server emits a `tasks` event on the SSE stream of every machine of that owner. Each machine's listener runs a dispatch tick; the 2-minute timer is the fallback.
3. **Claimed.** The dispatch tick plans free lane slots, calls `claim-task` (atomic, one machine wins) and starts the worker as a transient systemd unit `agent-board-<id>` (on macOS, as a detached process tracked by a pid file in the run directory; `setup/process-system.mts` is the second implementation of `System`).
4. **Running.** The worker opens the sealed prompt and starts `claude -p` with the board's rules (`--append-system-prompt`) and a PreToolUse hook (`--settings`). The prompt goes in on stdin as a stream-json user message, and stdin stays open: the worker later writes your messages, a pause request and interrupts to it. The hook keeps a heartbeat and records the working directory. The worker streams condensed, sealed transcript events to the board every 15 s.
5. **Reporting.** The agent uses `board comment`, `board ask`, `board wait`, `board pr` and `board add`. These are the same CLI, authenticated by the machine's token, which reaches every task of the owner. `AGENT_BOARD_TASK` marks the process as a run, so `board schedule` refuses and `board polish` posts on the run's own task. `AGENT_BOARD_RUN` is the board's id of the run (see [Design decisions](#design-decisions)): the agent's calls for its own task carry it, so an agent left over from an earlier run cannot ask, wait or move the task under a later one. The browser may remove a PR the agent reported (`tasks.removePr`, and `remove-pr` for the CLI) because that deletes a row and seals nothing; it still never writes a reported PR, which only an agent seals.
6. **Needs me.** The run ends. You answer, reply, re-run or mark it done in the browser. A reply puts the task back in Todo with `next: resume`, and the machine that holds the Claude session resumes it, in the directory the agent last worked in.

## Trust model

The design assumes the server and database may be hostile, and that any PR text an agent reads may be too. Two mechanisms carry this.

**Who created a task, and the agent it names, decide how it runs.** A task that names an agent runs as that agent, whoever made it (see [Agents](workers.md#agents)); otherwise `createdBy` is the permission bit:

| Creator  | Runs as                                                                                                                                                |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `user`   | Your full settings and `--permission-mode auto`, as if you typed the prompt yourself.                                                                  |
| `intake` | Only on the tasks of the removed built-in intake. With an agent they run as it; without one they never run, because the rules they ran under are gone. |
| `agent`  | Never runs. A proposal waits in `backlog` until you press Start, and then the browser seals the prompt again as yours.                                 |

**Every content field is sealed for its purpose.** The clients encrypt with AES-256-GCM. Each envelope's additional data binds it to the owner, the field, the row and the creator or author. So the server cannot move a prompt to another task, relabel a prompt of the removed intake as yours, present an agent's note as your reply, or write a note of its own beyond the fixed event texts. A value that does not open under its exact binding is unreadable, and nothing falls back to a looser reading. The table of bindings is in [encryption.md](encryption.md), and `packages/shared/src/sealing.mts` is its single implementation.

What the server can still do: decide when and where a task runs, reorder or withhold notes, and replay older values of the same task. [encryption.md](encryption.md#encryption) lists all of it.

**Sign-in is the proxy's job.** The backend has no login of its own. It takes the user from the `Remote-User` header and checks `Remote-Groups` against `ALLOWED_GROUPS`. That is only safe behind a proxy that signs the user in, strips any `Remote-*` header the client sent, and sets its own. Stripping at the edge does not cover callers that reach the backend without passing the proxy, such as another pod in the cluster. So the backend also takes those headers only together with `Board-Proxy-Secret`, a shared secret (`PROXY_SECRET`) that the web container's Caddy adds to every request it proxies. The backend compares it in constant time and refuses to start in production without it. Without the secret, a request to `/trpc` is a 403 whatever `Remote-*` headers it carries. Never expose the backend's `/trpc` without such a proxy. The machine API is the exception: the proxy lets `/api/machine/*` through without a login, and the backend checks the bearer token itself. Which proxy does this is a deployment choice; [operations.md](operations.md#the-board-server) describes the current one.

**Multi-tenancy.** Each signed-in user (`Remote-User`) has a private board. Requests run as the unprivileged `board_app` role with row-level security on `app.owner`, set per request transaction (`apps/backend/src/db/scope.ts`). The privileged `DATABASE_URL` is used only at start, for role setup and migrations. There is deliberately no fallback to it, because a superuser or table owner bypasses RLS.

**No sandbox.** A worker runs as you. A sandbox per command could not support implementation work (worktrees, installs, pushes), and once an agent may push, the boundary that matters is the machine and its credentials. Permission rules are not a security boundary. A dedicated OS user for workers is the planned way to get one.

## Versioning

The CLI sends `version` once per process and checks the server's API range (see [machine-api.md](machine-api.md#version-handshake)): it stops when its `API_VERSION` is below the server's `minClient`, or when the server's version is below its own `MIN_SERVER`. A server that is merely older makes the unattended dispatch tick skips quietly until it catches up. CLIs up to 0.7.0 compare `contract` exactly, so the server keeps answering it (`LEGACY_CONTRACT`, 9) until a break raises `MIN_CLIENT` above it. The server deploys on every merge to `main`, while the CLI updates only through a `cli-v*` release and `board self-update`, so a raised `MIN_CLIENT` leaves every older machine refusing to work until it is updated.

- The numbers are a break level, not a count of changes. An additive change adds a **feature name** and bumps no number, so parallel branches do not collide: a new machine command, a new optional request field, a new enum value with a vocabulary row (see [machine-api.md](machine-api.md#features)). The server answers the features it has, the CLI checks the one it needs and a missing one disables only that command; the CLI sends the vocabulary it understands, and the server leaves out what the client cannot read. `board attach` and suggested replies shipped this way.
- A new enum value in a response is additive if it gets a vocabulary feature, and breaking if it does not or if it changes what an existing value means: then older CLIs parse it strictly (a list skips an item it does not know, a single object fails). Contracts 8 (`polish` notes) and 9 (`waiting`) were bumped for this, before the vocabulary features existed.
- A break (`API_VERSION` raised, then `MIN_CLIENT` to it) ships with a CLI version bump, an Upgrading note in [setup.md](setup.md#upgrading), and a CLI release, which CI makes after the merge, before the images. CI fails a pull request, and a push to `main`, that raises it without a CLI version above the newest `cli-v*` tag, and runs the newest release against the pull request's server.

## Design decisions

| Decision                                                                                                                                                                  | Why                                                                                                                                                                                                                      | Rejected                                                            |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| A task is a prompt; its leading `/skill` picks the lane                                                                                                                   | Works for any skill without per-type code                                                                                                                                                                                | Task types and labels in config                                     |
| Workers on your own machines, not in the cluster                                                                                                                          | They need your checkouts, logins and Claude Code session files                                                                                                                                                           | Hosted workers                                                      |
| Lanes with borrowing; lane bias beats priority                                                                                                                            | Parallelism per kind of work without a scheduler; idle slots never wait                                                                                                                                                  | Global priority queue                                               |
| Pause and stop through claude's stream-json stdin: a message, then an interrupt                                                                                           | The session stays clean (no refused tool calls to confuse it), a paused run can say where it stopped, and you can reach a running agent                                                                                  | A hook that denies tool calls; killing runs                         |
| Heartbeat on every tool call; 15 min idle, 6 h max                                                                                                                        | Foreground Bash is capped at 10 min, so a quiet agent is stuck                                                                                                                                                           | Fixed run timeouts                                                  |
| SSE for "something changed", writes stay POST                                                                                                                             | Plain GET on the existing token route, through Caddy                                                                                                                                                                     | WebSocket                                                           |
| `board events` derives changes on the client by comparing two listings                                                                                                    | The stream carries no data and the server cannot read titles or notes, so only a client with the data key can say what changed; a note count per task (`noteCount`) tells which threads to read                          | A server-side change log; sending content over the stream           |
| Keep the 2-minute timer next to the listener                                                                                                                              | The stale sweep, missed events and a dead listener have no event; delays, waits, checks and take-backs tick on the listener's timer for what each tick says is next due                                                  | Event stream only; a server-side tick                               |
| Board rules and hook passed per run (`--append-system-prompt`, `--settings`)                                                                                              | Nothing to install in `~/.claude`, so no machine can miss it                                                                                                                                                             | A Claude Code plugin                                                |
| The directory list is enforced from the machine's own `config.json`                                                                                                       | The server may be hostile: a list it holds, or the copy each machine sends it (`machine.dirs`, which the New task form offers), is advice the worker cannot rely on, so the worker consults only the file on its machine | Enforcing a list the server holds                                   |
| Each machine sends a sealed catalogue of its skills and models, found by asking `claude`                                                                                  | The browser completes `/skill` and offers models, and only the program that runs a task knows its plugins and bundled skills. The probe costs no tokens, and the copy is sealed advice that no CLI reads back            | Reading skill folders; an unsealed list                             |
| Each machine sends a sealed usage status (limits, readings, the tasks it holds and the tasks it leaves open)                                                              | The browser can say which machine holds a task, for which window and until when; the open list lets it tell a held task from one that only waits for a slot elsewhere. Sealed display data that no CLI reads back        | Showing the dispatcher log; a server-side hold                      |
| `board ask` instead of AskUserQuestion                                                                                                                                    | Headless `claude -p` offers no AskUserQuestion; the hook stays offline, so it never slows a tool call                                                                                                                    | Waiting on Claude Code                                              |
| A schedule keeps one pending card; missed runs are skipped                                                                                                                | A machine that was off finds one card, not a pile; no server timer                                                                                                                                                       | Catch-up runs                                                       |
| Agent output that changes your text is a suggestion you apply (`board polish`, `--suggest`)                                                                               | An agent must never seal anything as `user`                                                                                                                                                                              | Agents editing tasks                                                |
| Bun-compiled release binary                                                                                                                                               | No Node to find on a worker machine, the most fragile part of installing                                                                                                                                                 | esbuild bundle on Node                                              |
| Duplicate check by a Haiku call for scheduled tasks; a blind-indexed dedupe key only for scripts (`board schedule --key`)                                                 | A key does not fit free-form prompts                                                                                                                                                                                     | Dedupe keys everywhere                                              |
| Slack intake was built and removed (`/board <text>`, a Send to board shortcut, an inbox)                                                                                  | Not useful as an intake: the bot had to be invited to every channel, and a worker can read a Slack message through your own claude.ai connector when a task links to it                                                  | A Slack app as the way in                                           |
| An open task's worktree is locked with `git worktree lock`; the dispatcher unlocks it once the task is finished                                                           | A cleanup's plain `git worktree remove` refuses and names the task. The worker never learns that a task is done, so the 2-minute sweep that already drops a finished task's files takes the lock off                     |
| Every claim gets a run id; a run's calls for its task name it                                                                                                             | Status and the token's machine cannot tell two runs on the same machine apart: an agent whose run was taken back and claimed again there would pass every check. The id is opaque and exact, unlike `runStartedAt`       | Comparing `runStartedAt`; fencing by machine only                   |
| Agent definitions are files on each machine (`config.json` or `agents/<name>.yaml`); `board agents add` shows every grant and asks before it writes, and never re-fetches | A definition decides what an unattended run may do, so it must not change without the user reading it: no auto-update from a URL, and no copy on the board, which could swap one machine's rules for another's           | Definitions held (sealed) on the board; URLs that update themselves |
| Watches run in a unit of their own (`agent-board-watch.service`) with all state on disk                                                                                   | Polls leave the dispatch tick's 2-minute pace and 45-second budget; the unit can be restarted at any time (self-update, a crash) without losing a watch, and the listener stays as it is                                 | Watches inside the listener; a server-side poller                   |
| An event reaches the agent from a spool file on the machine, never from a board note                                                                                      | The server can withhold or replay a note, and an event can hold text you did not write; the file is deleted only once handed over, so an event is not lost in the race between a park and its wake                       | Reading the wake note back as today's wait does                     |
| The unit and the dispatch tick share watches through a heartbeat file, and finish one by renaming its file                                                                | No lock to leak when a process dies; whoever renames first writes the event                                                                                                                                              | File locks; a socket between the two                                |
| A woken task waits for a slot of its lane like any resume                                                                                                                 | The lane limit stays strict; an event for a live run does not need a slot at all                                                                                                                                         | Overbooking a lane by one for a wake                                |

## Rules for changes

Break one of these only with a decision recorded here.

1. **The server never needs plaintext.** New content fields are sealed in the client with a binding in `sealing.mts`, listed in `apps/backend/src/db/sealedColumns.ts` and guarded by a database check. Validation of content happens in the clients.
2. **Nothing runs unless your own client sealed it as runnable.** No code path seals a prompt as `user` for an agent or for the server: proposals and polish are suggestions you apply in the browser. An agent cannot create a task that starts by itself: `board schedule` refuses inside a run, and the reviewer agent's allow-list excludes it. The limit of this rule: the data key sits in `~/.config/agent-board/env`, so an agent in `auto` mode that reads the file can seal anything.
3. **Clear values from the server are checked to a tight shape** before they reach argv, a path, a unit name, the shell or the agent. The task link is built by the CLI from its own `web.json`, and server error text is quoted, cut and labelled.
4. **The prompt reaches `claude` on stdin**, never as an argument.
5. **Every machine API command is atomic** under concurrent callers (several machines, workers, the browser). Claims return 409 to the losers.
6. **A resume runs only on the machine that holds the session,** and only a session that machine started for the task.
7. **Contract changes follow [Versioning](#versioning).**
8. **CLI code runs on Node and Bun.** Use `node:` APIs only, never `Bun.*`.
9. **Keep `docs/` true.** A behaviour change updates the doc that describes it. The command reference is generated, and a test checks it.

## Known limits

- Change events live in the backend process, so the server runs one replica. Postgres `LISTEN/NOTIFY` would lift that.
- Workers have no OS-level isolation.
- On macOS a run is not a cgroup: when it ends, what stayed in the agent's process group is killed, but a process that started its own session (a daemon, `setsid`) survives it, and a stop from the dispatcher's sweep has the same gap. A Mac worker runs only while its user is logged in and awake (the worker holds `caffeinate -i` during a run).
- A raised `MIN_CLIENT` is a coordinated rollout.
- Turning GitHub review requests into tasks is a script (`github-reviews`) that each machine runs on its own timer, not part of the dispatcher.
