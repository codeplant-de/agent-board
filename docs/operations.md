# Running the board server

Deployment, server configuration, and the one-off encryption cutover.

## The board server

`apps/backend`: Fastify, tRPC for the UI, Drizzle on Postgres; migrations run on start. `apps/slack`: the optional [Slack app](#the-slack-app). `apps/frontend`: React, Mantine and TanStack Query, served by Caddy, which proxies `/trpc`, `/api` and `/healthz` to the backend. The backend's answers share the app's origin, so Caddy passes on none of their headers (`header_down -*`: an allow-list of nothing, so `Clear-Site-Data`, `Set-Cookie`, `Refresh`, `Link`, `Location`, `Service-Worker-Allowed`, `Strict-Transport-Security`, `Access-Control-*`, `Content-Encoding` and any header nobody thought of are dropped, and only the status and the body get through) and writes its own (`Content-Type: application/json`, `Cache-Control: no-store`, `Content-Security-Policy: sandbox; default-src 'none'`, `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment`, `Cross-Origin-Resource-Policy: same-origin`). The app's own CSP has `worker-src 'none'`, so no service worker can be registered, and a script served from a backend path is JSON to a browser anyway: a page the backend made up under `/api` or `/trpc` is not a page to a browser and cannot run script with the app's access to the keys in IndexedDB. The app itself is served with `Cross-Origin-Opener-Policy: same-origin`. Images: `agent-board-backend`, `agent-board-web` and `agent-board-slack` on GHCR, built by `.github/workflows/ci.yml` on a push to main, only after its typecheck, lint and test job passed (a manual run builds them too), and rolled out by Flux image automation.

Environment of the backend:

| Variable           | Meaning                                                                                                                                                                                                                                                                                                                           |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`     | Postgres, as a superuser or as the schema owner with CREATEROLE. Used only at start to create the app role and run migrations, then closed.                                                                                                                                                                                       |
| `APP_DATABASE_URL` | The same database as `board_app`, the unprivileged role that serves every request (no superuser, no BYPASSRLS). It must be `board_app`; the backend creates it with this URL's password, or resets the password, on start, and refuses to start if the role is privileged.                                                        |
| `ALLOWED_GROUPS`   | Authelia groups that may use the UI, comma-separated. Default `admins`.                                                                                                                                                                                                                                                           |
| `DEV_AUTH_USER`    | Local development only: act as this user without Authelia. The backend refuses to start with it in production.                                                                                                                                                                                                                    |
| `BACKFILL_OWNER`   | Only for the first start on a database that already has tasks, from before boards were separated: the username that owns them. The migration stops with an error naming this variable when rows exist and it is unset; it is not needed on a fresh database and ignored afterwards.                                               |
| `INTAKE_TOKEN`     | Turns on the Slack intake API and is the bearer token of the [Slack app](#the-slack-app); at least 32 characters, the same value there. Unset, the API does not exist (404). `openssl rand -hex 32` makes one.                                                                                                                    |
| `BOARD_URL`        | The board's public address without a trailing slash, such as `https://board.codeplant.de`. Required with `INTAKE_TOKEN`: the links the Slack app hands out are built on it.                                                                                                                                                       |
| `CLI_VERSION`      | The newest CLI release, `x.y.z`, which the machine API advertises as `cli` in its `version` answer. The backend image sets it from `apps/cli/package.json` at build time (the `build-and-push` job passes it as a build argument). Unset or not `x.y.z` means unknown: nothing is advertised and no machine is shown as outdated. |
| `PORT`             | Default 4000.                                                                                                                                                                                                                                                                                                                     |

Boards are separated per user: every row belongs to the signed-in user (`Remote-User`, lower-cased), and requests run as the unprivileged `board_app` role with row-level security, so a query only sees its owner's rows even if it forgets a `WHERE`. A machine token belongs to the user who made it on the Settings page, and the machine API works on that user's board. Two users may use the same machine name or dedupe key.

Three ways in:

- **The UI** (`/trpc`): Traefik runs Authelia's forward-auth and strips client-sent `Remote-*` headers before it; the backend takes the user from `Remote-User` and requires one of `ALLOWED_GROUPS` in `Remote-Groups`.
- **The machine API** (`POST /api/machine/<subcommand>`): its own Traefik route skips Authelia, matched only for that path with an `Authorization: Bearer` header. The backend looks the token up by its sha256 (tokens are shown once, on the Settings page) and refuses a revoked one. A token claims tasks only under its own machine name.
- **The intake API** (`POST /api/intake/<command>`): for the Slack app only, with the shared `INTAKE_TOKEN`; see [architecture.md](architecture.md#the-slack-companion). Never add it to the proxy's login bypasses: the Slack app calls the backend directly inside the cluster.

The cluster side (namespace, Postgres, Deployments (backend, web, Slack app), IngressRoutes, Authelia rule, image policies, DNS, nightly `pg_dump` into the restic backup) is `infra/cloud-infra/add-agent-board.patch`, written against codeplant-de/cloud-infra: `git apply` it there, fill in and encrypt `cluster/apps/agent-board/env.sops.yaml` and the new `ghcr-pull` entry, and apply the DNS with tofu. The images come from `codeplant-de/agent-board` on GitHub (`ghcr.io/codeplant-de/agent-board-*`).

## The Slack app

`apps/slack` is a small container (`agent-board-slack`, built next to the backend and web images and rolled out the same way) that answers `/board` in Slack: `/board link`, `/board unlink` and `/board <text>`, which lands in the board's **From Slack** box. It has no state, listens on no port and needs no ingress: it dials out to Slack (Socket Mode) and to the backend. See [usage.md](usage.md#slack) for what users do, and [architecture.md](architecture.md#the-slack-companion) for why it is separate and what its token can do.

| Variable          | Meaning                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `SLACK_APP_TOKEN` | The app-level token (`xapp-…`, scope `connections:write`) of the Slack app. The only Slack secret; no bot token is read. |
| `BOARD_API_URL`   | The backend as the container reaches it, inside the cluster: `http://backend:4000` in the `agent-board` namespace.       |
| `INTAKE_TOKEN`    | The same value as on the backend.                                                                                        |

The backend holds no Slack token. Slack outages and backend outages do not stop the app: it retries the connection with growing delays, and a command it cannot answer gets an ephemeral "the board did not answer". Logs name the reason, never a token or what someone typed.

Setting it up:

1. In the Cosuno workspace, create an app from `infra/slack-app-manifest.yaml` (api.slack.com/apps, "Create New App", "From a manifest"). The manifest asks for the `commands` scope and Socket Mode, nothing else. A workspace admin may have to approve it.
2. Under Basic Information, "App-Level Tokens", generate a token with the scope `connections:write`. That is `SLACK_APP_TOKEN`. Install the app to the workspace.
3. Generate an `INTAKE_TOKEN` and put it in the backend's env secret together with `BOARD_URL`, and `SLACK_APP_TOKEN`, `BOARD_API_URL` and `INTAKE_TOKEN` in the Slack app's secret (`agent-board-slack-env`, see the patch). Restart the backend, then the app.
4. In Slack, send `/board link` and open the link.

Without `INTAKE_TOKEN` on the backend the board runs as before and shows no Slack settings. The compose file does not start the app; locally, run `pnpm --filter @agent-board/slack dev` with `apps/slack/.env` (see `.env.example`) against `pnpm dev:backend` with `INTAKE_TOKEN` and `BOARD_URL=http://localhost:5173` set.

## Cutover to encryption

This cutover is done: production was re-encrypted on 2026-11-14, and migration 0014 is on `main`. The steps stay here as the record of how it was done, and for restoring a dump from before it. A new board starts encrypted and needs none of this.

For the one user who owns every row from before encryption, once. The operator is that user. It takes **two releases**, in this order:

1. **The first release** has the migrations up to 0013, the browser and CLI that encrypt, and the re-encryption script. It has no constraint on the sealed columns: it starts on a database that still holds plain text, which is what lets the backend run while you set up your key in the browser (step 4), the one thing the script needs.
2. **The second release**, shipped later, adds migration 0014 and nothing else: check constraints that make the database refuse plain text in every sealed column (`apps/backend/src/db/sealedColumns.ts` lists them). The migration fails, changing nothing, while any plain text remains, so it must not roll out before step 11 of the first release is done and its result checked. See [The second release](#the-second-release).

**What "trusted at cutover" covers.** The script seals whatever plain text the owner's rows hold at the moment it commits, and picks each binding (the creator, the schedule, the task a note belongs to, the author and kind of a note) from clear columns. So the trust covers every write up to that moment: not only what the board stored before the first release, but everything written while the first release ran over the legacy rows, which have no constraint yet and which the application role can write for any owner by setting `app.owner` itself, and anything the operator changed in the database. Whoever could write then can make the script seal a prompt as the user's or as intake's, or a note as another author's. That is acceptable here only because the operator and the single legacy owner are the same person, who also watches the cutover: the dry run prints every task (id, creator, status, `created_at`) and the rows per table, to compare with the dump of step 2, so nothing that was not there before the cutover (or any change of creator) goes unnoticed. For a board of other people this script is not the way to migrate. From the commit on, a value a client did not seal for its purpose is not trusted by any client.

Every step says what to do if it fails; steps 6 to 8 either complete or change nothing.

**Needs:** `kubectl` for the `agent-board` namespace, a checkout at the first release's commit with `pnpm install`, the backend's env secret with `DATABASE_URL`, `APP_DATABASE_URL` (`board_app`) and `BACKFILL_OWNER` (your lower-case username: the migration that adds owners stops without it), and a password manager for the recovery key.

0. **Rehearse** on a restored dump. `pg_restore` the newest `agent-board.dump` into a scratch database, start `pnpm dev:backend` on it (`DATABASE_URL`, `APP_DATABASE_URL`, `BACKFILL_OWNER`, `DEV_AUTH_USER=<you>`), set up encryption in the browser, then run steps 6 to 10 against it. To rehearse the second release as well, apply its patch and run its migration (`pnpm db:migrate`) against the result. The script does about 6,000 transcript events per second: 300,000 events took 50 seconds. Drop the scratch database.
1. **Stop the timers** on every worker machine, and wait for the running tasks: `systemctl --user disable --now agent-board-dispatch.timer agent-board-intake.timer`, then `systemctl --user list-units 'agent-board-*'` shows no task. _Safe to repeat._
2. **Take a dump**, your way back: `kubectl -n agent-board exec postgres-0 -c postgres -- sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > agent-board-before.dump`. It holds plain text: step 12 deletes it.
3. **Deploy the first release** (merge to main, Flux), and tag the CLI release: `cli-v<version>` on that commit (the version in `apps/cli/package.json`), so that `board self-update` has the contract-6 binary to fetch in step 5. The migrations run on start, in one transaction. _If the backend does not start:_ read `kubectl -n agent-board logs deploy/backend`; the usual cause is a missing `BACKFILL_OWNER`; nothing was changed, fix the secret and let it restart. _Once it runs, the old image no longer fits the schema:_ the way back is restoring the dump.
4. **Set up encryption in the browser:** sign in, choose a passphrase, store the recovery key in the password manager, then copy the data key from **Settings**. _If it says encryption is already set up, a key exists: use its passphrase or recovery key._
5. **Put the data key on each machine:** update the CLI first (`board self-update` for a release binary, or `git pull`, `pnpm install` and `apps/cli/install.sh` for a checkout), narrow the tools intake may use (in `~/.config/agent-board/config.json`: `Bash(board *)` in `intake.allowedTools` to the forms in `config.example.json`, and `Bash(board internal *)` added to `intake.disallowedTools`), then run `board init`: it sees the `env` that has a token and no key and asks for the key only (paste the `AGENT_BOARD_DATA_KEY=…` line from Settings as it is; the file stays mode 600, with a backup of the old one). Leave the timers off. Check with `board doctor` (the key must match the board's) and `board tasks`: until step 8 every task reads `(cannot decrypt …)`.
6. **Stop the writers:** `kubectl -n agent-board scale deploy/backend --replicas=0` (if Flux scales it back, suspend the apps Kustomization first). The script also takes a lock and stops with a clear message when anything is writing.
7. **Dry run.** Keep the port-forward's process id, and stop it at the end by that id.

   ```
   kubectl -n agent-board port-forward svc/postgres 54332:5432 &
   export DATABASE_URL="postgresql://board:$(kubectl -n agent-board get secret agent-board-env -o jsonpath='{.data.POSTGRES_PASSWORD}' | base64 -d)@localhost:54332/board"
   pnpm --filter @agent-board/backend reencrypt --owner <you> --key-file ~/.config/agent-board/env --dry-run
   ```

   It reads the key from the file (mode 600 or 400) or from `AGENT_BOARD_DATA_KEY`, never from an argument, and never prints it. It does everything in a transaction, checks the result and rolls back. Read the table: `converted` is what it seals, `left plain on purpose` the events the server wrote itself (`Closed.`, `Moved from … to ….`; any other text, including older wordings, is sealed as the system's), and every `WARNING` line. Before this change a started proposal stayed `created by agent` with `proposed = false`, but so did a discarded proposal that was reopened (reopening cleared the flag too), so the flag alone does not say it was started. The script treats a proposal as started only with evidence: a session id, a machine that claimed it, a run timestamp, a transcript run, the status `todo` or `running` (only a start, a reply, an answer or a re-run puts a proposal there), `next` being `resume`, or a note of yours that answered it or the note `Moved from … to todo.`. With evidence it seals the prompt for the creator `user` and makes you its creator; without, it keeps the agent as creator and sets `proposed = true`, so it waits until you start it. Both the dry run and the real run print every such task (id, creator before, status, `created_at`, the outcome and the evidence): read that list, and start again any proposal you did start that was kept (a started proposal with no trace at all is one you moved back before anything ran). The dry run also prints every task of the owner (id, creator, status, `created_at`) and the rows per table, to compare with `agent-board-before.dump`. _If it stops:_ "another key" means the data key is not the one of Settings; "an envelope that does not open" names a row that holds a value of another key or damage; "being written to" means step 6 or 1 was not finished; "rows of another user still hold plain text" means the board is not a one-owner board, and the script is not for it; "values that the clients refuse" lists rows (an id or a name a client rejects) to fix in SQL first; "Intake ran after the first release was deployed" names two tasks for one pull request (a legacy one, whose plain URL would collide with the new task's hashed key, and the one intake made when it ran between the deploy and the script): delete the newer one if nothing on it is worth keeping, or clear the older one's `dedupe_key`, as the message says, and run again. Nothing was changed in any of these.

8. **Run it for real:** the same command without `--dry-run`. One transaction: _if it fails, nothing changed; fix the cause and run it again._ A second run changes nothing, so a doubt about whether it finished is answered by running it.
9. **`VACUUM FULL`** the rewritten tables, so the old plain-text row versions leave the files (an update leaves them behind until the table is rewritten): `psql "$DATABASE_URL" -c 'VACUUM FULL task, schedule, note, transcript_run, transcript_event'`. It needs free disk about the size of the biggest table and locks them, so the backend stays off. In the rehearsal `transcript_event` was 116 MB, 919 MB after the script and 438 MB after. _Safe to repeat._
10. **Check that nothing plain is left, while the writers are still off:** the same dry-run command (step 7's port-forward and `DATABASE_URL`) reports `converted` as 0 everywhere, since a second run changes nothing. The real run already checks, in its own transaction and before it commits, that no plain text remains in a sealed column, so this shows the second run is idle rather than finding anything new. It takes a lock on the board's tables for its whole pass, and stops with "being written to" when a backend, a worker or a timer is writing: that is why it comes before the next step, not after.
11. **Start again:** `kubectl -n agent-board scale deploy/backend --replicas=1`, open the board, unlock, open a task and a transcript, run `board tasks` on a machine, then `systemctl --user enable --now agent-board-dispatch.timer agent-board-intake.timer`.
12. **Prune what holds plain text:** `agent-board-before.dump`, the dumps in `/var/backups/agent-board`, and the restic snapshots made before step 8 (`restic snapshots`, then `restic forget --prune <ids>`). Do this only after step 11 works, and the second release is the better moment: until then they are your way back. Dumps and snapshots from after step 8 hold ciphertext only. `BACKFILL_OWNER` may then leave the env secret.

`VACUUM FULL` rewrites the table files but does not scrub the disk blocks it frees or the write-ahead log, so the old plain text can still sit in freed space and in replicas until they are overwritten.

### The second release

Ships after step 11 of the first, as its own change: migration 0014 (`0014_sealed_content_constraints.sql`), its snapshot and journal entry, the check constraints in `apps/backend/src/db/schema.ts` and their test. It first checks every sealed column and, when plain text remains, stops with `Plain text is still stored in sealed columns: <table.column (rows)>. Run the re-encryption script first`, changing nothing (the migrations run in one transaction); then it adds the constraints and validates them.

1. Confirm step 11 of the first release is done and the check of step 10 converted nothing.
2. Deploy the second release. _If its backend does not start_ with the message above, the board is down meanwhile (the deployment recreates): pin the previous image tag to bring it back (the migration changed nothing), run steps 6 to 10 of the first release again, and deploy the second release again.
3. Once it runs, a client that forgets to seal a field gets a 400 from the server's own check, and one that bypassed it would be refused by the database.
