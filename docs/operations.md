# Running the board server

Deployment, server configuration, and the one-off encryption cutover.

## The board server

`apps/backend`: Fastify, tRPC for the UI, Drizzle on Postgres; migrations run on start. `apps/frontend`: React, Mantine and TanStack Query, served by Caddy, which proxies `/trpc`, `/api` and `/healthz` to the backend. The backend's answers share the app's origin, so Caddy passes on none of their headers (`header_down -*`: an allow-list of nothing, so `Clear-Site-Data`, `Set-Cookie`, `Refresh`, `Link`, `Location`, `Service-Worker-Allowed`, `Strict-Transport-Security`, `Access-Control-*`, `Content-Encoding` and any header nobody thought of are dropped, and only the status and the body get through) and writes its own (`Content-Type: application/json`, `Cache-Control: no-store`, `Content-Security-Policy: sandbox; default-src 'none'`, `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment`, `Cross-Origin-Resource-Policy: same-origin`). The app's own CSP has `worker-src 'none'`, so no service worker can be registered, and a script served from a backend path is JSON to a browser anyway: a page the backend made up under `/api` or `/trpc` is not a page to a browser and cannot run script with the app's access to the keys in IndexedDB. The app itself is served with `Cross-Origin-Opener-Policy: same-origin`. An error Caddy makes itself on a backend path (a 502 when the backend is down) gets the same headers through `handle_errors`. The Caddy image is pinned by version and digest in `ARG CADDY_IMAGE` of `apps/frontend/Dockerfile`; the CI job pulls that image and `caddyfile.docker.test.ts` runs the Caddyfile in it against a hostile backend, so a Caddy upgrade is a change to that line and passes the test first. Images: `agent-board-backend` and `agent-board-web` on GHCR, built by `.github/workflows/ci.yml` on a push to main, only after its typecheck, lint and test job passed (a manual run builds them too), and rolled out by Flux image automation.

Environment of the backend:

| Variable           | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DATABASE_URL`     | Postgres, as a superuser or as the schema owner with CREATEROLE. Used only at start to create the app role and run migrations, then closed.                                                                                                                                                                                                                                                                                                                  |
| `APP_DATABASE_URL` | The same database as `board_app`, the unprivileged role that serves every request (no superuser, no BYPASSRLS). It must be `board_app`; the backend creates it with this URL's password, or resets the password, on start, and refuses to start if the role is privileged.                                                                                                                                                                                   |
| `ALLOWED_GROUPS`   | Authelia groups that may use the UI, comma-separated. Default `admins`.                                                                                                                                                                                                                                                                                                                                                                                      |
| `DEV_AUTH_USER`    | Local development only: act as this user without Authelia. The backend refuses to start with it in production.                                                                                                                                                                                                                                                                                                                                               |
| `BACKFILL_OWNER`   | Only for the first start on a database that already has tasks, from before boards were separated: the username that owns them. The migration stops with an error naming this variable when rows exist and it is unset; it is not needed on a fresh database and ignored afterwards.                                                                                                                                                                          |
| `PROXY_SECRET`     | Required in production (the backend does not start without it), at least 32 characters. The web container's Caddy sends it as `Board-Proxy-Secret` on every request it proxies to the backend, and the backend takes `Remote-User` and `Remote-Groups` only with it, so a pod that reaches port 4000 directly cannot pose as a user. The same value goes into the web container's env. `openssl rand -hex 32` makes one. Unset outside production: no check. |
| `CLI_VERSION`      | The newest CLI release, `x.y.z`, which the machine API advertises as `cli` in its `version` answer. The backend image sets it from `apps/cli/package.json` at build time (the `build-and-push` job passes it as a build argument). Unset or not `x.y.z` means unknown: nothing is advertised and no machine is shown as outdated.                                                                                                                            |
| `PORT`             | Default 4000.                                                                                                                                                                                                                                                                                                                                                                                                                                                |

Boards are separated per user: every row belongs to the signed-in user (`Remote-User`, lower-cased), and requests run as the unprivileged `board_app` role with row-level security, so a query only sees its owner's rows even if it forgets a `WHERE`. A machine token belongs to the user who made it on the Settings page, and the machine API works on that user's board. Two users may use the same machine name or dedupe key.

Two ways in:

- **The UI** (`/trpc`): Traefik runs Authelia's forward-auth and strips client-sent `Remote-*` headers before it; Caddy in the web container adds `Board-Proxy-Secret` (overwriting any value a client sent); the backend checks that secret, takes the user from `Remote-User` and requires one of `ALLOWED_GROUPS` in `Remote-Groups`. A NetworkPolicy lets only the web pod reach port 4000, and the secret keeps any other pod that gets through off `/trpc`. The session cookie covers the whole parent domain, so another subdomain can send a plain HTML form with it; a write to `/trpc` whose `Content-Type` is not `application/json` (a form cannot send that) is a 415, before tRPC reads it.
- **The machine API** (`POST /api/machine/<subcommand>`): its own Traefik route skips Authelia, matched only for that path with an `Authorization: Bearer` header. The backend looks the token up by its sha256 (tokens are shown once, on the Settings page) and refuses a revoked one. A token claims tasks only under its own machine name.

The cluster side (namespace, Postgres, Deployments (backend, web), IngressRoutes, Authelia rule, image policies, DNS, nightly `pg_dump` into the restic backup) lives in the separate, private codeplant-de/cloud-infra repository. The images come from `codeplant-de/agent-board` on GitHub (`ghcr.io/codeplant-de/agent-board-*`).

## Removing the Slack app

The Slack intake was removed. The migration `0035_drop_slack` drops the `slack_inbox`, `slack_link` and `slack_link_code` tables with their data, and the four `slack_*` functions. `INTAKE_TOKEN` and `BOARD_URL` are no longer read, so remove them from the backend's env secret. The `agent-board-slack` image is no longer built, and its Deployment and secret (`agent-board-slack-env`) go from `codeplant-de/cloud-infra`. The Slack app itself can be deleted at api.slack.com/apps.

## Cutover to encryption

Done once, on 2026-11-14: the only board from before encryption (contract 6) was re-encrypted in place, and migration 0014 then made the database refuse plain text in every sealed column (`apps/backend/src/db/sealedColumns.ts` lists them). A new board starts encrypted and needs none of this.

The re-encryption script (`pnpm --filter @agent-board/backend reencrypt`) and its runbook were removed afterwards. The last tag that ships both is `cli-v0.8.0`: see `apps/backend/src/scripts/reencrypt.ts` and this section at that tag. Migration 0014 still names the script in its error, because migrations are not edited after they ship. On a database this code has migrated that error cannot occur: 0014 only applies when no plain text is left.
