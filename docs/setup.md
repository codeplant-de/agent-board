# Setting up a machine

Installing the `board` CLI, its configuration, and upgrading.

## Install

The `board` command and the worker (`dispatch`, `intake`, `worker`) are one program. A released build is a single binary per platform (Linux x64 and arm64, macOS arm64) and needs no Node; a worker machine needs Linux with systemd, `flock`, `systemd-run`, `gh` (logged in) and `claude` (logged in). On macOS only the `board` commands run, not the worker, and `board ask`, `board add` and `board polish` are not available (they read their file through `/proc`); `board comment` takes its text as arguments or `-` for stdin.

### From a release

```
gh release download --repo codeplant-de/agent-board --pattern install.sh -O - | sh
board init
board setup --enable
board doctor
```

`install.sh` needs `gh`, logged in (the repository is private). It downloads the newest `cli-v*` release for this platform, checks it against `SHA256SUMS` and installs it as `~/.local/bin/board` (`BOARD_INSTALL_DIR` chooses another directory). Set up encryption in the browser first (see [Encryption](encryption.md#encryption)), and copy your data key from the **Settings** page. `board init` asks for the board's URL, the token (create one for this machine on the board's **Settings** page; it is not shown), the data key (not shown either) and the machine name (at a prompt paste one line: the bare value, or its own `AGENT_BOARD_TOKEN=…` or `AGENT_BOARD_DATA_KEY=…` line as the Settings page offers it; a file or a pipe given with `--token-file` or `--data-key-file` can hold both lines), and writes `~/.config/agent-board/web.json`, `env` (mode 600, token and data key; a file with any other mode is refused) and, if it is missing, `config.json` from `apps/cli/config.example.json`; edit `repos` there to this machine's checkouts. For a script: `board init --url https://board.codeplant.de --token-file <file> --data-key-file <file> --machine <name>`; a secret never goes on the command line, and a file can be `/dev/stdin` for one of them (a pipe). An `env` that has the token but no data key (a machine from before encryption) is completed without `--force`: `board init` asks for the missing value only. A file that exists is kept unless `--force`, which copies it to `<name>.bak-<timestamp>` first and keeps the secrets you do not give again. `board setup` writes the dispatch and intake services and timers and the listener service (`agent-board-listen.service`) into `~/.config/systemd/user` as copies and reloads systemd; `--enable` also enables and starts the timers and the listener, and `--print` only shows the units. The listener holds a stream to the board and runs a dispatch tick about a second after a task, an answer or a drag to Todo; the 2-minute timer stays as the fallback for what no event announces (a delayed task coming due, the stale sweep, taking back a borrowed slot, an event missed while the stream was down). A tick it starts runs under the same lock as the timer's and is stopped after 110 s, like the timer's (`timeout` from coreutils is needed). Its log is `journalctl --user -u agent-board-listen`. `board doctor` checks the whole machine: Node (checkout only), config, token, server and API range, the worker tools and the units.

The credentials file `env` holds two lines, the token and the data key: `AGENT_BOARD_TOKEN=abm_...` and `AGENT_BOARD_DATA_KEY=abk1_...`. The data key is the same on every machine and never leaves your machines and browser. The CLI refuses to start without it, with a different key than the board's, or before the board has a key; `board doctor` checks all three.

The checksum catches a broken or partial download. It is not a signature: anyone who can write releases of this repository can replace the binary and `SHA256SUMS` together, so the trust is in who has write access to the repository.

The units run the installed binary under `flock`: `<board> internal dispatch|intake`. Run `board setup` again after moving the binary. A board-only machine needs just `board init`.

### From a checkout (development)

Needs Node 24+, pnpm, and for a worker the tools above. `pnpm install` in the repo (the CLI depends on `commander` and `@clack/prompts`, and imports `@agent-board/shared` through the workspace link, so every machine needs this install, again after each pull). Then `apps/cli/install.sh`: it links `board` into `~/.local/bin` and `apps/cli/bin/.node` to a Node 24+ binary (`NODE=` chooses one; it is a real binary, not a mise shim, which does not resolve a version outside a project directory), and runs `board setup`. Continue with `board init` and `board doctor` as above, then enable the timers with `board setup --enable` (or run `apps/cli/install.sh --enable` instead of the plain `install.sh`). The units then run `<node> <checkout>/apps/cli/src/main.mts internal dispatch|intake`, with the Node that ran `board setup`; run `install.sh` or `board setup` again after moving the checkout or upgrading Node (`board doctor` flags a unit whose Node or checkout has gone).

`apps/cli/build.sh` compiles the binaries (needs Bun, pinned in `mise.toml`) into `apps/cli/dist` with a `SHA256SUMS`; `pnpm --filter @agent-board/cli test:binary` builds one for this host and runs it the way a worker machine would. A release is a tag `cli-v<version>` matching `apps/cli/package.json`; `.github/workflows/release-cli.yml` builds, tests and publishes it.

User timers and the listener only run while you are logged in. For runs after logout: `loginctl enable-linger $USER`. `board completion bash|zsh|fish` prints a shell completion script, see [Commands](cli.md).

## Upgrading

**Machine names.** A name is 1 to 64 characters of letters, digits, `.`, `-` and `_`, starting with a letter or digit (the CLI states this when it refuses a name). The 64 is what the CLIs before accepted, and the character set, which keeps a name from being a sentence, is what protects the fixed event text and the agent's log lines; a shorter cap would add nothing but break names that worked. A machine token made earlier through the Settings page could carry any name of 1 to 64 characters. Such a token keeps working for what the machine API allows, and the Settings page shows its name as `(invalid)` (never as text) and still offers **Revoke**, which sends the raw name; to use the machine again, issue it a token under a name of the shape and set `machine` to it in its config.json.

The CLI checks the server's API range once per process (see [Version handshake](machine-api.md#version-handshake)). Only a change that raises `MIN_CLIENT` makes the server refuse older CLIs, so only that change needs the server and every machine's CLI updated together; a machine left on an older CLI then fails each dispatch and intake run with a version error until it is updated. An additive change (a new endpoint, a new optional key, a new enum value) adds a [feature](machine-api.md#features) name and no number: deploy the server and release the CLI in any order, and an older CLI keeps working. A CLI that is newer than the server (a release that went out first) skips its dispatch and intake ticks quietly until the server catches up, and a command that needs a feature the server lacks refuses with that message alone. For a change that raises `MIN_CLIENT`, in this order:

**The Slack webhook is gone (no contract change).** `board notify`, `slackWebhookFile` and every message the CLI posted to Slack (a question asked, a run that failed or ended without reporting) were removed, which is CLI-only: the wire is unchanged, so the contract stays at 9 and no bump or order is needed. An existing `slackWebhookFile` is ignored; remove it from `config.json`, and revoke the old incoming webhook in Slack, because a CLI that was not updated keeps posting through it, in clear text. Slack now only takes text in, through the separate [Slack app](operations.md#the-slack-app) (`/board <text>`); there are no notifications.

**Contract 9 (Waiting) needs no cutover but the general order below.** It adds the status `waiting` and the task columns `wake_at`, `wait_check` and `woken_at` (migration 0017), the task fields `wakeAt`, `waitCheck` and `woken`, and the machine commands `wait` and `wake`: a CLI of contract 8 cannot read those fields, so server and machines update together. `board wait` and the **Waiting** column come with it.

**Contract 8 (`polish` notes) needs no cutover but the general order below.** It adds the note kind `polish` (migration 0016, which adds the enum value): a CLI of contract 7 cannot read a thread that holds one, and a server of contract 7 would store one as an unreadable comment, so the contract number moves and server and machines update together. `board polish` and the **Polish prompt** button come with it.

**Contract 6 (encryption) moves data, so it has its own sequence: follow [Cutover to encryption](operations.md#cutover-to-encryption) from its first step, in its order.** It stops the timers and takes the dump before anything is deployed, and it holds the CLI release, the keys, the re-encryption and the restart. The list below is the order for a raised `MIN_CLIENT` that needs no such cutover:

1. Stop the dispatch and intake timers and the listener on every worker machine: `systemctl --user stop agent-board-dispatch.timer agent-board-intake.timer agent-board-listen.service`.
2. Take a dump of the database, your way back if a migration has to be undone.
3. Deploy or restart the server; migrations run on start.
4. Release the CLI: once the change is on `main`, tag the commit `cli-v<version>` (the version in `apps/cli/package.json`; `cli-v0.3.0` is the contract-5 build, `0.4.0` is contract 6, `0.5.0` is contract 7, `0.6.0` is contract 8, `0.7.0` is contract 9, `0.8.0` is the first with the API range check) and push the tag. CI fails a pull request that raises `MIN_CLIENT` without a CLI version above the newest `cli-v*` tag, so the release is never forgotten. The release workflow builds and publishes the binaries, so that `board self-update` has something to fetch before any machine is switched. `board self-update --check` on a machine shows it.
5. On each machine: update the CLI: `board self-update` for a release binary (it needs `gh`; `--check` only reports), or for a checkout `git pull`, `pnpm install` and `apps/cli/install.sh`. A checkout that only pulls cannot resolve new dependencies, and then `board`, dispatch, intake and every run's hook fail. Then `board setup` once if the units were written by an older version, and `board doctor`.
6. In an existing `config.json`, narrow `Bash(board *)` in `intake.allowedTools` to the forms in `config.example.json`, and add `Bash(board internal *)` to `intake.disallowedTools`. The old `backend` key is ignored; remove it if you like.
7. Start the timers and the listener again: `systemctl --user start agent-board-dispatch.timer agent-board-intake.timer agent-board-listen.service`.

The listener checks the API range each time it connects. When the server no longer serves this CLI it logs that and exits, and systemd restarts it every 10 seconds until the CLI matches, so a machine updated late needs no hand. When the server is older than the CLI it logs that once and keeps reconnecting with its usual backoff. A running listener does not load new code by itself: it is one process that keeps the code it started with, across reconnects. `board setup` restarts it when it wrote a changed unit file (`systemctl --user try-restart`, which leaves a stopped listener alone). After a plain `git pull` or `board self-update` with an unchanged unit file, run `systemctl --user restart agent-board-listen` yourself. Stopping it waits for a dispatch tick that is running, up to systemd's stop timeout. Contract 7 was a plain bump: it added the event stream and moved no data. It is CLI version 0.5.0 (`cli-v0.5.0`); a CLI up to 0.7.0 compares `contract` exactly, which is why the server still answers `contract: 9`. CLI 0.8.0 is the first with the range check.

## Config

`~/.config/agent-board/config.json` (`AGENT_BOARD_CONFIG_DIR` changes the directory):

| Key                 | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `machine`           | This machine's name on the board. Default: the host name up to the first dot. Must match the name of its token.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `lanes`             | Lane name to `{ "skills": [...], "slots": n }`, see [Lanes](workers.md#lanes). Default: `general` with `*` and 3 slots.                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `defaultCwd`        | Where a task without a directory of its own runs. Default `~`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `pauseAfterMinutes` | A borrowed run is paused for its lane's own work only after this long. Default 5.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `inactivityMinutes` | A run with no tool call for this long is stopped. Default 15.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `maxRunHours`       | A run is stopped after this long, however busy. Default 6.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `intake`            | How intake's reviews run: `prompt` (default `/review-pr {url} --auto`), `priority` (default `normal`), the narrow `allowedTools` and `disallowedTools` they run with, `env`: variables the worker copies from the checkout's `.claude/settings.json` and `settings.local.json` into the run, and `mcpServers`: servers of the checkout's `.mcp.json` it passes with `--mcp-config` (such as `shortcut`, which then uses the login Claude Code already has for it), since intake loads only your user settings. See [What a worker may do](workers.md#what-a-worker-may-do). |
| `repos`             | `owner/name` to local checkout. Intake ignores a PR in another repo, and dispatch leaves its task to a machine that has the checkout.                                                                                                                                                                                                                                                                                                                                                                                                                                       |

`web.json` next to it holds the board's `url`; plain `http` is refused except for localhost. Every link to a task that the CLI prints is `<url>/t/<id>`, built here: the board's own answers carry no link. The token comes from `env`. The CLI reads them on its first call to the board, so a command that fails on a usage error needs neither.

Logs: `~/.local/state/agent-board/logs/<task>.log`, one per task, emptied when a worker starts. The worker's own fatal errors are appended to it. The checks of waiting tasks are in `~/.local/state/agent-board/waits/<task>.json` (see [Waiting](usage.md#waiting)).
