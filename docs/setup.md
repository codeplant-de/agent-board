# Setting up a machine

Installing the `board` CLI, its configuration, and upgrading.

## Install

The `board` command and the worker (`dispatch`, `intake`, `worker`) are one program. A released build is a single binary per platform (Linux x64 and arm64, macOS arm64) and needs no Node; a worker machine needs Linux with systemd, `flock`, `systemd-run`, `gh` (logged in) and `claude` (logged in). On macOS only the `board` commands run, not the worker, and `board ask`, `board add` and `board polish` are not available (they read their file through `/proc`); `board comment` takes its text as arguments or `-` for stdin.

### From a release

```
gh release download --repo codeplant-de/agent-board --pattern install.sh -O - | sh
board init
board setup --enable
board doctor
```

`install.sh` needs `gh`, logged in. It downloads the newest `cli-v*` release for this platform, checks it against `SHA256SUMS` and installs it as `~/.local/bin/board` (`BOARD_INSTALL_DIR` chooses another directory). Set up encryption in the browser first (see [Encryption](encryption.md#encryption)), and copy your data key from the **Settings** page. `board init` asks for the board's URL, the token (create one for this machine on the board's **Settings** page; it is not shown), the data key (not shown either) and the machine name (at a prompt paste one line: the bare value, or its own `AGENT_BOARD_TOKEN=…` or `AGENT_BOARD_DATA_KEY=…` line as the Settings page offers it; a file or a pipe given with `--token-file` or `--data-key-file` can hold both lines), and writes `~/.config/agent-board/web.json`, `env` (mode 600, token and data key; a file with any other mode is refused) and, if it is missing, `config.json` from `apps/cli/config.example.json` (one `general` lane, no `repos`, no `intake`); add `repos` there for this machine's checkouts. For a script: `board init --url https://board.codeplant.de --token-file <file> --data-key-file <file> --machine <name>`; a secret never goes on the command line, and a file can be `/dev/stdin` for one of them (a pipe). An `env` that has the token but no data key (a machine from before encryption) is completed without `--force`: `board init` asks for the missing value only. A file that exists is kept unless `--force`, which copies it to `<name>.bak-<timestamp>` first and keeps the secrets you do not give again. `board setup` writes the dispatch service and timer, the intake service and timer when `config.json` has an `intake` key (see below), and the listener service (`agent-board-listen.service`) into `~/.config/systemd/user` as copies and reloads systemd; `--enable` also enables and starts the timers and the listener, and `--print` only shows the units. Without an `intake` key, setup leaves intake units installed by an earlier version alone: it neither rewrites nor enables them, and says so. The listener holds a stream to the board and runs a dispatch tick about a second after a task, an answer or a drag to Todo; the 2-minute timer stays as the fallback for what no event announces (a delayed task coming due, the stale sweep, taking back a borrowed slot, an event missed while the stream was down). A tick it starts runs under the same lock as the timer's and is stopped after 110 s, like the timer's (`timeout` from coreutils is needed). Its log is `journalctl --user -u agent-board-listen`. `board doctor` checks the whole machine: Node (checkout only), config, token, server and API range, the worker tools and the units (the intake timer only when `config.json` has an `intake` key; an installed intake timer without the key is a warning). A key in `config.json` the CLI does not read (a typo such as `inactivityMinuts`, or one a newer version dropped) is a warning naming the nearest known key, in `board doctor` and as a `WARN config.json:` line at the start of every dispatch tick; it never stops the machine, and its setting keeps the default.

The credentials file `env` holds two lines, the token and the data key: `AGENT_BOARD_TOKEN=abm_...` and `AGENT_BOARD_DATA_KEY=abk1_...`. The data key is the same on every machine and never leaves your machines and browser. The CLI refuses to start without it, with a different key than the board's, or before the board has a key; `board doctor` checks all three.

The checksum catches a broken or partial download. It is not a signature: anyone who can write releases of this repository can replace the binary and `SHA256SUMS` together, so the trust is in who has write access to the repository.

The units run the installed binary under `flock`: `<board> internal dispatch|intake`. Intake is optional: it runs only on a machine whose `config.json` has an `intake` key (a copy of the block in `apps/cli/examples/config.reviews.json` turns on review-request intake), and `board internal intake` refuses without it. Run `board setup` again after moving the binary. A board-only machine needs just `board init`.

### From a checkout (development)

Needs Node 24+, pnpm, and for a worker the tools above. `pnpm install` in the repo (the CLI depends on `commander` and `@clack/prompts`, and imports `@agent-board/shared` through the workspace link, so every machine needs this install, again after each pull). Then `apps/cli/install.sh`: it links `board` into `~/.local/bin` and `apps/cli/bin/.node` to a Node 24+ binary (`NODE=` chooses one; it is a real binary, not a mise shim, which does not resolve a version outside a project directory), and runs `board setup`. Continue with `board init` and `board doctor` as above, then enable the timers with `board setup --enable` (or run `apps/cli/install.sh --enable` instead of the plain `install.sh`). The units then run `<node> <checkout>/apps/cli/src/main.mts internal dispatch|intake`, with the Node that ran `board setup`; run `install.sh` or `board setup` again after moving the checkout or upgrading Node (`board doctor` flags a unit whose Node or checkout has gone).

`apps/cli/build.sh` compiles the binaries (needs Bun, pinned in `mise.toml`) into `apps/cli/dist` with a `SHA256SUMS`; `pnpm --filter @agent-board/cli test:binary` builds one for this host and runs it the way a worker machine would. A release is a GitHub release `cli-v<version>` of the version in `apps/cli/package.json`; after a merge to `main` that has no release for that version, `.github/workflows/release-cli.yml` builds, tests and publishes it (see [Releasing the CLI](development.md#releasing-the-cli)).

User timers and the listener only run while you are logged in. For runs after logout: `loginctl enable-linger $USER`. `board completion bash|zsh|fish` prints a shell completion script, see [Commands](cli.md).

## Upgrading

**Tasks that run as an agent (no contract change).** A new server feature, `task.agent`: the server stores the sealed `agent` of a task and of a schedule and copies a schedule's into its occurrences (a migration adds the column `agent` to `task` and `schedule`), and the CLI and the browser send it. Nothing changes for a task without an agent: its prompt keeps the context it always had, and the server leaves the key out. The order matters, because **a CLI that does not know the field cannot run such a task, only skip it**:

1. Update the server first. A CLI refuses `--agent` against a server without `task.agent` before sending anything, and the New task form needs the new server anyway.
2. Update every machine's CLI to the release that runs tasks as an agent (`board self-update`; the listener restarts with `systemctl --user restart agent-board-listen`) **before anyone sets an agent**, and define the `agents` the tasks will name in each machine's `config.json` (see [Agents](workers.md#agents)); `board doctor` checks them.
3. Then use `--agent` or the form's Agent field.

**Intake runs as an agent (no contract change).** The built-in review intake takes its permission lists from an agent instead of its own `intake` lists. It needs the `task.agent` feature above, and an owner config moves in this order:

1. Update the server (with `task.agent`), then the CLI on every machine to the release that ships `intake.agent`, as above.
2. In `config.json`, define `agents.reviewer` from the `intake` lists: `allowedTools`, `disallowedTools`, `env` and `mcpServers` move over unchanged, and add `description` and `tools` (the tool names the lists use; `apps/cli/examples/config.reviews.json` shows the result). `board doctor` warns while the lists are still in `intake`. Defining an agent opts a machine into the reviews that name it: a machine without an `intake` block but with this agent and the checkout of a repository runs the intake tasks that name it.
3. Only on a machine whose CLI is the release from step 1 (`board doctor` no longer says `unknown key "intake.agent"`), set `"agent": "reviewer"` in `intake` and delete its `allowedTools`, `disallowedTools`, `env` and `mcpServers`. Both together is a config error. An older CLI ignores `intake.agent` with only that warning, so with the lists gone it would run intake reviews in `dontAsk` with no allow or deny list at all. `board doctor` checks that the agent exists.
4. Intake tasks made earlier have no agent: a machine with `intake.agent` runs them as that agent, so nothing needs finishing first. A machine that has not been moved keeps running intake as before.

What an older CLI does with such a task: it does not read `agent`, so it computes the context of the prompt without the name, which is not the one the prompt was sealed under (see [Encryption](encryption.md#encryption)). It cannot open the prompt, lists the task as unreadable, and its dispatcher skips it (`SKIP <id> cannot decrypt its input`) and its worker, if started on it, fails it without running claude. This holds for every CLI the server still accepts (0.7.0 and newer: contract 9, `MIN_CLIENT` 9, which already treat an unreadable prompt that way), so an older CLI can leave an agent task waiting in Todo but never run it with the user's permissions. A task that nobody can run waits in Todo.

**The `dirs` list is enforced (no contract change).** The CLI alone changes; the server and the contract stay as they are, so update machines in any order. Nothing changes on a machine until its `config.json` has a `dirs` key, and the first `board dirs add` creates it. Before that, on each machine: run `board dirs add --from-config` (it lists `defaultCwd`, the lane `cwd`s and the `repos` checkouts that exist), add the directories you schedule from, then `board doctor`, which fails for a route the list does not cover. Restart the listener afterwards (`systemctl --user restart agent-board-listen`). Existing tasks meet the list at their next start: a task in Todo, or a resume, whose directory is not listed goes to Needs me with the reason (list the directory, then **Re-run fresh** or **Send & continue**); a running task finishes; a waiting task is woken as before and then checked like any resume; an intake review needs its `repos` checkout listed. `board schedule` refuses in an unlisted directory.

**Directory lists on the board (no contract change).** A new server feature, `machine.dirs`: the server stores the sealed list each machine sends (a migration adds three columns to `machine`), and the CLI sends it. Update the server first; a CLI sends nothing to a server without the feature, and `board doctor` warns about it. Nothing changes for a machine without a `dirs` key. One with it sends its list from the next dispatch tick (restart the listener after updating the CLI) or its next `board dirs add` or `rm`. The New task form offers these directories in its Working directory field; the copy is advice and no worker reads it.

**Directory settings (no contract change).** The CLI alone changes: `board dirs set` and `unset`, and four settings in the `dirs` entries of `config.json` (see [Config](#config)). Nothing changes on a machine that does not use them. The board server needs no update and no migration: a label travels inside the sealed directory list, which only clients read, so a browser that does not know labels shows the path alone and a CLI that does not send them sends none. Update the CLI on a machine to use `set`; its next list sent to the board carries the labels, and the New task form shows them once the web app is deployed too.

**Machine names.** A name is 1 to 64 characters of letters, digits, `.`, `-` and `_`, starting with a letter or digit (the CLI states this when it refuses a name). The 64 is what the CLIs before accepted, and the character set, which keeps a name from being a sentence, is what protects the fixed event text and the agent's log lines; a shorter cap would add nothing but break names that worked. A machine token made earlier through the Settings page could carry any name of 1 to 64 characters. Such a token keeps working for what the machine API allows, and the Settings page shows its name as `(invalid)` (never as text) and still offers **Revoke**, which sends the raw name; to use the machine again, issue it a token under a name of the shape and set `machine` to it in its config.json.

The CLI checks the server's API range once per process (see [Version handshake](machine-api.md#version-handshake)). Only a change that raises `MIN_CLIENT` makes the server refuse older CLIs, so only that change needs the server and every machine's CLI updated together; a machine left on an older CLI then fails each dispatch and intake run with a version error until it is updated. An additive change (a new endpoint, a new optional key) adds a [feature](machine-api.md#features) name and no number: deploy the server and release the CLI in any order, and an older CLI keeps working. A new enum value is additive only once every machine runs CLI 0.8.0 or newer: 0.7.0 fails its intake run on the 422 for a task it cannot read and drops the stored check of a waiting task, so until then the value comes with a raised `MIN_CLIENT`. A CLI that is newer than the server (a release that went out first) skips its dispatch and intake ticks quietly until the server catches up, and a command that needs a feature the server lacks refuses with that message alone. For a change that raises `MIN_CLIENT`, in this order:

**The Slack webhook is gone (no contract change).** `board notify`, `slackWebhookFile` and every message the CLI posted to Slack (a question asked, a run that failed or ended without reporting) were removed, which is CLI-only: the wire is unchanged, so the contract stays at 9 and no bump or order is needed. An existing `slackWebhookFile` is ignored; remove it from `config.json`, and revoke the old incoming webhook in Slack, because a CLI that was not updated keeps posting through it, in clear text. Slack now only takes text in, through the separate [Slack app](operations.md#the-slack-app) (`/board <text>`); there are no notifications.

**Contract 9 (Waiting) needs no cutover but the general order below.** It adds the status `waiting` and the task columns `wake_at`, `wait_check` and `woken_at` (migration 0017), the task fields `wakeAt`, `waitCheck` and `woken`, and the machine commands `wait` and `wake`: a CLI of contract 8 cannot read those fields, so server and machines update together. `board wait` and the **Waiting** column come with it.

**Contract 8 (`polish` notes) needs no cutover but the general order below.** It adds the note kind `polish` (migration 0016, which adds the enum value): a CLI of contract 7 cannot read a thread that holds one, and a server of contract 7 would store one as an unreadable comment, so the contract number moves and server and machines update together. `board polish` and the **Polish prompt** button come with it.

**Contract 6 (encryption) moved data and had its own sequence, done once; see [Cutover to encryption](operations.md#cutover-to-encryption).** The list below is the order for a raised `MIN_CLIENT`:

1. Stop the dispatch and intake timers and the listener on every worker machine: `systemctl --user stop agent-board-dispatch.timer agent-board-intake.timer agent-board-listen.service`.
2. Take a dump of the database, your way back if a migration has to be undone.
3. Deploy or restart the server; migrations run on start.
4. The CLI is released by itself: once the change is on `main`, CI publishes `cli-v<version>` (the version in `apps/cli/package.json`) before it builds the images. (`cli-v0.3.0` is the contract-5 build, `0.4.0` is contract 6, `0.5.0` is contract 7, `0.6.0` is contract 8, `0.7.0` is contract 9, `0.8.0` is the first with the API range check.) CI fails a pull request, and a push to `main`, that raises `MIN_CLIENT` without a CLI version above the newest `cli-v*` tag, so the release is never forgotten. The binaries are published before the images, so `board self-update` has something to fetch before any machine is switched. `board self-update --check` on a machine shows it.
5. On each machine: update the CLI: `board self-update` for a release binary (it needs `gh`; `--check` only reports), or for a checkout `git pull`, `pnpm install` and `apps/cli/install.sh`. A checkout that only pulls cannot resolve new dependencies, and then `board`, dispatch, intake and every run's hook fail. Then `board setup` once if the units were written by an older version, and `board doctor`.
6. In an existing `config.json`, narrow `Bash(board *)` in `intake.allowedTools` to the forms in `apps/cli/examples/config.reviews.json`, and add `Bash(board internal *)` to `intake.disallowedTools`. The old `backend` key is ignored; remove it if you like.
7. Start the timers and the listener again: `systemctl --user start agent-board-dispatch.timer agent-board-intake.timer agent-board-listen.service`.

The listener checks the API range each time it connects. When the server no longer serves this CLI it logs that and exits, and systemd restarts it every 10 seconds until the CLI matches, so a machine updated late needs no hand. When the server is older than the CLI it logs that once and keeps reconnecting with its usual backoff. A running listener does not load new code by itself: it is one process that keeps the code it started with, across reconnects. `board setup` restarts it when it wrote a changed unit file (`systemctl --user try-restart`, which leaves a stopped listener alone), and so does `board self-update` after it replaced the binary (it prints a line saying so; a machine without `systemctl` has no listener to restart). After a plain `git pull` in a checkout, run `systemctl --user restart agent-board-listen` yourself. Stopping it waits for a dispatch tick that is running, up to systemd's stop timeout. Contract 7 was a plain bump: it added the event stream and moved no data. It is CLI version 0.5.0 (`cli-v0.5.0`); a CLI up to 0.7.0 compares `contract` exactly, which is why the server still answers `contract: 9`. CLI 0.8.0 is the first with the range check.

### Updating the CLI

The board server knows the newest CLI release (`CLI_VERSION`, see [The board server](operations.md#the-board-server)) and every CLI reports its own version, so both sides can tell when a machine is behind.

- **Settings** lists each machine's CLI as the machine last reported it: `0.7.0` (current), `0.5.0 · update available` (older than the newest release), `0.4.0 · incompatible — run board self-update` (its API break level is below the server's `minClient`: its dispatcher and intake fail until it is updated) and `version unknown` (the machine has not called since the board learned to ask, or runs a CLI from before). A checkout's `x.y.z-dev` compares as `x.y.z`. The **board page** shows a banner naming every machine that is incompatible, was seen in the last 24 hours and whose token is not revoked.
- **The hint.** When a command that reached the board learns of a newer release than the CLI you run, it prints one line on stderr after its output: `board 0.7.0 is available (this is 0.6.0); run "board self-update"` (a checkout is told to `git pull` instead; a `-dev` checkout counts as its base version). At most once per 24 hours from when it was printed (the time is kept in `update.json` of the state directory, `~/.local/state/agent-board`, and a file that cannot be read or written never fails the command), only when stderr is a terminal, never inside a board run (`AGENT_BOARD_TASK`) and never from `board internal`, which the dispatcher, listener, worker and hook run.
- **`autoUpdate`** (in `config.json`) lets the dispatcher fetch the CLI itself. When a tick fails because this CLI is too old for the board (the `cli-older` mismatch) and the mode is not `never`, it runs `board self-update` in-process, asks systemd to restart the listener without waiting (`systemctl --user --no-block try-restart agent-board-listen`), logs what happened and ends the tick with success; the next tick runs the new binary. With `always` it does the same at the start of a tick when the board advertises a newer release than the binary and no worker unit runs, and otherwise logs `UPDATE-WAIT` and goes on. Workers run as their own transient units, so restarting the listener does not stop them, and the restart is requested only after the new binary is in place, the tick then ending at once. The attempt is recorded in `update.json` (`retryAfter`) before it starts, so a tick that its time limit kills does not start the download over on every tick; each `gh` call is limited to 90 s, and download directories left behind in the temp directory are removed once they are an hour old. If the update fails (`gh` missing or not logged in, a cut-off download) the reason is logged and the dispatcher does not try again for one hour; if the advertised release is not published yet it tries again after 5 minutes. In that time a too-old dispatcher skips its ticks with one `UPDATE-SKIPPED` line each and exit code 0. A checkout never updates itself: it logs `UPDATE-NEEDED` with the `git pull` hint on each tick, and a too-old checkout's tick still fails.
- **The listener** of a machine whose CLI is too old exits on the mismatch and starts no ticks, so the update on such a machine comes from the 2-minute dispatch timer.

`web.json` next to it holds the board's `url`; plain `http` is refused except for localhost. Every link to a task that the CLI prints is `<url>/t/<id>`, built here: the board's own answers carry no link. The token comes from `env`. The CLI reads them on its first call to the board, so a command that fails on a usage error needs neither.

Logs: `~/.local/state/agent-board/logs/<task>.log`, one per task, emptied when a worker starts. The worker's own fatal errors are appended to it. The record of the Claude session the machine started for each task is `~/.local/state/agent-board/sessions/<task>`. The checks of waiting tasks are in `~/.local/state/agent-board/waits/<task>.json` (see [Waiting](usage.md#waiting)).
