# Worker machines

How a worker machine picks tasks, runs them and reports back.

## Two machines

Every worker machine runs its own timers and its own listener against the same board, under the name `machine` in its config.json (default: the host name). Every machine holds its own event stream, so a change reaches all of them at once and they race to claim; `claim-task` is atomic, so the losers move on, as they do with two timers.

- A claim is atomic on the server: of two machines claiming a task at once, one wins, and the other moves on to the next task.
- A machine skips a todo task it cannot serve, so the other one can take it: a task scheduled on the other machine (its directory is there), a resume whose session lives on the other machine, or a task that names an agent this machine does not define.
- A machine sweeps only its own running tasks: the worker unit lives where the task was claimed. When that machine is off, you can take the task back from the task page once its agent has been quiet for 20 minutes.
- A script that schedules with `board schedule --key`, such as the github-reviews script (see [Scripts](usage.md#scripts)), may run on both: the board keeps one task per key (sent as its blind index), so both make the same task once.

Tasks only move while a machine with the right setup is on.

## Lanes

A machine splits its parallel runs into lanes by skill, configured in its config.json:

```json
"lanes": {
  "reviews": { "skills": ["review-pr"], "slots": 2 },
  "general": { "skills": ["*"], "slots": 3 }
}
```

- **Own work first.** A task belongs to the lane that names the skill its prompt starts with (`/review-pr` and `/pr-review:review-pr` both count as `review-pr`), else to the lane with `*`, which also takes prompts without a skill. A lane with a free slot takes the first Todo task of its own: resumes first (answered, replied to or paused), then by priority. A skill belongs to at most one lane, and at most one lane has `*`.
- **Borrowing.** A lane with nothing of its own borrows the first task any other lane would run, so idle slots do not wait. The run is marked borrowed.
- **Taking the slot back.** When a full lane has its own work waiting and runs borrowed work that has gone on for `pauseAfterMinutes` (default 5), the dispatcher asks the newest such run to pause, one per lane at a time. Lane bias beats priority: a borrowed urgent run gives way to its lane's own low task. An urgent task only has guaranteed room in its own lane.
- **Pausing is cooperative.** The dispatcher drops a pause flag. The worker sees it on its next 15-second tick and writes a message to the agent's stdin: post a one-line status and end your turn. Nothing is refused, so the session stays clean and the agent finishes the step it is on. When the turn ends, the worker notes "Paused on <machine>: …" and puts the task back in Todo, ahead of new work, to resume in its session on the same machine. A turn that has not ended 2 minutes after the message is interrupted (see [Talking to a running agent](#talking-to-a-running-agent)) and the task is paused all the same. The resumed run is told it was paused and checks its state before it goes on.

A lane may also name a `cwd`: where its tasks run when they have no directory of their own (see [Where a task runs](#where-a-task-runs)), say `"reviews": { "skills": ["review-pr"], "slots": 2, "cwd": "~/workspace/cosuno/cosuno" }`, so `/review-pr 17766` from the New task form runs in the checkout and gets its settings. The same can be set from the directory's side: `board dirs set lane reviews ~/workspace/cosuno/cosuno` (see [Config](setup.md#config)); it wins over the lane's `cwd`, and one directory serves one lane.

Without `lanes`, a machine runs one lane, `general`, with `*` and three slots.

## Usage limits

A machine can stop starting low-priority work while its Claude subscription is nearly used up. The `usageLimits` key of its config.json (see [Config](setup.md#config)) sets thresholds on the 5-hour and the 7-day usage:

```json
"usageLimits": { "fiveHour": 80, "sevenDay": 90, "priority": "urgent" }
```

While the last known usage of a window is at or over its threshold, the dispatcher does not claim Todo tasks below `priority` (default `urgent`, so only urgent tasks still start). Without the key nothing is held, and a window without a number is not limited.

- **What is held.** Todo tasks below `priority`, including resumes (answered, replied to, paused or woken) of such tasks: they use quota too. They stay in Todo. To run one anyway, raise it to the priority.
- **What is not held.** Runs that are going go on; nothing is stopped or paused. Held tasks do not count as waiting work, so a lane does not pause a borrowed run for a task that will not start.
- **When it ends.** A reading is void once its window has reset (and one whose reset is more than 8 days off is not believed), and the dispatcher starts a tick at the earliest reset of the windows that held something (see `next` in [How it decides](#how-it-decides)).
- **Where to see it.** The dispatcher logs one `HOLD <n> task(s) below <priority>: 5-hour usage 85% (limit 80%, resets <time>)` line per tick, naming every reached window, and adds `held=<n>` to the `TICK` line. `board doctor` shows the thresholds, the last reading per window with the time it was seen, and whether work is held now. The board shows it too, as below.

- **On the board.** At the end of each tick the machine builds its usage status: its limits, the last reading per window as a whole percent, the windows over their threshold, the ids of the Todo tasks it could serve and held back, and the ids it could serve and did not hold (started, or waiting for a slot). It seals the status as `machine.usage` and sends it on every tick when the server has the feature, so the board also learns that this dispatcher is running (see `set-usage` in [machine-api.md](machine-api.md#commands)). A dry run only prints. Machines without `usageLimits` send it too: their list of open tasks is what tells the browser that a task is not really held. A held Todo card shows a `Held until <time>` badge, and a machine's row in Settings shows the readings, the limits and the hold (see [Usage limits in the board](usage.md#usage-limits)).
- **Not really held.** A task is shown as held only when a machine holds it and no other machine could still run it. If another machine lists it as open, it is just waiting for a slot there, and no badge shows.
- **Fresh machines only.** A machine's status counts for 10 minutes after the board last received it (not after the machine last connected: the listener's pings say nothing about the dispatcher), and never for a revoked one. The dispatcher ticks at least every 2 minutes, so a machine that is switched off, or whose dispatcher is refused or failing, neither holds nor opens tasks. The dispatcher logs `USAGE sent` only when the status changed or tasks are held, not on every tick. A window whose reset has passed no longer holds, as in the dispatcher.

The number comes from the `rate_limit_event` lines that `claude -p --output-format stream-json` prints in every run on this machine. The worker keeps the newest reading per window in `usage.json` of the state directory. This is not a documented interface (checked against Claude Code 2.1.326), and a line of any other shape counts as no reading. That has limits:

- Usage from outside the board (your own terminal sessions, another machine on the same account) is only seen when the next run here reports it, so the next tick may still fill every free slot past the threshold.
- A machine that runs on an API key gets no such events and is never held.
- Before the first run reports a reading there is nothing to compare, so nothing is held.

## Liveness and limits

The hook also touches a heartbeat file on every tool call. The worker checks it every 15 seconds:

- no tool call for `inactivityMinutes` (default 15): the run is interrupted as stuck and the task goes to `needs-me` with the end of the log. Claude Code caps a foreground Bash call at ten minutes, so a long command does not trip it.
- a run longer than `maxRunHours` (default 6): interrupted, however busy. A guard against an agent looping on tool calls.

The worker passes the heartbeat on to the board every 15 seconds while the agent is active, with the lane. A running card counts the seconds since ("active 12s ago", then "active 1m 5s ago"), amber after 5 quiet minutes, red after 10, and its lane with a "borrowed" badge when it runs in another lane's slot.

Every stop is an interrupt first: the worker sends `claude` an interrupt on stdin, which ends what the agent is doing at once and keeps the session resumable, then closes stdin so the process exits. Only a process that is still there 30 seconds after the interrupt is killed (SIGTERM, then SIGKILL).

The heartbeat, pause flag, lane, working directory and, for an agent's run, the agent's definition (`<task>.agents`) of a run live in `$XDG_RUNTIME_DIR/agent-board/` (`AGENT_BOARD_RUN_DIR` overrides it), private to your user; on macOS, without an `XDG_RUNTIME_DIR`, in `~/.local/state/agent-board/run` (mode 700), where the process supervisor keeps its pid files too. If the clock jumps (the machine slept), the worker moves the heartbeat up to the wake instead of counting the sleep as time without a tool call, and the dispatcher's sweep does not count quiet time on a tick that follows a gap of more than 10 minutes.

## Talking to a running agent

The worker starts `claude -p` with `--input-format stream-json` and keeps its stdin open for the whole run. The prompt is the first user message, written as a JSON line. Three things follow it on stdin, all written by the worker:

- **A pause message**, when the dispatcher wants the slot back (see [Lanes](#lanes)).
- **Your messages.** **Send** on a running task (see [Ask and resume](usage.md#ask-and-resume)) stores a pending note on the board. The worker reads the task's run inbox on every 15-second tick and whenever the board's event stream says tasks changed (so a message usually arrives within seconds), writes the notes to stdin as user messages and acknowledges them. Claude Code takes a user message up at its next tool boundary, so the agent is not interrupted; the note shows **Delivered** in the thread.
- **An interrupt**, for **Stop**, **Stop & send** and the limits above. Plain Stop ends the run: the worker reports it stopped and the task goes to Needs me with "Stopped by you.". With Stop & send the worker interrupts, writes your message after it and the run carries on in the same session. The stop request is cleared once the worker has acted on it.

A message that has not been handed over when the run ends (the agent had finished or the worker had closed stdin) is not lost: the task goes to the top of Todo to resume in its session with the message, and a note in the thread says so. If you stop the run or take the task back instead, the message becomes an ordinary reply that the next Send & continue carries. A worker whose server does not offer the run inbox runs as before and never reads it; a CLI too old to know the inbox ignores stop requests, and the task page says so after a minute (Take back still works).

## Watches

A watch (`board watch`, see [Waiting](usage.md#waiting)) is kept in `<state dir>/watches/<task>/watch-<name>.json` on the task's machine. The **watch unit**, `agent-board-watch.service` (a launchd agent on macOS), written by `board setup` and started by `board setup --enable`, polls them:

- It rescans the directory every 2 seconds, so `board watch` only writes a file, and attempts each watch on its own timer (`--every`, 30 seconds for `--ci`). An attempt may take 2 minutes. It touches `<state dir>/watches/.heartbeat` on every scan.
- An event is written to `<state dir>/watches/<task>/event-<time>-<name>.json` and posted to the thread as an agent comment. Then the unit's one rule: an event not handed over and no live run for the task means `wake`. A worker marks its task as live with `<task>/live` (its pid) while it runs. When `wake` answers `applied: false` (the task is in Needs me, paused in Todo, or still running), the event stays for the next resume. If the worker's run goes away while an event waits, the unit tries the wake once more: that covers an event that fires between the worker's decision to park and its exit.
- It keeps nothing in memory that is not on disk, so `board self-update` restarts it as it restarts the listener, and a reboot loses nothing.
- Finishing a watch is a rename of its file: whichever process (the unit, the dispatch tick, `board unwatch`) renames it first writes the event, so no event is written twice.

On the worker's side:

- Every 2 seconds the worker looks for events of its task and hands them to the agent on stdin as one user message, deleting the files it handed over.
- At the end of a turn (a `result` line) it looks again. A pending event is sent as the next message and the run goes on, as long as the task still runs. Once the task has left Running (the agent asked with `board ask` or parked with `board wait`) or a pause was requested, the worker hands nothing more over, during the turn or at its end: the events wait for the next resume. Without one, the worker closes stdin as before.
- A run that ends with watches open and the task still running is parked: the worker calls `wait` itself, with `wakeAt` the earliest timeout and `waitCheck` set when a watch is not a timer, and the thread gets "Waiting for watches: …".
- A resume builds its prompt from the event files, which are deleted at the agent's first output. The worker logs the oldest event's time, the wake and its own start, and at the first output how long it took from each, so the cost of `claude --resume` can be read from the task log.
- A fresh run (Re-run fresh) drops the task's watches first.

**Fallback.** On a machine where the unit does not run (`board setup` was not rerun after the update), the dispatch tick polls the watches that are due, with 45 seconds per attempt, and logs `WARN watches on this machine are polled by the dispatch tick: the watch unit is not running; run "board setup --enable"`. The tick polls only when the unit's heartbeat is older than 30 seconds, so the two never run the same attempt. Whatever the heartbeat says, the tick also finishes the timeouts of a task whose `wakeAt` has passed before it wakes it, wakes a waiting task that has an event and no live run, and drops the watches of a task that is Done, closed, in Backlog or gone.

## Transcripts

Every run records what it did. The worker starts `claude -p` with `--output-format stream-json --verbose`, condenses each event (the agent's text, each tool call with its input, each tool result, subagent calls tagged with their Agent call, notes such as the model and directory, and the result with turns, time, cost and refused tool calls), writes a readable line per event to the local log, and sends the events to the board with every 15-second check and once more when the run ends. A batch the board refuses is sent again with the next. What waits for a board that is down is bounded by count (20,000 events) and by size (32 MB of JSON): past either, the oldest tool outputs are emptied first, then the oldest events dropped, and a note in the transcript says how many. The end of the run makes two bounded passes.

On the board, **Transcript** on a task page (or the terminal icon on a card) opens the runs, newest first, live while one runs. Tool calls are one line each; a click shows the input and loads the output. A tool result over 256 KB is cut with a note; the full one stays in the session file on the machine. Claude Code passes thinking on without its text, so a thinking block shows as a marker with its token estimate.

Transcripts can hold whatever the agent saw: file contents, `gh` output, now and then an environment value. The worker seals each event (and each tool output apart) before it sends it, so the server stores only ciphertext. They go 14 days after a task is closed, and 28 days after the last change of an open task in Done, which covers tasks with a key (a script's reviews) and those of the removed intake (the server checks hourly). A task of yours untouched in Done is closed after 7 days.

The board loads a run's events in pages of 2000 and afterwards only those after the last one it has, so long runs show in full and a live run costs one small request per poll.

## Where a task runs

A task is bound to a directory on the machine that ran it:

- A fresh run starts in the task's own directory: where it was scheduled from with `board schedule`, or where the proposing agent worked. A task without a directory of its own (a task from the New task form with an empty Working directory) starts in the checkout of the PR its prompt names (`repos`), else in its lane's `cwd`, else in `defaultCwd`. Each of the three can also come from the `dirs` list: a directory with `repo` is that repository's checkout, one with `lane` is that lane's `cwd`, and the one with `default` is `defaultCwd`. A setting there wins over the old key, which keeps working. This matters beyond the files: Claude Code loads the checkout's `.claude/settings*.json` only when it starts there, and that is where tokens and endpoints such as `CIRCLECI_TOKEN` or the replica endpoints usually live. The task's `workdir` is set to it.
- The hook records the agent's working directory on every tool call. When a run ends somewhere else, typically in a worktree the agent entered with `/worktree` (`EnterWorktree`), the worker stores that as the task's `workdir`.
- A resume (after an answer, a reply or a pause) starts `claude --resume` in the `workdir`, so the session continues in exactly the worktree it left. The resume is pinned to the same machine, where that directory exists.
- **The task locks its worktree.** When the task's directory is a linked git worktree, the worker runs `git worktree lock --reason "agent-board task <id>"` on it as the run starts and again for the worktree the session ended in; the hook does the same as soon as the agent enters a worktree during the run. A cleanup of merged branches with `git worktree remove` then refuses with that reason (it takes `-f -f` or `git worktree unlock`), and `git worktree prune` leaves it be. The lock stays while the task is open, in any column, so a reply days later still finds its worktree. At the end of each run the worker unlocks the worktrees the task held that are no longer its `workdir` (one the agent only passed through, or the old one after Re-run fresh). The dispatcher unlocks the rest once the task is done, closed or deleted; moving a task back out of Done locks its worktree again at its next run. A worktree someone else locked is left as it is. Which worktrees a task locked is kept on the machine in `<state dir>/worktree-locks/<task>.json`; a lock left over, for example after that file was deleted, comes off with `git worktree unlock <path>`.
- **A resume whose directory is gone** continues the same session in the git checkout that held it. The usual cause is a worktree removed while its task was still open, say by a cleanup of merged branches with `git worktree remove`. Claude Code resumes a session by id from any directory, so nothing is recreated at the old path. The worker takes the nearest parent directory with a `.git` (the `/repo` of `/repo/.claude/worktrees/feat-x`), which has to be listed when there is a `dirs` list, and runs there; the task's `workdir` becomes that checkout. The agent's prompt starts with a notice: the old directory is gone, whatever was not committed and pushed in it is lost, and before changing files it should recreate its worktree on its branch the way the repository does (its CLAUDE.md), check that the branch still has its last commits, and say in its next comment which commit it continues from, or, when the branch is gone as well, ask you how to go on. A system note on the task records the move. The task goes to `needs-me` with the reason instead when no git checkout exists above the directory, or when that checkout is not a listed directory (`board dirs add` in it allows it). A fresh run in a gone directory still fails with the path: only a resume has a session worth keeping.
- **Re-run fresh** forgets the session and sets the `workdir` back to the directory the task was created with (the server keeps that envelope as `home_workdir`, written once at creation and never updated, so a worker's rewrite cannot lose it), which keeps the task pinned to its machine. A task created without a directory (a form task with an empty Working directory) and a task from before this was kept start where a task without a directory starts, as before. With a `dirs` list, the directory has to be listed, the original one included.

**The list of directories.** `board dirs` keeps a per-machine list of the directories workers may run in: the `dirs` key of this machine's `config.json` (see [Config](setup.md#config)). Without the key nothing is limited. Once the key exists, even as `{}`, a run starts only in a listed directory, and an empty list allows nothing. An entry's settings (`repo`, `default`, `lane`) only say where tasks run; they change nothing about what is allowed, and the directory they name is listed by construction.

- A directory is allowed when it is a listed one or below one, matched by path segment (`/work/app` allows `/work/app/sub`, not `/work/app2`). A worktree inside a listed checkout (`.claude/worktrees/...`) counts; a worktree folder outside it needs its own entry.
- The real path decides, so a symlink inside a listed directory that points elsewhere does not pass, and a listed symlink counts through its target.
- The check runs in the worker for every start, after the check that the directory exists: a task with its own directory, a form task in `defaultCwd` or its lane's `cwd`, and a resume in the stored `workdir`. A directory outside the list ends the task in `needs-me` with the path and the way out: `board dirs add` in it on that machine, then **Re-run fresh** or **Send & continue**. A running task is not stopped when the list changes.
- When a run ends in a directory outside the list (the agent entered a worktree elsewhere, or went to `/tmp`), the worker does not store it as the `workdir`. The task keeps the directory it started in, and a system note on the task says where the agent ended and that the next resume starts in the start directory. Storing it would make the next resume refuse its own directory.
- `board schedule` and `board add` take the working directory as the task's directory, so they refuse outside the list: `board schedule` with a usage error, and `board add` first tries `AGENT_BOARD_START_DIR` (the directory the run started in) and refuses only when that is not allowed either.
- The dispatcher does not look at the list. It claims a task whose directory is not listed and the worker fails it, so the task shows in Needs me instead of sitting in Todo. `board attach` and command watches are not limited either: they stay on the machine.
- `board doctor` fails for a `defaultCwd`, lane `cwd` or `repos` checkout that no entry covers, since tasks routed there stop. `board dirs add --from-config` lists them.
- **The board gets a copy, as advice.** A machine with a `dirs` key sends its list to the board, sealed, for the New task form's Working directory field to offer: the listed directories that exist, as written, each with its `label` when it has one (`repo`, `default` and `lane` stay on the machine), from every dispatch tick when the list changed and from `board dirs add`, `rm`, `set` and `unset`. The dispatcher compares a blind index with the one the board holds, so an unchanged list sends nothing, and a failed or unsupported send costs the tick one log line at most. If the board cannot be reached, `add` and `rm` still succeed and warn, and the next tick sends the list. The copy never reaches a path, argument or decision on any machine: the worker reads only its own `config.json`. A server without the `machine.dirs` feature is skipped, and `board doctor` says whether the board has the current list.

Claude Code itself (2.1.323) also restores a session's worktree when it is resumed from the original directory; the `workdir` makes the board independent of that and shows it on the task page. Once the worktree is deleted that restore is no use, which is what the recovery above is for.

**Skills and models on the board.** Each machine tells the board which skills (slash commands) and which Claude models it has, sealed, so the browser can complete `/skill` in a prompt or a reply and offer the machine's models. The catalogue is advice: no CLI reads it back, no worker relies on it, and a machine without it works as before.

- **How it asks.** The dispatcher starts `claude -p --input-format stream-json --output-format stream-json --verbose --strict-mcp-config` in a directory, writes one `initialize` control request to its stdin and no prompt, reads the answer and ends the process (30 seconds at most, then it is killed with its process group; the group gets a SIGKILL once more when `claude` has gone, for a process that ignored the SIGTERM). With `--strict-mcp-config` and no `--mcp-config` no MCP server is started, which the probe has no use for since it drops MCP prompts; checked against Claude Code 2.1.326, the answer then lists the same skills. No model is called, so it costs no tokens, and no session is written. It does run the `SessionStart` hooks of the user's and the directory's settings, as any start of `claude` does. It is the request the Agent SDK uses to start a session, and it is not a documented CLI interface: it was checked against Claude Code 2.1.326, and an answer of any other shape counts as no answer. A probe that fails (or times out) is logged as a `WARN` line and leaves the old catalogue in place, and that directory is not tried again for an hour unless its fingerprint changed.
- **Which directories.** The listed directories that exist (the `dirs` key); for a machine without one, the directories the config routes work to (`defaultCwd`, lane `cwd`s, `repos` checkouts). Each once, at most 20.
- **When.** A tick asks in at most one directory, and only after it has started its tasks and run its checks, so a probe never holds a start back; a tick with less time left than a probe can take (its timeout and the kill grace) sends what is cached without asking. A machine with several directories is complete after as many ticks. A directory is asked again when it was never asked, when its fingerprint changed (the `mtime` of the `claude` program, of `~/.claude/plugins/installed_plugins.json`, `~/.claude/settings.json` and `~/.claude/skills`, and of the directory's `.claude/skills` and `.claude/settings.json`; a missing one counts as one value, and nothing is started to compute it), or when a run reported other skills than the last probe saw. The last works through the `system/init` event every run starts with: the worker hashes its `skills` (a run restricted to an agent reports none: its `--setting-sources user` leaves out the directory's own skills) and remembers them for the probed directory that covers the run's directory (a worktree below it included; a run outside every probed directory records nothing). If the hash differs from the one at the directory's last probe, the next tick asks again, once. Recording is best effort: a failure is a line in the run's log and never touches the run. The results are files under `<state dir>/catalog/`, one per directory, written whole.
- **What goes in.** The commands `claude` lists that have a safe skill name. Of those, the ones `claude` marks as its own (`/compact`, `/clear`) are left out unless a run on this machine reported them as skills (that is what the `skills` of the start event are); MCP prompts and anything else with a space in its name are never in. A skill keeps its name, a description of at most 200 characters and an argument hint of at most 100, each on one line; its aliases and agents are not sent. The models are those `claude` offers except `default`, with their display name and description. `skills` are the skills every probed directory has; each directory lists those only it has, so a project's own skills show only for it.
- **Sending.** After the probe, the dispatcher composes one document from every directory asked so far and sends it when its blind index differs from the one the board holds, so an unchanged catalogue sends nothing. Until one directory has an answer nothing is sent. A document over the 256 KiB the board takes for a sealed catalogue is cut before it is sent: first the descriptions and hints of the skills of single directories, then those of the common skills, then the lists to half as many skills each time, and the send is logged once with what was left out; `board doctor` counts what is sent and says when it was cut. A failed or unsupported send costs the tick one log line at most, and a server without the `machine.catalog` feature is skipped. `--dry-run` starts no probe and prints `DRY probe claude in <dir>` and `DRY set-catalog`. `board doctor` says how many skills and models were sent and whether the board's copy is current.

## What a worker may do

There is no sandbox. A worker runs `claude` as you, with your home directory, your SSH agent and your `gh` login. The [list of directories](#where-a-task-runs) is not one either: it decides where a run may start, and so whose `.claude/settings*.json` it loads (a repository you did not list does not get to hand a run its allow rules, tokens or hooks). The agent can still `cd` anywhere, and an agent in `auto` mode can edit `config.json`, the list included. How much it may do depends on who made the task:

- **Tasks you made** (`board schedule`, the New task form, and agent proposals once you start them) run as if you ran the prompt in your terminal: all your settings (user, project, local) and `--permission-mode auto`, Claude Code's classifier mode that lets safe actions through and refuses risky ones. Headless, a refusal cannot become a prompt; it shows in the log and usually in the agent's report.
- **Tasks that name an agent** (`board schedule --agent`, the **Agent** field of the New task form, the github-reviews script) run as that agent (see [Agents](#agents)), unattended. That fits PR text nobody chose to read, so they get less: `--permission-mode dontAsk` with only the agent's `allowedTools` allowed and its `disallowedTools` denied on top, and `--setting-sources user`, which keeps a checkout's own `.claude/settings*.json` (its allow rules and tokens) out of the run. The shipped `agents.reviewer` in `apps/cli/examples/config.reviews.json` allows reading, `gh` reads, the pr-review scripts, `board comment`, `ask`, `add`, `show` and `move <task> needs-me` (it cannot `board schedule` or start work), CircleCI through the engineering plugin's `cci.sh`, a few Shortcut reads and `bin/replica-psql` (the production and staging read replicas); it cannot push, merge or approve. Its `env` hands it `CIRCLECI_TOKEN`, `SHORTCUT_API_TOKEN` and the replica endpoints from the checkout's settings, and nothing else from there. A review that a PR's text turns against you can read production data through the replica, and could put it into the pending draft (which you see before submitting) or onto the board.
- **Tasks of the removed built-in intake** (their `createdBy` is `intake`) run as their agent like any other task when they have one. One that names no agent ran under intake's own lists, which no longer exist, so it never runs, in `auto` or otherwise: a worker that claims it fails it with a note telling you to close it or create it again with `board schedule --agent <name>`.

## Agents

An agent is a named set of tools and rules on the machine: an entry under `agents` in its `config.json`, or a file `<name>.yaml` in the `agents` directory beside it (see [Sharing and importing agents](#sharing-and-importing-agents)). A task that names one runs as that agent, with only what the agent allows, whoever made the task. The task names it as a sealed `agent` field, which the board server stores and returns but cannot read, change or drop without making the task unreadable (see [Encryption](encryption.md#encryption)); you choose it with `board schedule --agent <name>` or the **Agent** field of the New task form (see [Choosing an agent](usage.md#choosing-an-agent)). The definition of the agent never leaves the machine: the board holds only its name. A repeating schedule hands its agent to every occurrence. The limits of the field are in [Encryption](encryption.md#encryption): a proposal made from an agent's run carries no agent and runs in `auto` once you start it, `board attach` resumes an agent's task with your own settings, the commands that are refused inside a run rely on `AGENT_BOARD_TASK`, so it is the agent's lists that stop a command from unsetting it, and the name is the only link to the definition, so machines must define same-named agents the same way.

```json
"agents": {
  "reviewer": {
    "description": "Reviews a PR and stages the findings.",
    "prompt": "You review pull requests.",
    "tools": ["Read", "Grep", "Bash"],
    "allowedTools": ["Bash(gh pr view *)", "Bash(board comment *)"],
    "disallowedTools": ["Bash(git push *)"],
    "mcpServers": ["shortcut"],
    "env": ["SHORTCUT_API_TOKEN"],
    "model": "opus"
  }
}
```

The name is lowercase letters, digits and dashes, at most 32 characters. `description` and `tools` are required; `prompt`, `allowedTools`, `disallowedTools`, `mcpServers`, `env` and `model` are optional, and so are `version` and `source`, which only describe the definition (where `board agents add` got it) and change nothing about a run. Unlike the rest of `config.json`, an unknown key or a wrong type inside an agent makes that agent unusable instead of being ignored: a misspelt `disallowedTool` must not leave the agent without a deny list. Only that agent is lost: the machine's other work goes on, a task that names it fails closed, the dispatcher logs a warning on every tick and `board doctor` fails. `tools` lists tool names only (`Read`, `Bash`, `mcp__shortcut__get_story`); a pattern such as `Bash(git status)` belongs in `allowedTools`. `env` and `mcpServers`: the worker copies the named variables from the working directory's `.claude/settings*.json` and the named servers from its `.mcp.json`, after the directory has passed the [list of directories](#where-a-task-runs).

### Sharing and importing agents

An agent can also live in a file of its own: `~/.config/agent-board/agents/<name>.yaml` (or `.yml` or `.json`; the directory is beside `config.json`, so `AGENT_BOARD_CONFIG_DIR` moves it too). The file holds the same keys as a `config.json` entry, plus an optional `name`, which must match the file name. Everything that reads the config reads the directory as well, with the same strictness: a file with an unknown key, a `name` that is not its file's, two files for one name, or a file others may write to (group or world writable) makes that agent unusable, and so does a name that both `config.json` and a file define, so which definition a task gets never depends on load order. Other files (a README, a hidden temp file) are ignored. YAML is read as YAML 1.2 with aliases and duplicate keys refused.

`board agents` manages both places (see [the CLI reference](cli.md)):

```
board agents                                   # each agent: tools, allow and deny counts, where it is defined, source, usable here or why not
board agents show reviewer                     # one agent as YAML (--json for JSON)
board agents export reviewer > reviewer.yaml   # the same without this machine's source, to share
board agents add example:reviewer              # the reviewer that ships with the CLI
board agents add ./reviewer.yaml --name strict # a file; - reads stdin
board agents add https://example.com/reviewer.yaml#sha256=<hex>
board agents rm reviewer                       # the file, or the config.json entry
```

An agent definition is a permission grant: it decides what a run may do on this machine, whoever made the task. So `add` prints the whole definition as it will be written and then what it grants: every tool, allow rule and deny rule, the `env` names it copies and the MCP servers. It flags broad allow rules (a bare `Bash`, `Edit`, `Write`, `Read` or `WebFetch`, `Bash(*)`, a `Bash` rule that starts with `*`, one that runs a shell, an interpreter, `curl`, `ssh` or `sudo`, `Bash(board *)`, a rule for a whole tree such as `Read(~/**)`, every tool of an MCP server), `env` names that look like secrets (`TOKEN`, `SECRET`, `PASSWORD`, `KEY` and the like), an empty deny list, allow rules for tools that `tools` leaves out, and plugin placeholders such as `{pr-review}` that do not resolve here (a run as the agent fails until they do). It writes `agents/<name>.yaml` (mode 600, the directory mode 700, through a temp file and a rename) only after you confirm at a terminal, or with `--yes`; a definition read from stdin needs `--yes`, since there is no terminal left to ask on. `--dry-run` prints all of it and writes nothing.

- The name is `--name`, else the document's `name`, else the file name. An agent that exists needs `--replace`; one defined in `config.json` is never replaced by a file (remove it with `board agents rm` first, or add the file under another name).
- The `source` written into the file is where `add` read it: the path, the URL, `example:<name>` or `stdin`. A `source` in the document itself is ignored.
- A URL must be `https://`, without a user name or password. The fetch gives up after 15 seconds and at 256 KB, and follows at most 3 redirects, each only to https on the same host. A `#sha256=<hex>` fragment pins the file's SHA-256, and `add` refuses a file whose hash differs. Nothing fetches the URL again: run `add --replace` with it to take a newer version.
- `example:<name>` reads `apps/cli/examples/agents/<name>.yaml`, built into the CLI (`board example agents/reviewer.yaml` prints it). The shipped `reviewer` is the same agent as `agents.reviewer` in `config.reviews.json`.
- `rm` removes the file, or the entry from `config.json`, which it rewrites like `board dirs` does (every other key kept, the file's mode kept). A task that names the agent then no longer runs on this machine.
- `add` and `rm` are refused inside a board run (`AGENT_BOARD_TASK` or `AGENT_BOARD_RESTRICTED` set). The shipped reviewer also denies `Bash(board agents *)`.

The definitions stay on each machine; nothing sends them to the board. Machines that should run the same agent each `add` the same file.

The run is `claude -p --tools=<tools> --agents=<file> --agent=<name> --permission-mode dontAsk --setting-sources user --allowedTools … --disallowedTools …`, in the working directory the task would run in anyway. `<file>` is a private copy (mode 0600) of the agent's `description`, `prompt`, `tools` and `model`, written to `$XDG_RUNTIME_DIR/agent-board/<task>.agents` and removed when the run ends; Claude Code runs the main thread as that agent. `--tools` holds the agent's `tools` without MCP ones, so the built-in tools are withheld even if Claude Code fails to load the agent. `tools` limits the tool names only: with `Bash` in `tools` but no `dontAsk`, the agent could run any command. The command-level rules take effect because of `--permission-mode dontAsk`, which refuses whatever `allowedTools` does not allow; `--setting-sources user` keeps a checkout's own settings out. The lists expand `~/` and plugin placeholders as [described below](#how-a-task-runs).

An agent with `Agent` in its `tools` can start subagents, and they stay inside the run's limits. Claude Code 2.1.325 was checked with a probe agent (`tools` `Read`, `Bash`, `Agent`; `Bash(touch *)` denied; `Bash(echo *)` allowed). The subagents it started (`general-purpose`, a plugin agent and an agent defined with `tools` `Bash`, `Write`, `WebFetch` and `permissionMode: bypassPermissions`) got only the tools in `--tools`, inherited dontAsk mode and both lists, and could not escape any of them. The agent's own `bypassPermissions` setting did not take effect. `touch` was refused, `mkdir` and a redirect were refused because no rule allowed them, `echo` ran, and MCP tools outside `allowedTools` were refused. The Agent tool's list of subagent types still shows each type's own tools (`pr-reviewer` with `WebFetch`, for example), so an agent may say it can reach tools it cannot. Those tools are not given to the subagent. A subagent or skill that runs a shell command on load (a `` !`…` `` line) needs that command in `allowedTools` as well, or it fails to start.

An agent's run gets reduced board rules (watches only with `--ci` and timers, no opening PRs) and `AGENT_BOARD_RESTRICTED=1` in its environment, which the agent's `env` cannot override. A command watch (`board watch -- '<command>'`, `board wait --check`) refuses while it is set: it would run any command outside the agent's list. `--ci`, `--in` and `--at` still work. Inside any run, `board watch`, `board watches` and `board unwatch` act only on the run's own task.

It fails closed. A task whose `agent` cannot be opened (a name the server dropped or replaced, or one sealed for another task) is skipped by the dispatcher and refused by the worker like any task with an unreadable prompt; it never runs unrestricted. A machine that does not define the agent leaves a task that names it in Todo for another machine (the dispatcher logs `SKIP <id> no agent <name> defined here`), unless the task is pinned here (a resume, or its own directory): then the machine claims it. A worker that gets such a task, a resume included, fails it with a system note and starts nothing. A plugin placeholder that does not resolve fails the run the same way. `board doctor` checks each agent: that its plugins resolve, and that no allow rule is for a tool its `tools` leave out.

## How it decides

Dispatcher, per tick:

1. For each task in `running` claimed by this machine, ask whether its worker is running: `systemctl --user is-active agent-board-<task>` on Linux; on macOS whether the pid in the run directory's `<task>.pid` is alive and its command line ends in `internal worker <task>`. A task whose unit is gone moves to `needs-me` with the log tail, timed from the unit's own start (else the task's `runStartedAt`). So does one whose worker failed to enforce the [limits](#liveness-and-limits) for five minutes past them; its unit is stopped. If `systemctl` gives no known state, or the backend fails, the tick stops before starting anything and exits non-zero.
2. For each task in `waiting` that this machine ran: a wait whose `wakeAt` has passed (a timer, or a check past its timeout) or whose check is not stored here is woken with the reason (`wake`), so it can start in this tick. A check whose task is neither waiting nor running here any more is deleted.
3. A task this machine cannot serve is skipped (see [Two machines](#two-machines)). The rest are planned into [lanes](#lanes): own work first, then borrowing. Each start is claimed, its lane written to the run directory, then the worker starts (`systemd-run --user --collect --unit agent-board-<task>` on Linux, a detached `board internal worker <task>` process with its output in the task log on macOS) and a start note names the machine, lane and PID. A lost claim hands its slot to the next task; the first failed start ends the tick's starting. While a [usage limit](#usage-limits) is reached, tasks below its priority are left out of this plan.
4. Lanes whose own work still waits ask one borrowed run each to pause.
5. The checks that are due run side by side (45 s each at most). One that exits 0 wakes its task with the end of its output; for any other the result is kept with the check for the timeout message.
6. The tick writes when this machine next has something to do that no event announces to `dispatch.next` in the run directory, next to `dispatch.tick`, and logs it as `next=<time>` on its `TICK` line: the earliest of the `notBefore` of a delayed Todo task this machine could serve, the `wakeAt` of a wait here, the next attempt of each check here (its last attempt plus `--every`; one that never ran or was put off is due at once), the moment a borrowed run reaches `pauseAfterMinutes` in a full lane whose own work waits, and the earliest reset of the windows that held a task back for [usage](#usage-limits). Nothing due removes the file, and so does the start of every tick, so a tick that stops early leaves no stale time behind.
7. Last, at most every 10 minutes and only where `gh` is installed, the [PR state](#pr-state) of the open tasks is refreshed. It never fails the tick: a problem is one `WARN PR states not refreshed` line.

The listener reads `dispatch.next` after each of its ticks and arms a one-shot timer for it, so a delayed task, the end of a wait, a check or a take-back starts its tick on time instead of up to 2 minutes late. Each tick cancels the timer and arms it again. When it fires it reads the file again, because a tick the timer unit started rewrites it too: a later time arms the timer again, anything else starts a tick. The timer waits at least 5 seconds, so a time that stays in the past (a check put off, say) cannot start tick after tick, and at most an hour, after which it reads the file again. The 2-minute timer unit stays as the fallback for a listener that is down. A change on the board that moves one of these times (a new or delayed task, a wait, a wake, a schedule) sends the `tasks` event, and the tick that follows arms the timer again.

Worker, per task: before anything starts, a directory that does not exist, or that a `dirs` list does not allow, ends the task in `needs-me` with the reason (see [Where a task runs](#where-a-task-runs)). A task with `next: resume`, a session, and a user reply, a pause or a wake since the agent last spoke resumes that session with the reply (and "you were paused", or "your wait is over: <why>") as the prompt, but only a session this machine started for the task; for any other the run is refused with the reason. Anything else starts a new session, whose id is recorded on this machine and stored on the task once the run is about to start (and cleared again if the process cannot be spawned). A run is also refused when it would hand the agent a note of yours that cannot be decrypted. A fresh run's prompt is the task's prompt; when the thread already holds notes by you or the agent, it is followed by what you wrote since the previous run started and a line telling the agent to read the thread with `board show <task>`. Either way `next` goes back to `fresh`.

The dispatcher makes no tasks from GitHub: the github-reviews script does (see [Scripts](usage.md#scripts)).

### PR state

The PR state shown on the board is refreshed by the dispatcher. For every task that is not closed or done and has PRs (the one its prompt names and every one its agent reported), it asks GitHub for the state of each: one `gh api graphql` query for up to 50 PRs, an alias per PR, owner, repository and number passed as variables. A task is written once, with `set-pr-states`, holding only the PRs whose state differs from the stored one (log: `PRSTATE <task> <state> …`, the new states in order, then `PRSTATES changed=<n>` for the tasks written), so the board can show a merged or closed PR on the card and offer **Move merged to Done**. A PR GitHub gives no answer for (deleted, no access) is logged as `WARN no state for <url>` and that PR keeps its state. A failed query, or one that takes longer than 30 seconds, is logged as `WARN PR states not refreshed` and does not fail the tick. Against a board server without the `task.prs` feature the write goes to `set-pr-state`, which that server applies to one PR per task (the newest reported one, else the prompt's); the CLI then writes only the state of that PR. Against a server without `task.pr-state` either the first write is refused, logged once, and the rest is skipped.

The lookup runs at most once per 10 minutes per machine: the time of the last one is kept in `pr-refresh.json` in the state directory (a file that cannot be read or written costs only an extra lookup), and is written before the query, so a failing `gh` is not tried again on every tick. A tick does nothing, and logs nothing, when `gh` is not on `PATH` or no open task has a PR. `--dry-run` runs the queries and prints the writes, and does not write the time.
