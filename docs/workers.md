# Worker machines

How a worker machine picks tasks, runs them and reports back.

## Two machines

Every worker machine runs its own timers and its own listener against the same board, under the name `machine` in its config.json (default: the host name). Every machine holds its own event stream, so a change reaches all of them at once and they race to claim; `claim-task` is atomic, so the losers move on, as they do with two timers.

- A claim is atomic on the server: of two machines claiming a task at once, one wins, and the other moves on to the next task.
- A machine skips a todo task it cannot serve, so the other one can take it: a task scheduled on the other machine (its directory is there), a resume whose session lives on the other machine, or an intake review of a repository it has no checkout of.
- A machine sweeps only its own running tasks: the worker unit lives where the task was claimed. When that machine is off, you can take the task back from the task page once its agent has been quiet for 20 minutes.
- Intake runs on both. The PR URL is the task's dedupe key (sent as its blind index), so both create the same task once.

Tasks only move while a machine with the right setup is on.

## Lanes

A machine splits its parallel runs into lanes by skill, configured in its config.json:

```json
"lanes": {
  "reviews": { "skills": ["review-pr"], "slots": 2 },
  "general": { "skills": ["*"], "slots": 3 }
}
```

- **Own work first.** A task belongs to the lane that names the skill its prompt starts with (`/review-pr` and `/pr-review:review-pr` both count as `review-pr`), else to the lane with `*`, which also takes prompts without a skill. A lane with a free slot takes the first Todo task of its own: resumes first (answered, replied to or paused), then by priority. A skill belongs to at most one lane, and at most one lane has `*`.
- **Borrowing.** A lane with nothing of its own borrows the first task any other lane would run, so idle slots do not wait. The run is marked borrowed.
- **Taking the slot back.** When a full lane has its own work waiting and runs borrowed work that has gone on for `pauseAfterMinutes` (default 5), the dispatcher asks the newest such run to pause, one per lane at a time. Lane bias beats priority: a borrowed urgent run gives way to its lane's own low task. An urgent task only has guaranteed room in its own lane.
- **Pausing is cooperative.** The dispatcher drops a pause flag. The worker sees it on its next 15-second tick and writes a message to the agent's stdin: post a one-line status and end your turn. Nothing is refused, so the session stays clean and the agent finishes the step it is on. When the turn ends, the worker notes "Paused on <machine>: …" and puts the task back in Todo, ahead of new work, to resume in its session on the same machine. A turn that has not ended 2 minutes after the message is interrupted (see [Talking to a running agent](#talking-to-a-running-agent)) and the task is paused all the same. The resumed run is told it was paused and checks its state before it goes on.

A lane may also name a `cwd`: where its tasks run when they have no directory of their own (see [Where a task runs](#where-a-task-runs)), say `"reviews": { "skills": ["review-pr"], "slots": 2, "cwd": "~/workspace/cosuno/cosuno" }`, so `/review-pr 17766` from the New task form runs in the checkout and gets its settings. The same can be set from the directory's side: `board dirs set lane reviews ~/workspace/cosuno/cosuno` (see [Config](setup.md#config)); it wins over the lane's `cwd`, and one directory serves one lane.

Without `lanes`, a machine runs one lane, `general`, with `*` and three slots.

## Liveness and limits

The hook also touches a heartbeat file on every tool call. The worker checks it every 15 seconds:

- no tool call for `inactivityMinutes` (default 15): the run is interrupted as stuck and the task goes to `needs-me` with the end of the log. Claude Code caps a foreground Bash call at ten minutes, so a long command does not trip it.
- a run longer than `maxRunHours` (default 6): interrupted, however busy. A guard against an agent looping on tool calls.

The worker passes the heartbeat on to the board every 15 seconds while the agent is active, with the lane. A running card counts the seconds since ("active 12s ago", then "active 1m 5s ago"), amber after 5 quiet minutes, red after 10, and its lane with a "borrowed" badge when it runs in another lane's slot.

Every stop is an interrupt first: the worker sends `claude` an interrupt on stdin, which ends what the agent is doing at once and keeps the session resumable, then closes stdin so the process exits. Only a process that is still there 30 seconds after the interrupt is killed (SIGTERM, then SIGKILL).

The heartbeat, pause flag, lane, working directory and, for an agent's run, the agent's definition (`<task>.agents`) of a run live in `$XDG_RUNTIME_DIR/agent-board/` (`AGENT_BOARD_RUN_DIR` overrides it), private to your user; on macOS, without an `XDG_RUNTIME_DIR`, in `~/.local/state/agent-board/run` (mode 700), where the process supervisor keeps its pid files too. If the clock jumps (the machine slept), the worker moves the heartbeat up to the wake instead of counting the sleep as time without a tool call, and the dispatcher's sweep does not count quiet time on a tick that follows a gap of more than 10 minutes.

## Talking to a running agent

The worker starts `claude -p` with `--input-format stream-json` and keeps its stdin open for the whole run. The prompt is the first user message, written as a JSON line. Three things follow it on stdin, all written by the worker:

- **A pause message**, when the dispatcher wants the slot back (see [Lanes](#lanes)).
- **Your messages.** **Send** on a running task (see [Ask and resume](usage.md#ask-and-resume)) stores a pending note on the board. The worker reads the task's run inbox on every 15-second tick and whenever the board's event stream says tasks changed (so a message usually arrives within seconds), writes the notes to stdin as user messages and acknowledges them. Claude Code takes a user message up at its next tool boundary, so the agent is not interrupted; the note shows **Delivered** in the thread.
- **An interrupt**, for **Stop**, **Stop & send** and the limits above. Plain Stop ends the run: the worker reports it stopped and the task goes to Needs me with "Stopped by you.". With Stop & send the worker interrupts, writes your message after it and the run carries on in the same session. The stop request is cleared once the worker has acted on it.

A message that has not been handed over when the run ends (the agent had finished or the worker had closed stdin) is not lost: the task goes to the top of Todo to resume in its session with the message, and a note in the thread says so. If you stop the run or take the task back instead, the message becomes an ordinary reply that the next Send & continue carries. A worker whose server does not offer the run inbox runs as before and never reads it; a CLI too old to know the inbox ignores stop requests, and the task page says so after a minute (Take back still works).

## Transcripts

Every run records what it did. The worker starts `claude -p` with `--output-format stream-json --verbose`, condenses each event (the agent's text, each tool call with its input, each tool result, subagent calls tagged with their Agent call, notes such as the model and directory, and the result with turns, time, cost and refused tool calls), writes a readable line per event to the local log, and sends the events to the board with every 15-second check and once more when the run ends. A batch the board refuses is sent again with the next. What waits for a board that is down is bounded by count (20,000 events) and by size (32 MB of JSON): past either, the oldest tool outputs are emptied first, then the oldest events dropped, and a note in the transcript says how many. The end of the run makes two bounded passes.

On the board, **Transcript** on a task page (or the terminal icon on a card) opens the runs, newest first, live while one runs. Tool calls are one line each; a click shows the input and loads the output. A tool result over 256 KB is cut with a note; the full one stays in the session file on the machine. Claude Code passes thinking on without its text, so a thinking block shows as a marker with its token estimate.

Transcripts can hold whatever the agent saw: file contents, `gh` output, now and then an environment value. The worker seals each event (and each tool output apart) before it sends it, so the server stores only ciphertext. They go 14 days after a task is closed, and 28 days after the last change of an open task in Done, which covers intake's tasks (the server checks hourly). A task of yours untouched in Done is closed after 14 days.

The board loads a run's events in pages of 2000 and afterwards only those after the last one it has, so long runs show in full and a live run costs one small request per poll.

## Where a task runs

A task is bound to a directory on the machine that ran it:

- A fresh run starts in the task's own directory: where it was scheduled from with `board schedule`, or where the proposing agent worked. A task without a directory of its own (an intake review, a task from the New task form with an empty Working directory) starts in the checkout of the PR its prompt names (`repos`), else in its lane's `cwd`, else in `defaultCwd`. Each of the three can also come from the `dirs` list: a directory with `repo` is that repository's checkout, one with `lane` is that lane's `cwd`, and the one with `default` is `defaultCwd`. A setting there wins over the old key, which keeps working. This matters beyond the files: Claude Code loads the checkout's `.claude/settings*.json` only when it starts there, and that is where tokens and endpoints such as `CIRCLECI_TOKEN` or the replica endpoints usually live. The task's `workdir` is set to it.
- The hook records the agent's working directory on every tool call. When a run ends somewhere else, typically in a worktree the agent entered with `/worktree` (`EnterWorktree`), the worker stores that as the task's `workdir`.
- A resume (after an answer, a reply or a pause) starts `claude --resume` in the `workdir`, so the session continues in exactly the worktree it left. The resume is pinned to the same machine, where that directory exists.
- **A resume whose directory is gone** continues the same session in the git checkout that held it. The usual cause is a worktree removed while its task was still open, say by a cleanup of merged branches with `git worktree remove`. Claude Code resumes a session by id from any directory, so nothing is recreated at the old path. The worker takes the nearest parent directory with a `.git` (the `/repo` of `/repo/.claude/worktrees/feat-x`), which has to be listed when there is a `dirs` list, and runs there; the task's `workdir` becomes that checkout. The agent's prompt starts with a notice: the old directory is gone, whatever was not committed and pushed in it is lost, and before changing files it should recreate its worktree on its branch the way the repository does (its CLAUDE.md), check that the branch still has its last commits, and say in its next comment which commit it continues from, or, when the branch is gone as well, ask you how to go on. A system note on the task records the move. The task goes to `needs-me` with the reason instead when no git checkout exists above the directory, or when that checkout is not a listed directory (`board dirs add` in it allows it). A fresh run in a gone directory, and any intake task, still fail with the path: only a resume has a session worth keeping.
- **Re-run fresh** forgets the session and sets the `workdir` back to the directory the task was created with (the server keeps that envelope as `home_workdir`, written once at creation and never updated, so a worker's rewrite cannot lose it), which keeps the task pinned to its machine. A task created without a directory (an intake review, a form task with an empty Working directory) and a task from before this was kept start in `defaultCwd` as before (an intake review: in the checkout). With a `dirs` list, the directory has to be listed, the original one included.

**The list of directories.** `board dirs` keeps a per-machine list of the directories workers may run in: the `dirs` key of this machine's `config.json` (see [Config](setup.md#config)). Without the key nothing is limited. Once the key exists, even as `{}`, a run starts only in a listed directory, and an empty list allows nothing. An entry's settings (`repo`, `default`, `lane`) only say where tasks run; they change nothing about what is allowed, and the directory they name is listed by construction.

- A directory is allowed when it is a listed one or below one, matched by path segment (`/work/app` allows `/work/app/sub`, not `/work/app2`). A worktree inside a listed checkout (`.claude/worktrees/...`) counts; a worktree folder outside it needs its own entry.
- The real path decides, so a symlink inside a listed directory that points elsewhere does not pass, and a listed symlink counts through its target.
- The check runs in the worker for every start, after the check that the directory exists: a task with its own directory, a form task in `defaultCwd` or its lane's `cwd`, an intake review in its `repos` checkout, and a resume in the stored `workdir`. A directory outside the list ends the task in `needs-me` with the path and the way out: `board dirs add` in it on that machine, then **Re-run fresh** or **Send & continue**. A running task is not stopped when the list changes.
- When a run ends in a directory outside the list (the agent entered a worktree elsewhere, or went to `/tmp`), the worker does not store it as the `workdir`. The task keeps the directory it started in, and a system note on the task says where the agent ended and that the next resume starts in the start directory. Storing it would make the next resume refuse its own directory.
- `board schedule` and `board add` take the working directory as the task's directory, so they refuse outside the list: `board schedule` with a usage error, and `board add` first tries `AGENT_BOARD_START_DIR` (the directory the run started in) and refuses only when that is not allowed either.
- The dispatcher does not look at the list. It claims a task whose directory is not listed and the worker fails it, so the task shows in Needs me instead of sitting in Todo. `board attach` and the checks of `board wait` are not limited either: they stay on the machine.
- `board doctor` fails for a `defaultCwd`, lane `cwd` or `repos` checkout that no entry covers, since tasks routed there stop. `board dirs add --from-config` lists them.
- **The board gets a copy, as advice.** A machine with a `dirs` key sends its list to the board, sealed, for the New task form's Working directory field to offer: the listed directories that exist, as written, each with its `label` when it has one (`repo`, `default` and `lane` stay on the machine), from every dispatch tick when the list changed and from `board dirs add`, `rm`, `set` and `unset`. The dispatcher compares a blind index with the one the board holds, so an unchanged list sends nothing, and a failed or unsupported send costs the tick one log line at most. If the board cannot be reached, `add` and `rm` still succeed and warn, and the next tick sends the list. The copy never reaches a path, argument or decision on any machine: the worker reads only its own `config.json`. A server without the `machine.dirs` feature is skipped, and `board doctor` says whether the board has the current list.

Claude Code itself (2.1.323) also restores a session's worktree when it is resumed from the original directory; the `workdir` makes the board independent of that and shows it on the task page. Once the worktree is deleted that restore is no use, which is what the recovery above is for.

## What a worker may do

There is no sandbox. A worker runs `claude` as you, with your home directory, your SSH agent and your `gh` login. The [list of directories](#where-a-task-runs) is not one either: it decides where a run may start, and so whose `.claude/settings*.json` it loads (a repository you did not list does not get to hand a run its allow rules, tokens or hooks). The agent can still `cd` anywhere, and an agent in `auto` mode can edit `config.json`, the list included. How much it may do depends on who made the task:

- **Tasks you made** (`board schedule`, the New task form, and agent proposals once you start them) run as if you ran the prompt in your terminal: all your settings (user, project, local) and `--permission-mode auto`, Claude Code's classifier mode that lets safe actions through and refuses risky ones. Headless, a refusal cannot become a prompt; it shows in the log and usually in the agent's report.
- **Intake's reviews** run as the agent named by `intake.agent` (see [Agents](#agents)): every review task is created with that agent sealed into it, so it gets the agent's tools and lists, and the shipped `agents.reviewer` in `apps/cli/examples/config.reviews.json` holds what the paragraph below describes. The paragraph describes the deprecated lists of an `intake` block without `agent`, which still work for one more release: they run unattended on PR text nobody chose to read, so they get less: `--permission-mode dontAsk` with only `intake.allowedTools` allowed and `intake.disallowedTools` denied on top, and `--setting-sources user`, which keeps a checkout's own `.claude/settings*.json` (its allow rules and tokens) out of the run. The shipped list allows reading, `gh` reads, the pr-review scripts, `board comment`, `ask`, `add`, `show` and `move <task> needs-me` (it cannot `board schedule` or start work), CircleCI through the engineering plugin's `cci.sh`, a few Shortcut reads and `bin/replica-psql` (the production and staging read replicas); it cannot push, merge or approve. `intake.env` hands it `CIRCLECI_TOKEN`, `SHORTCUT_API_TOKEN` and the replica endpoints from the checkout's settings, and nothing else from there. A review that a PR's text turns against you can read production data through the replica, and could put it into the pending draft (which you see before submitting) or onto the board.

Every run gets `AGENT_BOARD_TASK=<id>` in its environment, `AGENT_BOARD_START_DIR=<the directory it started in>` (whose settings a check of `board wait` takes its `env` from), and `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`, so print mode waits for background subagents instead of stopping them 10 minutes after the last turn. The board's rules also tell the agent not to end its turn while background work runs. And `board schedule`, the changes of `board schedules` and `board dirs add` and `rm` refuse to run while it is set: an agent proposes follow-up work with `board add`, which waits in Needs me until you start it. A config that allows `Bash(board *)` covers `board schedule` and `board move <task> todo`; narrow it to the rules in `apps/cli/examples/config.reviews.json` (`board comment *`, `board ask *`, `board add *`, `board show *`, `board move * needs-me`), and deny `Bash(board schedule *)`, `Bash(board schedules *)`, `Bash(board dirs *)` and `Bash(board internal *)`. `board dirs add` and `rm` refuse inside a run, and the deny rule keeps an agent from even trying.

A check of `board wait --check` runs later, from the dispatcher, outside Claude Code: its permission rules and the auto-mode classifier see the command only as part of the `board wait` call, so do not allow `Bash(board wait *)` by rule, or a check skips the classifier.

Permission rules match the text of a call: they keep an agent on its task, but they are not a security boundary. A PR or story whose text turns the agent against you reaches whatever the run allows and whatever those commands can reach. A dedicated OS user for the workers, with its own checkouts and a narrowly scoped GitHub token, would make that a boundary again; it is not set up yet.

## Agents

An agent is a named set of tools and rules in the machine's `config.json`, under `agents`. A task that names one runs as that agent, with only what the agent allows, whoever made the task. The task names it as a sealed `agent` field, which the board server stores and returns but cannot read, change or drop without making the task unreadable (see [Encryption](encryption.md#encryption)); you choose it with `board schedule --agent <name>` or the **Agent** field of the New task form (see [Choosing an agent](usage.md#choosing-an-agent)). The definition of the agent never leaves the machine: the board holds only its name. A repeating schedule hands its agent to every occurrence. The limits of the field are in [Encryption](encryption.md#encryption): a proposal made from an agent's run carries no agent and runs in `auto` once you start it, `board attach` resumes an agent's task with your own settings, the commands that are refused inside a run rely on `AGENT_BOARD_TASK`, so it is the agent's lists that stop a command from unsetting it, and the name is the only link to the definition, so machines must define same-named agents the same way.

```json
"agents": {
  "reviewer": {
    "description": "Reviews a PR and stages the findings.",
    "prompt": "You review pull requests.",
    "tools": ["Read", "Grep", "Bash"],
    "allowedTools": ["Bash(gh pr view *)", "Bash(board comment *)"],
    "disallowedTools": ["Bash(git push *)"],
    "mcpServers": ["shortcut"],
    "env": ["SHORTCUT_API_TOKEN"],
    "model": "opus"
  }
}
```

The name is lowercase letters, digits and dashes, at most 32 characters. `description` and `tools` are required; `prompt`, `allowedTools`, `disallowedTools`, `mcpServers`, `env` and `model` are optional. Unlike the rest of `config.json`, an unknown key or a wrong type inside an agent makes that agent unusable instead of being ignored: a misspelt `disallowedTool` must not leave the agent without a deny list. Only that agent is lost: the machine's other work goes on, a task that names it fails closed, the dispatcher logs a warning on every tick and `board doctor` fails. `tools` lists tool names only (`Read`, `Bash`, `mcp__shortcut__get_story`); a pattern such as `Bash(git status)` belongs in `allowedTools`. `env` and `mcpServers` work as in `intake`: the worker copies the named variables from the working directory's `.claude/settings*.json` and the named servers from its `.mcp.json`, after the directory has passed the [list of directories](#where-a-task-runs).

The run is `claude -p --tools=<tools> --agents=<file> --agent=<name> --permission-mode dontAsk --setting-sources user --allowedTools … --disallowedTools …`, in the working directory the task would run in anyway. `<file>` is a private copy (mode 0600) of the agent's `description`, `prompt`, `tools` and `model`, written to `$XDG_RUNTIME_DIR/agent-board/<task>.agents` and removed when the run ends; Claude Code runs the main thread as that agent. `--tools` holds the agent's `tools` without MCP ones, so the built-in tools are withheld even if Claude Code fails to load the agent. `tools` limits the tool names only: with `Bash` in `tools` but no `dontAsk`, the agent could run any command. The command-level rules take effect because of `--permission-mode dontAsk`, which refuses whatever `allowedTools` does not allow; `--setting-sources user` keeps a checkout's own settings out, as for intake. The lists expand `~/` and plugin placeholders as [described below](#how-a-task-runs).

An agent with `Agent` in its `tools` can start subagents, and they stay inside the run's limits. Claude Code 2.1.325 was checked with a probe agent (`tools` `Read`, `Bash`, `Agent`; `Bash(touch *)` denied; `Bash(echo *)` allowed). The subagents it started (`general-purpose`, a plugin agent and an agent defined with `tools` `Bash`, `Write`, `WebFetch` and `permissionMode: bypassPermissions`) got only the tools in `--tools`, inherited dontAsk mode and both lists, and could not escape any of them. The agent's own `bypassPermissions` setting did not take effect. `touch` was refused, `mkdir` and a redirect were refused because no rule allowed them, `echo` ran, and MCP tools outside `allowedTools` were refused. The Agent tool's list of subagent types still shows each type's own tools (`pr-reviewer` with `WebFetch`, for example), so an agent may say it can reach tools it cannot. Those tools are not given to the subagent. A subagent or skill that runs a shell command on load (a `` !`…` `` line) needs that command in `allowedTools` as well, or it fails to start.

An agent's run gets the reduced board rules of an intake review (no `board wait`, no opening PRs) and `AGENT_BOARD_RESTRICTED=1` in its environment, which the agent's `env` cannot override. `board wait --check` refuses while it is set: a check would run any command outside the agent's list. `--in` and `--at` still work.

It fails closed. A task whose `agent` cannot be opened (a name the server dropped or replaced, or one sealed for another task) is skipped by the dispatcher and refused by the worker like any task with an unreadable prompt; it never runs unrestricted. A machine whose `config.json` has no `agents.<name>` leaves a task that names it in Todo for another machine (the dispatcher logs `SKIP <id> no agents.<name> in config.json here`), unless the task is pinned here (a resume, or its own directory): then the machine claims it. A worker that gets such a task, a resume included, fails it with a system note and starts nothing. A plugin placeholder that does not resolve fails the run the same way. `board doctor` checks each agent: that its plugins resolve, and that no allow rule is for a tool its `tools` leave out.

## How a task runs

A fresh run is

```
claude -p --session-id=<new uuid> --input-format stream-json --append-system-prompt "<the board's rules>" --settings '<hook>' <permissions>
```

in the task's directory (see [Where a task runs](#where-a-task-runs)). The prompt is the task's `input`, as written, and goes to `claude` on stdin, never as an argument. The appended rules tell the agent its task id, to report with `board comment`, to ask with `board ask` instead of AskUserQuestion, to finish with `board move <task> needs-me`, to wait for CI and the like with `board wait` (not in an intake review), and how to propose follow-ups. Outside an intake review they also set how far the agent goes alone:

- It decides and acts without asking on steps that are easy to undo and stay on the machine (editing files, tests, local branches, worktrees and commits). It uses `board ask` only before a step that is hard to undo or that other people see, unless the prompt asked for it: force-pushing, deleting branches or data, merging, deploying, posting to Slack, Shortcut, email or someone else's PR.
- A prompt to implement, fix or change code counts as the request to commit and push. The agent works on a new branch (in a new worktree if the checkout holds changes that are not its own), pushes it, opens a PR with `gh pr create`, starts CI when the repository's CLAUDE.md or skills say it has to be started or approved by hand, waits for CI with `board wait`, and links the PR in its final comment. Right after opening the PR it runs `board pr <task> <url>`, so the board shows the PR on the task's card and page (see [Pull requests on the card](usage.md#ask-and-resume)). A task that asks only for a plan, an investigation or a review opens no PR.

The rules only ask; `--permission-mode auto` can still refuse a push or `gh pr create`, and the refusal shows in the log.

A task that names a model (`board schedule --model`, or the Model select of the New task form) adds `--model=<model>` as one argument, on a fresh run and on a resume; a name that is not of a model name's shape (a clear value from the server) refuses the run instead. Without one, claude uses its own default.

The hook is the [heartbeat and question hook](#liveness-and-limits), and `--input-format stream-json` keeps stdin open for [messages, pauses and interrupts](#talking-to-a-running-agent). A resumed run is `claude -p --resume=<session>` with the same flags and your reply on stdin (see [Ask and resume](usage.md#ask-and-resume)).

In intake's rules and an agent's, `Bash(` rules expand `~/` to your home directory and `{<plugin>}` (such as `{pr-review}` or `{engineering}`) to the root Claude Code gives the one installed `<plugin>@*` as `${CLAUDE_PLUGIN_ROOT}`, resolved when the worker starts (`{<plugin>@<marketplace>}` names the marketplace; a plugin that is not installed, or is installed from several marketplaces, is an error): for a marketplace added as a directory (`~/.claude/plugins/known_marketplaces.json`) that is the plugin's `source` in the marketplace's `.claude-plugin/marketplace.json` (Claude Code loads it from the checkout, not from the cache copy), otherwise the `installPath` in `~/.claude/plugins/installed_plugins.json`. A rule must not start with `*` before a script path: a leading `*` matches any command that merely contains the path. If the plugin path cannot be resolved the task goes to `needs-me` with the reason. `Read(...)` rules are passed on unchanged (they take `~/` themselves). Old `backend`, `labels`, `intakeLabel` and `sandbox` entries in a config are ignored.

A missing allowed tool in an intake review shows up as a failed run: the log says what was denied. Add it to the agent's `allowedTools` (or, for a legacy intake, `intake.allowedTools`).

## How it decides

Dispatcher, per tick:

1. For each task in `running` claimed by this machine, ask whether its worker is running: `systemctl --user is-active agent-board-<task>` on Linux; on macOS whether the pid in the run directory's `<task>.pid` is alive and its command line ends in `internal worker <task>`. A task whose unit is gone moves to `needs-me` with the log tail, timed from the unit's own start (else the task's `runStartedAt`). So does one whose worker failed to enforce the [limits](#liveness-and-limits) for five minutes past them; its unit is stopped. If `systemctl` gives no known state, or the backend fails, the tick stops before starting anything and exits non-zero.
2. For each task in `waiting` that this machine ran: a wait whose `wakeAt` has passed (a timer, or a check past its timeout) or whose check is not stored here is woken with the reason (`wake`), so it can start in this tick. A check whose task is neither waiting nor running here any more is deleted.
3. A task this machine cannot serve is skipped (see [Two machines](#two-machines)). The rest are planned into [lanes](#lanes): own work first, then borrowing. Each start is claimed, its lane written to the run directory, then the worker starts (`systemd-run --user --collect --unit agent-board-<task>` on Linux, a detached `board internal worker <task>` process with its output in the task log on macOS) and a start note names the machine, lane and PID. A lost claim hands its slot to the next task; the first failed start ends the tick's starting.
4. Lanes whose own work still waits ask one borrowed run each to pause.
5. The checks that are due run side by side (45 s each at most). One that exits 0 wakes its task with the end of its output; for any other the result is kept with the check for the timeout message.

Worker, per task: before anything starts, a directory that does not exist, or that a `dirs` list does not allow, ends the task in `needs-me` with the reason (see [Where a task runs](#where-a-task-runs)). A task with `next: resume`, a session, and a user reply, a pause or a wake since the agent last spoke resumes that session with the reply (and "you were paused", or "your wait is over: <why>") as the prompt, but only a session this machine started for the task; for any other the run is refused with the reason. Anything else starts a new session, whose id is recorded on this machine and stored on the task once the run is about to start (and cleared again if the process cannot be spawned). A run is also refused when it would hand the agent a note of yours that cannot be decrypted. A fresh run's prompt is the task's prompt; when the thread already holds notes by you or the agent, it is followed by what you wrote since the previous run started and a line telling the agent to read the thread with `board show <task>`. Either way `next` goes back to `fresh`.

Intake runs only on a machine whose `config.json` has an `intake` key (`apps/cli/examples/config.reviews.json` is a full example). Per run it searches the repos in `repos` for open, non-draft PRs that request your review, then creates one task per PR URL (the dedupe key), checked against every task, closed ones included. One `gh api graphql` call per page covers all repos. A PR without an author (a deleted account) is listed as `ghost`. A PR whose data cannot be read is logged as `WARN skipped <url>` and its task is left alone; a result without a URL fails the run. A failed GitHub search or backend listing changes nothing and exits non-zero.

- A PR whose head moved and whose last commit is at least ten minutes old sends its task from `needs-me` or `done` back to `todo` (a task parked in `backlog` stays there) with `next: fresh`. A failed task stays in `needs-me` until the head moves.
- A task still waiting in Todo for a PR that no longer appears (merged, closed, draft, or no longer asking for your review) is moved to `done` with a note, and its `head` is cleared in the same update.
- A PR that is listed again with the same head brings such a task back: a settled PR whose intake task is `done` without a head is queued again the same way. A task you marked done keeps its head and stays done.

After the reviews, intake also refreshes the PR state shown on the board. For every task that is not closed or done and has a PR (the one its agent reported, else the one its prompt names), it asks GitHub for the PR's state: one `gh api graphql` query for up to 50 PRs, an alias per PR, owner, repository and number passed as variables. When the state differs from the task's `prState`, it writes the new one with `set-pr-state` (log: `PRSTATE <task> <state>`), so the board can show a merged or closed PR on the card and offer **Move merged to Done**. A PR GitHub gives no answer for (deleted, no access) is logged as `WARN no state for <url>` and its task keeps its state. A failed query is logged as `WARN PR states not refreshed` and does not fail the run: the review work above has been done by then. Against a board server without the `task.pr-state` feature the first write is refused, logged once, and the rest is skipped. `--dry-run` runs the queries and prints the writes.

`intake.agent` names an agent of the machine's `agents` and seals it on every task intake creates; a task queued again keeps the agent it has. Intake refuses to run (the unit fails, `board doctor` fails) while that agent is not defined or cannot be read; the machine's dispatch and workers go on. Against a board server without the `task.agent` feature intake creates no task (`SKIP #<n> no task created: …`) rather than one without the agent. Setting `agent` together with `allowedTools`, `disallowedTools`, `env` or `mcpServers` is a config error. Those lists alone stay supported for one more release, create tasks without an agent, and make `board doctor` warn that they are deprecated: move them into `agents.<name>` and set `intake.agent`; nothing is translated for you.

The machine chooses the rules of its intake tasks, as the lists did: an intake task that names no agent (one made before the move, or by a machine that still had the lists) runs as `intake.agent` on a machine that has it, with the same dontAsk mode, `--tools`, `--agents`, lists, `AGENT_BOARD_RESTRICTED` and board rules as a task that names that agent. A task that names its own agent runs as that one. Without `intake.agent` and without lists an agentless intake task fails closed as before (`no intake block in config.json here`). A machine with no `intake` block but with the agent a task names, and the checkout of its repository, runs that task: defining the agent opts the machine into those reviews.
