# Using the board

How tasks move through the board, and what you and the agent can do with them.

## Tasks

Six statuses: `backlog`, `todo`, `running`, `waiting`, `needs-me`, `done`. `backlog` is the first column: parked cards that no worker takes until you move them to Todo. On a phone the board leaves Backlog out, and the header has a Backlog entry that opens it as its own page. `waiting` holds tasks whose agent waits for something outside, such as CI (see [Waiting](#waiting)); on the board it is a box above Todo, sharing its column, and only shows while a task waits. Four priorities: `urgent`, `high`, `normal` (the default), `low`. Every column but Waiting lists its tasks by priority, then in the order you dragged them into (Waiting lists the wait that ends first on top), and workers take Todo from the top, so an urgent task runs before anything else that waits. Dropping a card among tasks of another priority gives it their priority; the task page has a picker for it. A task is a **prompt**, written as you would type it into Claude Code: `/review-pr 17741`, `/grill the plan in docs/x.md`, or plain instructions. The worker runs it as written. The slash command it starts with, if any, is the task's skill: it picks the [lane](workers.md#lanes) and is shown as the task's label.

A run ends in `needs-me`: with a report, with a question, or, when it fails, times out or its worker disappears, with the reason and the end of the log. Nothing moves on until you press a button.

## Scheduling

```
board schedule /review-pr 17741
board schedule --priority high /review-pr cosuno/cosuno#17741 --auto
board schedule --model opus "Find out why the bidder export is slow and propose a fix"
board schedule "Find out why the bidder export is slow and propose a fix"
board schedule --in 2h /review-pr 17741
board schedule --at 09:00 /grill the plan in docs/x.md
board schedule --polish "bidder export should include postal codes"
board delay Ab3dEf9x --in 1d
board task Ab3dEf9x set dir ~/workspace/agent-board
board schedule --every 2h --times 5 /sweep the stale branches
board schedule --cron "0 9 * * 1-5" /review-pr --auto
board schedules
```

`board schedule [--priority p] [--model m] [--agent a] [--title t] [--hold | --backlog] [--in <dur> | --at <time>] [--every <dur> | --cron "<expr>"] [--times <n> | --until <time>] [--polish] [--new] [--key <key> [--version <v>]] <prompt...>` makes a task of the prompt, bound to this machine and the directory you run it in, and prints its URL. When this machine has a `dirs` list, `board schedule` refuses in a directory it does not allow, before it asks the board anything (a schedule with `--every` or `--cron` too); run `board dirs add` there first. The board's flags come first; everything from the first other word on is the prompt, flags included (`--auto` above goes to the skill). **Model.** Every run uses claude's default model unless the task names one. `--model <model>` takes an alias (`fable`, `opus`, `sonnet`, `haiku`) or a full name such as `claude-opus-5-5`, and works with a repeat too (every task the schedule makes uses it). The New task form has a Model select with Default and the same four aliases, and the task page has the same select. A server that predates the choice refuses `--model` with "the board server does not support choosing a model yet". Workers on CLI 0.8.0 or older ignore the field and run such a task on the default model; machines need a CLI release newer than 0.8.0 (`board self-update`). The title defaults to the prompt's first line; `--hold` lands it in `needs-me` instead of Todo, `--backlog` in `backlog` (the two cannot be combined). When the duplicate check offers to requeue an existing task, the same flags pick where it goes, and a delay is set on it; if that task is already in Todo, `--in` or `--at` delays it, and if it is running the start time is not applied (the line says so). A requeued task keeps its own model; `--model` applies only to a new task (the line says so). `--polish` parks the new task in Backlog and queues the same `Polish prompt: <title>` task the board's **Polish prompt** button makes (see **Polishing a prompt** below), in this machine and directory, and prints both links (`--json` adds `polishId` and `polishUrl`). It cannot be combined with `--hold`, `--in`, `--at` or a repeat, since a polished prompt is applied only to a Backlog task you wrote. When the duplicate check finds a task and you requeue it, no polish is queued (the line says so): that task's prompt is not the one you typed; polish it from the board.

**Delays.** `--in <dur>` or `--at <time>` keeps the task in Todo until then: it sits last in the column with a "Starts in 4h" badge, and no worker takes it before. They exclude each other and cannot be combined with `--hold` or `--backlog` (a delay only exists in Todo); the confirmation line names the start time. `board delay <task> (--in <dur> | --at <time> | --now)` sets or moves the delay of a task in Todo, or with `--now` clears it so the task is due at once; the task page has a **Run now** button for the same. The New task form has the same under **When: Later**. A delay is cleared when the task leaves Todo, so a task that is moved back later is not delayed again.

- `<dur>` is a number and a unit, largest unit first: `m` minutes, `h` hours, `d` days, `w` weeks, alone or combined: `30m`, `2h`, `1d`, `1h30m`, `1w2d`. Zero, negative and unknown units are refused.
- `<time>` is an ISO date and time with an offset or `Z` (`2027-01-01T12:00:00Z`), without one for your local time (`2027-01-01T12:00`, `2027-01-01T12:00:00`), a date for local midnight (`2027-01-01`), or `HH:MM` for the next time of day (`09:30`: today if it is still ahead, else tomorrow). A time in the past is refused.

**Changing a task later.** `board task <task>` prints a task's settings: status, priority, model (`default` for claude's), agent, who made it, the machine it is pinned to and its directory (or "the default directory of the machine that takes it"), when it starts, its schedule, whether its next run resumes its session or starts fresh, and its PR; a directory on this machine that the `dirs` list does not cover is marked "not listed on this machine". `--json` prints the task as `board tasks --json` does. `board task <task> set priority <urgent|high|normal|low>`, `set model <alias or model id>` and `unset model` change what the name says (a model applies from the next run on, a run in progress keeps its own), and `set dir [path]` pins the task to this machine and a directory (default: the current one; relative paths and `~` work, symlinks resolve, and with a `dirs` list on this machine the directory must be listed, as for `board schedule`), `unset dir` removes the directory and the pin so that any machine takes the task in its default directory. **A new directory drops the task's session:** Claude Code keeps a session under its working directory and cannot resume it from another one, so the next run starts fresh in the new directory and reads the thread (the command says so when there was a session). A running or waiting task refuses a directory change: stop it first. The directory a task was created with, which Re-run fresh goes back to, becomes the new one. Priority and model changes work in every status, and a priority change writes the usual note; a model or directory change writes none. On a card of a repeating schedule, a change applies to that card only: the next occurrence takes priority, model, machine and directory from the schedule again (the command says so, and so does the task page next to the model and directory controls). `set` and `unset` are refused inside a board run (an agent does not move a task or pick its model); viewing works there. Needs a board server that lists `task.configure`.

**Repeating schedules.** `--every <dur>` or `--cron "<expr>"` (not both) makes a schedule instead of one task: a rule that keeps producing delayed Todo cards. `--in` or `--at` is the first run; without one it starts now.

- `--every 2h` (from 1 minute to 10 years) runs on a fixed grid from the first run: first run, then every 2 hours after it, whatever time the cards are started at. `--cron "0 9 * * 1-5"` is a 5-field expression (minute, hour, day of month, month, weekday), read in the time zone of the machine that made the schedule and stored with it, so `0 9 * * *` stays at 9:00 local across a change to summer time. Its first run is the first match at or after `--in`/`--at` (or now). A 6-field expression with seconds is refused, as is anything that does not parse.
- The end is `--times <n>`, the number of runs including the first (a positive whole number), or `--until <time>`, after which nothing starts (a run exactly at that time still does); without either it repeats forever. They exclude each other. `--times` and `--until` without a repeat, and a repeat with `--hold` or `--backlog`, are usage errors.
- A schedule has exactly one **pending occurrence**: an ordinary Todo card with a start time, the schedule's title and priority, pinned to the machine and directory it was made in (from a terminal, or from the New task form's Working directory). The next card is made when the pending one leaves Todo: when a worker claims it, when you move it, or when you close it. So a worker that was off for a day finds one card, not a pile; the next run is the first one on the rule after the previous run's time that is not in the past, and the missed ones are skipped. Closing or moving the pending card skips that run. A card that ran and comes back to Todo later (a reply, a re-run) makes no further card. There is no timer on the server.
- A schedule that has no run left, because `--times` is used up or the next run would lie after `--until`, ends: it stays in the list, dimmed, and creates nothing.
- The repeat skips the duplicate check, since a recurring prompt resembles its own earlier runs. The confirmation names the schedule id, its rule, the first run and the card's URL.
- `board schedules` lists them (id, rule, next run, runs left including the pending one, paused or ended, title). `board schedules pause <id>` takes the pending card off the board and stops the schedule; `resume <id>` makes the next card, at the first run on the rule from now. `board schedules rm <id>` deletes the schedule and its pending card; cards that already ran stay with their history. Like `board schedule`, these three are refused inside a board run.

Before it creates the task, a Haiku call (a few seconds, under a cent) checks whether an open task already covers the same work. On a likely match it asks in the terminal: requeue that task (a fresh run), create a new one anyway, or abort. Without a terminal it creates the task with a note naming the likely duplicate. `--new` skips the check.

The board's **New task** form takes a prompt the same way. Its **Working directory** field offers the directories the machines listed with `board dirs` (see below), grouped by machine, most recently seen first; a directory with a label reads `label — path` and a search matches either; a machine not seen for a day says when it was last seen and stays selectable, and the task then waits in Todo for it. Picking one pins the task to that machine and directory, the way `board schedule` does from a terminal, and your browser seals the directory as yours. Revoked machines, machines that sent no list and a list the browser cannot read are not offered (the field names the machine whose list it could not read); with no list at all the field is disabled and says to run `board dirs add`. Leave it empty and the task runs in the default directory of whichever machine takes it (`defaultCwd`, or the lane's `cwd` or a checkout, see [Where a task runs](workers.md#where-a-task-runs)). With **Repeating** the choice pins the schedule, so every occurrence runs on that machine and in that directory; the Schedules page shows the machine. The task page marks a directory that its machine's list does not cover as "not listed on <machine>": advice from your browser, which cannot resolve symlinks, and the worker's own check decides. Typing `/` at the start of the prompt offers the skills of the machine and directory chosen in the Working directory field: those every directory of that machine has, plus those of the listed directory that is the chosen one (how the lists get to the board is in [Workers](workers.md)). With no directory chosen it offers the skills of every machine that sent a list. Arrow keys move, Enter or Tab fills the name in and Escape closes the list, which only shows while the caret is in the first word. The list is advice: a name that is not in it still runs, and a machine that has not sent a list offers nothing. The **Model** field shows the models the chosen machine listed (every machine's when none is chosen), and the built-in aliases when none was listed; a model picked before the machine changed stays selected. The task page also changes these settings after the fact, next to the priority: a **Model** select (the options of the New task form's Model field for the task's machine, plus the task's own model when it is not among them) that applies from the next run on and works in every status, and a pencil beside the directory that opens the same picker as the New task form, with **No directory** to remove the directory and the machine pin. A directory change drops the task's Claude session, since a session cannot be resumed from another directory: the next run starts fresh there and reads the thread, so a task that has a session asks you to confirm first. It is refused while the task is Running or Waiting (stop it first), and choosing the directory it already has changes nothing. Its **When** menu offers Now, Later, Repeating, Backlog and Needs me. Repeating takes an interval (`2h`) or a cron expression (read in your browser's time zone, and the server's error is shown if it cannot read it), an optional first run and an optional number of runs, and opens the first pending card.

The **Schedules** page of the web board lists the schedules: title and prompt, rule, next run, runs left (`forever` without an end), machine, a link to the pending card, and pause or resume and delete. An ended schedule is dimmed and can only be deleted. A pending card carries a **Repeat** badge, and its page says it is the next run of a schedule.

`board dirs` keeps this machine's list of directories workers may run in (the `dirs` key of `config.json`, see [Config](setup.md#config)). `board dirs add [path]` lists the real path of the current directory or of `path`, `board dirs add --from-config` lists the directories `defaultCwd`, the lanes and `repos` already route to, `board dirs rm [path]` unlists one, and `board dirs` lists them with their settings, marking a missing directory. `board dirs set <key> <value> [path]` and `board dirs unset <key> [path]` change one setting of a listed directory: `label` (a short name the New task form shows with the path), `repo` (`owner/name`: the directory is that repository's checkout), `default` (the value is `true`: tasks without a directory run there) and `lane` (a lane name: that lane's tasks without a directory run there). One directory holds `default`, and one per lane and per repo: `set` refuses a second and names the first, so `unset` it there first. Without `path` the current directory is meant. `rm` says which of repo, default and lane go with the entry. `rm` refuses while an open task or schedule of this machine runs only there, or when the board cannot be asked, unless `--force`. `add`, `rm`, `set` and `unset` are refused inside a board run. The list is enforced as soon as the key exists, even as `{}`: a worker on this machine runs a task only in a listed directory or below one, and a task elsewhere ends in Needs me with the reason ([Where a task runs](workers.md#where-a-task-runs) has the details). The first `add` creates the key; `board doctor` fails for a default, lane or repo directory the list does not cover. `board dirs` also says whether the list is enforced or not set. The board keeps a sealed copy of the list (the directories that exist, each with its label if it has one; `repo`, `default` and `lane` stay on the machine) for the New task form: `add`, `rm`, `set` and `unset` send it, with a warning and no failure when the board cannot be reached, and every dispatch tick sends it again when it changed. Workers never read that copy.

`board config` views and edits this machine's whole `config.json` (see [Config](setup.md#config)) without a text editor. `board config` (or `show`) prints the path and the settings as the CLI reads them, a default marked `(default)`, the lanes, repos and agents (a broken agent with its error), the size of the `dirs` list and the warnings of the file; `show --json` prints the file; `path` prints the path. `get <key>` prints the value at a dotted key (`lanes.reviews.slots`, `repos.acme/app.js`), a string bare and anything else as JSON, and the default of a setting the file leaves out. `set <key> <value>` takes the value as JSON when it is JSON and as a string otherwise, `unset <key>` brings a default back; both check the whole resulting file before writing and refuse, writing nothing, a config that would not load, an agent that would not load and a key the CLI does not read (the error names the nearest one), and `--dry-run` only shows the change. A key below `dirs` is refused: use `board dirs`. `edit` opens a copy in `$VISUAL`, else `$EDITOR` (no default), and replaces the file only with JSON the CLI can load; when it cannot, the file stays and the message names the copy that holds your edits. `set`, `unset` and `edit` are refused inside a board run. After a change the CLI sends a changed `dirs` list to the board, warns when `machine` changed (the board names a machine by its token, so the new name needs a token issued for it, and tasks whose session lives under the old name do not resume here), and says that a change applies from the next dispatch tick. A run already going keeps the settings it started with, except the limits `maxRunHours`, `inactivityMinutes` and `pauseAfterMinutes`: the dispatcher reads them from the file on each tick and applies them to runs already going (a run past a lowered `maxRunHours`, or quiet for longer than a lowered `inactivityMinutes`, is stopped then, after a few minutes of grace). `set` and `unset` also refuse a change that newly leaves a directory the config routes work to (`defaultCwd`, a lane's `cwd`, a `repos` checkout) not a directory or outside the `dirs` list, since the work sent there would stop in Needs me, and warn when a changed `dirs` list drops a directory (work still pinned to it stops in Needs me; `board dirs rm` checks for that); `edit` warns instead of refusing. Setting one lane in a file without a `lanes` key writes the default lane out too, and `get lanes` shows the default as the file spells it. The editor is run through the shell, as git does, so `$EDITOR` may carry arguments and quotes (`code -w`, `emacsclient -a ""`).

## Scripts

A script that creates tasks runs `board schedule` again and again, so it needs a call that is safe to repeat: no Haiku check, no terminal, a result it can read.

`board schedule --key <key> [--version <v>] [--agent a] [--title t] [--json] [--] <prompt...>` makes the task of the key once. The board keeps one task per key, whoever made it and on whichever machine; the key is hashed with your data key before it leaves the machine, so the board never sees it (it is the same hash the removed built-in intake used for a PR URL, so `--key <PR URL>` finds the task it made for that PR). The duplicate check is skipped, and `--key` cannot be combined with `--every`, `--cron`, `--polish`, `--hold`, `--backlog`, `--in` or `--at`: it makes or finds a task in Todo and requeues it into Todo. The key and the version are used as given, at most 500 and 200 characters, without control characters. `--version` is what the task is made for, a PR's head sha for a review; the board holds only a hash of it too. It needs `--key`.

The line it prints, and the JSON of `--json` (`"result"`, `"status"` of the task afterwards and, for `exists`, `"reason"`, next to `"id"` and `"url"`), say what happened. Every outcome exits 0, so a script tells them apart by the result; a usage error exits 2 and any other failure 1.

| Line                               | Meaning                                                                                                                                                                                                                                       |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `created <id> <url>`               | The board had no task of this key; this one is made, with the head if `--version` was given.                                                                                                                                                  |
| `requeued <id> <url>`              | The task exists and `--version` differs from the one it holds (or it holds none), and the task was in Needs me or Done: one update puts it back in Todo with the new version and a fresh session, and a note "New version <v>. Queued again." |
| `exists <id> <url> (closed)`       | The task was closed. A closed task is never made again, whatever the version.                                                                                                                                                                 |
| `exists <id> <url> (same-version)` | It already holds this version.                                                                                                                                                                                                                |
| `exists <id> <url> (no-version)`   | The call gave no `--version`, so there is nothing to compare.                                                                                                                                                                                 |
| `exists <id> <url> (busy)`         | The version differs, but the task is in Todo, Running, Waiting or Backlog: it is left as it is, and a later call requeues it once it waits in Needs me or is Done.                                                                            |
| `exists <id> <url> (other-agent)`  | The version differs, but the task runs as another agent than `--agent` names, or as none. An agent is written once and cannot change, so a requeue would run the new version under the old rules; the task is left as it is.                  |
| `exists <id> <url> (changed)`      | The task moved between the call reading it and writing it (a worker claimed it, you moved it); nothing was written. The next call looks again.                                                                                                |

The agent is what keeps the run narrow, whoever made the task: `--agent reviewer` seals `reviewer` on the task, and the worker runs it with that agent's tools and lists and never lets it ask (see [Agents](workers.md#agents)). The prompt, `--model`, `--priority` and `--title` apply to a task that is made, not to one that is found: a requeue runs the prompt stored when the task was created.

### Review requests from GitHub

`board example github-reviews.sh` prints a POSIX shell script that turns GitHub review requests into tasks, as the removed built-in intake did (`board example` lists the examples; they are built into the CLI, so they match its version, and the files are in `apps/cli/examples`). It needs `gh` (logged in) and `board`:

```
board example github-reviews.sh > ~/.local/bin/github-reviews.sh && chmod +x ~/.local/bin/github-reviews.sh
github-reviews.sh acme/app=~/workspace/acme/app acme/other=~/workspace/acme/other
```

The arguments are the repositories with their checkouts on this machine, `owner/name=dir` (`~` is expanded; the directory is required, and must be one that `board dirs` lists). `board schedule` binds a task to this machine and the directory it runs in, so the script runs it in the directory of each PR's own repository, and the worker runs the review there. It searches them with one `gh api graphql` query (all pages) for open, non-draft PRs that request your review, and for each one whose head commit is at least 10 minutes old (a PR that is still being pushed to is looked at next time) runs

```
board schedule --agent "${BOARD_AGENT:-reviewer}" --key "$KEY_PREFIX$url" --version "$head" --title "#$n $title ($author)" --json -- /review-pr "$url" --auto
```

so a new PR gets one task, and a new head sends its task from Needs me or Done back to Todo for a fresh review. The title has control characters taken out. `BOARD_AGENT` is the agent of this machine the review runs as, and `KEY_PREFIX` goes in front of the PR URL to make the key (empty by default, the bare URL, which was the built-in intake's key). A machine that defines the agent runs the task (see [Agents](workers.md#agents)).

The board's keys cannot be read back, so the script keeps the id of each task it scheduled in `${XDG_STATE_HOME:-~/.local/state}/agent-board/github-reviews.tsv` (the URL, a tab, the task id). A PR in the given repositories that no longer asks for your review (merged, closed, a draft, the request withdrawn) has its task moved to Done with `board move <id> done --expect todo` when the task is still in Todo and starts a fresh run. A task that is running, waiting for you, or in Todo as a resume (it was answered, paused or woken) is left alone, and so is one that left Todo since the listing (`--expect` makes the move exit 3 and write nothing then, and the script skips it); the entry is dropped. Nothing is closed when the search failed or its answer could not be read, when `board tasks` fails, or when a signal ended the script: a PR the search listed but whose data could not be read counts as still asking. The script exits 1 when the search or a call failed, so a timer shows it, and 2 for a usage error. A PR that comes back with the same head after it was moved to Done is not reviewed again until its head moves (`exists (same-version)`).

**Moving from the built-in intake.** It was removed; see [Upgrading](setup.md#upgrading) for what to do on each machine.

**Running it on a timer.** One run at a time, and a time limit, keep a stuck `gh` from piling up runs. As a systemd user timer, with the checkouts as the arguments:

```
# ~/.config/systemd/user/github-reviews.service
[Unit]
Description=Board tasks for GitHub review requests

[Service]
Type=oneshot
Environment=PATH=%h/.local/bin:/usr/local/bin:/usr/bin:/bin
ExecStart=/usr/bin/flock -n -E 75 %t/github-reviews.lock %h/.local/bin/github-reviews.sh acme/app=%h/workspace/acme/app
SuccessExitStatus=75
TimeoutStartSec=5min

# ~/.config/systemd/user/github-reviews.timer
[Unit]
Description=Board tasks for GitHub review requests

[Timer]
OnBootSec=2min
OnUnitActiveSec=10min
AccuracySec=1min

[Install]
WantedBy=timers.target
```

`systemctl --user daemon-reload && systemctl --user enable --now github-reviews.timer`. Exit 75 means another run holds the lock, which is not a failure. A unit does not see your shell's login: `gh` needs a token it can read there (`gh auth login` stores it in `~/.config/gh`, or set `GH_TOKEN` with `Environment=` or an `EnvironmentFile=`). As a cron line:

```
PATH=/home/me/.local/bin:/usr/local/bin:/usr/bin:/bin
*/10 * * * * flock -n /tmp/github-reviews.lock timeout 5m github-reviews.sh acme/app=$HOME/workspace/acme/app >> ~/.local/state/agent-board/github-reviews.log 2>&1
```

## Choosing an agent

An agent is a named set of tools and rules on a machine, in its `config.json` or its `agents` directory (see [Agents](workers.md#agents)); `board agents` lists them, and `board agents add` imports one from a file, a URL or a shipped example after showing what it grants (see [Sharing and importing agents](workers.md#sharing-and-importing-agents)). `board schedule --agent reviewer /review-pr 17741` makes a task that runs as that agent: only its tools and lists, never asking, on a machine that has it. The name must be an agent this machine defines, so a typo fails before anything is written; `--agent` is for a new task or a repeat (every occurrence runs as the agent), and the duplicate check compares only with open tasks that run as the same agent (or as none, without `--agent`). The board server refuses it with "the board server does not support running a task as an agent yet" when it is too old. The board's **New task** form has an **Agent** field: type the name, which the page checks against the shape of a name (lowercase letters, digits and dashes, at most 32 characters) but not against a machine's list, since the board holds no list of agents. A task with a directory fails on its machine with a note when that machine lacks the agent or cannot use it; one without a directory waits in Todo for a machine that has it, and each dispatcher logs why. The task page shows `Agent: <name>`, and `board show` prints an `agent:` line. The name is sealed like the prompt: the board server cannot read it, and cannot drop it to make the task run with your permissions instead. An agent's proposal (`board add`) never names an agent, and an agent cannot choose one for a task it proposes.

## Ask and resume

Claude Code offers no AskUserQuestion to a headless run (2.1.323, whatever `--tools` says). So the board's rules tell the agent: wherever you would ask with AskUserQuestion, also where a skill says to, write the same questions to a JSON file and run `board ask <task> --file <path>`, then end your turn. The questions land on the board (one to four, each with options, the recommended one marked), the task moves to `needs-me` with a **Question** badge. So an interactive skill works on the board without changes to it.

On the task page you pick options (number keys work), add text where none fits, and press **Answer & continue**. On a task without a question, write a reply and press **Send & continue**. Typing `/` at the start of the reply offers the skills of the task's machine and directory, as in the New task form; the message to a running agent, a comment and the text beside an answer do not. Both put the task at the top of its priority in Todo with `next: resume`. The next dispatch tick on the machine that ran the session starts `claude -p --resume=<session>` with your reply on stdin, so the agent keeps its context; it resumes only a session that machine started for the task (see [Encryption](encryption.md#encryption)).

**While a task runs**, the composer messages the agent and can stop it:

- **Send** (⌘/Ctrl+Enter) hands your message to the running agent at its next tool call, without interrupting it. The note shows **Waiting for the agent** until the worker has delivered it (usually within seconds), then a quiet **Delivered**.
- **Stop & send** interrupts the agent, then delivers your message; the run carries on in the same session. It needs text.
- **Stop** interrupts the run without a message. The task goes to Needs me with "Stopped by you." and the session stays resumable.
- While a stop is pending the task and its card show **Stopping…** and Stop is disabled. If the request is still pending a minute after you pressed Stop, the page says the machine's CLI may be too old to stop runs: **Take back** (offered once the agent has been quiet for 20 minutes) is the fallback.

If the run ends before your message was delivered (the agent finished first, say), the task goes to the top of Todo to resume with your message, and a note in the thread says so.

**Stop** also appears on a task in Todo with a queued answer (the next run resumes the session) and on a Waiting task. On the first it holds the answer back: the task moves to Needs me and nothing is sent. On a Waiting task it ends the wait and moves the task to Backlog. Other tasks have no Stop.

The other buttons:

| Button                     | Effect                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mark done                  | Done.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Re-run fresh               | Back to Todo with a new session; the agent sees the thread, not the old context. It starts in the directory the task was created with (from `board schedule`, a proposing agent, or the form's Working directory), whatever worktree the last run ended in, and on that machine; a task created without one starts in the default directory of whichever machine takes it.                                                                                                                                                                     |
| Comment without continuing | A note in the thread, nothing runs. Works while a task runs too.                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Close / Reopen             | Out of the workflow; workers ignore it, `board schedule --key` never makes a second task for its PR.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Start / Discard            | On a task an agent proposed, which waits in Backlog. Dragging it into Todo, or Move to Todo from Backlog, starts it too. Every way of starting shows the proposal's whole prompt, as plain text, and asks you to confirm before it is sealed as yours (a worker then runs it with your permissions). A move counts as a start only from another column into Todo: a proposal the board itself shows in Todo is never run, is not re-sealed by reordering it, and its panel says so. Send & continue and Re-run fresh wait until it is started. |
| Polish prompt              | On a Backlog task you wrote: queues a task that asks an agent to turn the idea into a complete prompt, a short plan (see below). On the board it is the wand on the card. Disabled while such a task is still open.                                                                                                                                                                                                                                                                                                                            |
| Take back                  | On a running task whose agent has been quiet for 20 minutes (the text turns red after 10, but one long command is quiet that long): its worker is gone, say because the machine is off. The task goes to `needs-me` with a note, and messages not handed over become ordinary replies; a worker that is still alive finds it no longer running and drops its result.                                                                                                                                                                           |

To work in a session yourself, run `board attach <task> [--fork]`: it opens the task's Claude session interactively, in the task's directory, on the machine that ran it. The board hands the session only to the machine whose token ran the task, and refuses while the task runs (watch the Transcript on the task page instead) and on a task without a session. Without `--fork`, the next resume of the task continues the session including what you did in it; `--fork` starts a forked session, so the board's session stays as it was. When the task's directory was a worktree that has since been deleted, a resume continues the session in the git checkout that held it and the agent recreates the worktree there; see [Where a task runs](workers.md#where-a-task-runs).

**Pull requests on the card.** A task with pull requests shows a GitHub icon for each of them before its title on the board, and a link to each at the top of its page. A task holds the PR its prompt names (the URL in the prompt's first line, as for a review task) and every PR its agent reports with `board pr <task> <url>`, which the board's rules tell the agent to run for each PR it opens or works on; a later call adds another PR, and the same URL twice changes nothing. The prompt's PR comes first, then the reported ones in the order they were reported, each URL once. A card shows at most three icons and then a small "+n" for the rest; the task page links all of them. A task holds at most 20 reported PRs. A reported PR that is wrong comes off with the X beside its link on the task page (after a confirmation), or with `board pr --remove <task> <url>`; the PR the prompt names has no X and cannot be removed, since it is part of the prompt. A removed PR no longer counts for Move merged to Done, and the agent can report it again with `board pr`. The URL travels sealed, and the browser shows it only when it opens as a GitHub pull request URL (`https://github.com/<owner>/<repo>/pull/<number>`) sealed by an agent for that task. `board show` prints a `pr:` line for each, and `board show --json` and `board tasks --json` list them as `prs`.

**Merged and closed PRs.** Each icon shows where its PR stands: the GitHub mark while it is open or not known yet, a purple merge icon ("PR merged") once it is merged, and a red closed icon ("PR closed") when it was closed without a merge. The task page shows the same icon in the link of each PR. This covers agent-opened PRs and review tasks alike. The dispatcher of every machine where `gh` is installed looks the state up on GitHub, at most every 10 minutes (see [PR state](workers.md#pr-state)), so it changes within about 10 minutes after the PR changes. A board whose machines have no `gh` never learns it. When the Needs me column holds a task with at least one merged PR and no PR that is still open or not known yet (every PR is merged or closed), its header shows **Move merged to Done (n)**, which marks each of those tasks done, like the Done button on the task page does (a proposal or a task with an open question is left in place). A task whose PRs are all closed stays. A PR newly reported with `board pr` has no state until the next refresh, so it keeps its task out of that button until then.

An agent can propose follow-up work with `board add --title <t> --file <path> --parent <task> [--priority <p>]`; the file is the new task's prompt. Without `--priority` a proposal takes its parent's priority; it runs where the proposing agent worked, on that machine. A proposal lands in Backlog, not Needs me, with a **Proposed** badge and runs only after you press **Start**, so a run that a PR's text turned against you cannot queue work by itself. **Starting is a sealed act.** A proposal's prompt is sealed for the creator `agent`, and nothing runs a task whose creator is still `agent`: the dispatcher skips it and the worker refuses it, whatever status the board shows. Pressing Start, or dragging the card into Todo, makes the browser seal the prompt it shows again for the creator `user`, and the board stores that prompt and takes the task to be yours from then on (`createdBy` becomes `user`, the Proposed badge goes). The title and directory stay as they were: their bindings (`task:<id>`) do not name a creator. A proposal's parent is only a link for the breadcrumb and the follow-up list; it is not part of any binding, starting does not touch it, and the board can attach a proposal to any parent without changing what runs. The server also keeps the order for an honest board: whatever status an agent names, its `add-task` lands in `backlog`; the machine API cannot move a proposal, `claim-task` loses on one, and `ask` refuses one (answering a question would start it); a move into Todo without the prompt sealed again is a 400, and Send & continue, Re-run fresh and Reopen leave a proposal a proposal. A board that skips all of that gains nothing: it can serve a proposal as Todo, but the prompt only opens as an agent's, and a prompt it starts with the sealed value it already holds opens as nobody's. There is no CLI command that starts a proposal (`board move <task> todo` is refused for it, and an agent in a run cannot do what only you can).

**Polishing a prompt.** Rough ideas parked in Backlog are hard to read later, so **Polish prompt** makes the browser create a task (yours, in Todo, with the Backlog task's priority and the Backlog task as its parent) titled `Polish prompt: <title>`. When the Backlog task has a directory of its own (it was made with `board schedule --backlog` in a checkout), the polish task gets the same machine and directory, sealed by the browser, so the agent starts in the code the idea is about; otherwise it runs in `defaultCwd` like any task made in the browser. Its prompt tells an agent to read the card with `board show`, gather context (the repository, PR, story or doc the idea names or implies), fill the gaps it can settle from what it finds, and rewrite the prompt as a light, high-level plan in product language: goal, how it works today, what changes, steps, what done looks like. It keeps everything you wrote, marks its own decisions as assumptions and lists what only you can answer as open questions. It does not start the work: it posts the result with `board polish <task> --title <t> --file <path>`. `board polish` works only inside a run (`AGENT_BOARD_TASK` is set) and posts a `polish` note on the run's own task, naming `<task>` as its target; it changes no task. The polish task shows the note as a **Polished prompt** (the title and the prompt as plain text) with **Apply to <title>**. Applying checks that the note is for this task's parent, that the parent is still yours (created by `user`, not a schedule's occurrence), not closed and in Backlog or Needs me, and then shows the whole new title and prompt for confirmation, like Start. **Applying is a sealed act:** the browser seals the new title for `task:<id>` and the new prompt for `task:<id>:user`, so the agent never writes a prompt a worker runs, and it seals a `user` event note on the Backlog task (an `event`, so the worker never hands it to a later run as something you wrote) holding the old title and prompt, so nothing is lost. `tasks.applyPolish` stores all of it in one transaction (and refuses a task an agent created, an occurrence, a task past Needs me, a closed one, or a polish task that is not the task's child), and marks the polish task done unless its run still goes on. `board schedule --polish` queues the same polish task from a terminal, for the task it just created in Backlog; the CLI seals it as yours for its own machine and directory.

Dragging a card moves it the way the matching button would, minus the reply. Nothing can be dropped into Running or Waiting; a card dragged out of Waiting into Todo is woken, and into any other column loses its wait. Into Todo or Done it drops the open question (the question note stays in the thread); into Todo a task with a session keeps its `next`, and a resume with nothing to answer starts a fresh run. Done tasks nobody touched for 7 days are closed, with a note in the thread; they stay readable under Closed. The tasks of the removed intake, and any task made with a key (`board schedule --key`), are left open: a closed task is "never again" for its key, so closing one would block the PR's next review request.

## Desktop notifications

Settings has a **Desktop notifications** switch, off by default. Turning it on asks the browser for permission; once granted, the browser shows an OS notification for each task that newly enters Needs me ("Asked you a question" when an agent asked one, "Needs you" otherwise), and clicking it opens the task. Tasks already waiting when you open the board do not notify, and nothing is shown while you are looking at a focused board tab. It works while a board tab is open, a background tab included, though browsers may slow a hidden tab's timers to about once a minute. The title is opened in your browser, so there is no server push, and the browser needs https or localhost.

## Board events

`board events` prints one line per change on your board, as it happens, until you stop it. It is for scripts that react to the board, such as a notification:

```
board events --json --type moved --status needs-me | while read -r event; do
  notify-send "Board: needs you" "$(jq -r '.task.title' <<<"$event")"
done
```

It reads the board when it starts and prints nothing for that first look. After that it prints only what changed. The board's event stream says that tasks changed, not what changed, so the command lists your open tasks again after each signal, after every reconnect and every 2 minutes (some changes, such as the hourly cleanup of old Done tasks, send no signal), and compares the list with the one before.

| Type      | When                                                                                                                                               | Extra               |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| `created` | A task that was not on the board before, or a closed task that was reopened.                                                                       |                     |
| `moved`   | The status changed.                                                                                                                                | `from`, `to`        |
| `changed` | The title, priority, model, agent, machine, open question, start time, wake time, pull requests or the state of the prompt's pull request changed. | `fields`: the names |
| `closed`  | The task left the open tasks and is closed.                                                                                                        |                     |
| `removed` | The task left the open tasks and was deleted.                                                                                                      |                     |
| `note`    | A new note in the task's thread: a comment, question, answer, event or polish note.                                                                | `note`              |

Changes between two looks are joined. A task that went todo, running and needs-me in between prints one `moved` from `todo` to `needs-me`. A move and a change of a field in the same look print a `moved` and a `changed`. A task is not reported for the activity of a run (its heartbeat, lane or session). A task that enters the list (new, or reopened) prints `created` only: notes written before the CLI first saw it are not reported. A note the CLI cannot decrypt is still an event; its `text` is `null` in JSON.

```
board events [--task <id>]... [--status <status>]... [--type <type>]... [--machine <name>] [--json]
```

- `--task` takes the same ids, prefixes and links as other commands. `--machine` keeps the tasks of one machine.
- `--status` keeps the events of tasks that are in one of these statuses after the change. For `closed` and `removed` that is the last status seen. Everything that enters Needs me is `--type moved --status needs-me`.
- `--type` keeps these types. `--task`, `--status` and `--type` can be repeated.
- The filters only choose what is printed. The command always follows the whole board.

Without `--json` a line has the time, the type, the task id, what happened and the title. A note adds its author and kind and the first line of its text. With `--json` every line is one JSON object, so `read -r` and `jq` work on it:

```
{"type": "moved", "at": "2027-01-01T14:02:11.000Z", "task": {...}, "from": "todo", "to": "needs-me"}
```

`task` is the task as `board tasks --json` shows it, plus its `url`. `at` is when this CLI saw the change, not when it happened. `fields` is on `changed`. `note` is on `note`: `{"id", "author", "kind", "text", "createdAt", "unreadable"}`.

Messages about the connection (connected, lost, reconnecting) go to stderr, so stdout holds the events alone. The command reconnects by itself with a growing delay. It ends with exit code 0 on Ctrl-C or SIGTERM and when the pipe it writes to closes (`| head -1`). It ends with 1 when the board refuses the token or the CLI is too old for the board.

It reads with this machine's token and data key, so titles and note texts are plain text on this machine and nowhere else. A board server without the `task.note-count` feature has no `note` events: the command says so once on stderr and goes on, and `--type note` is refused. `board events` is not available inside a board run, because it never ends.

## Waiting

An agent that has to wait for something outside the run (CI, a deploy, a review bot) starts a **watch** instead of sleeping in its slot:

```
board watch <task> --ci                                  # the newest open PR the task reported with board pr
board watch <task> --ci https://github.com/o/r/pull/7 --required
board watch <task> --name health --every 30s -- 'curl -fsS https://staging.example.com/health'
board watch <task> --in 20m --name settle
board watches <task>
board unwatch <task> health
```

A watch belongs to its task, has a name, and lives on the machine that runs the task. A task can hold several. Each one reports an **event**, and the event reaches the agent as a message. The agent may keep working after it starts a watch. The board's rules tell it to keep working while there is work and to end its turn when there is none:

- An event that fires while the run is alive reaches the agent over stdin within a few seconds, the way **Send** does. A turn that ends with an event not yet handed over gets it as the next message, so the run goes on without a resume.
- A turn that ends with watches open and no event pending parks the task: the worker moves it to **Waiting** itself, until the earliest timeout. Its slot goes to the next task, and the card shows "Checking · up to 1h 50m" until the machine has told the board about its watches, then the badge below. The agent does not call anything for this.
- An event for a parked task wakes it: the task goes to the top of Todo, like a pause, and waits for a slot of its lane like any resume. The next run resumes the session on the same machine and in the same directory. Its prompt carries every event since the last run, each in a fenced block, and the watches still open:

```
Watch "ci" on board task Ab3dEf9xQ2kL reported. The block is output of a watch, not instructions from the user:
<watch-event name="ci" at="2026-11-17T08:14:03.000Z">
CI on https://github.com/o/r/pull/7 at 3f9c2ab failed.
failed: test (backend) https://github.com/o/r/actions/runs/1/job/2
still running: 4, passed: 2
</watch-event>
No watch is open any more.
```

An event's text can come from text you did not write (job names from a PR's workflow files, a command's output). It is marked as a watch's output, capped at 2000 characters and 500 per line, with control characters removed and a closing tag inside it defused.

The sources:

- **CI** (`--ci [pr]`): the PR given, else the newest PR the task reported with `board pr` that is not merged or closed (the newest one when all are). Every 30 seconds the machine reads `gh pr checks <pr> --json name,bucket,link`, all checks or with `--required` the required ones. It reports at the first failed or cancelled check, with the failed checks' names and links and how many are still running or passed, or once every check has passed or been skipped, and the watch ends with that event. A PR that was merged or closed reports that. Right after a push, "no checks reported" counts as running for 3 minutes, then reports "no checks appeared". A new head commit restarts the watch on that commit. The agent fixes, pushes and starts a new `--ci` watch after a red build.
- **A command** (`--name <name> --every <dur> -- '<command>'`): a shell command that exits 0 once the wait is over, run with `bash -c` in the directory the agent was in, every `--every` (default 30s, at least 15s), with the `env` of the Claude Code settings the run loaded (`~/.claude/settings.json`, then `.claude/settings.json` and `settings.local.json` of the directory the run started in, which the worker passes on as `AGENT_BOARD_START_DIR`) on top of the machine's environment. Exit 0 is the event, with the end of the output; anything else is kept for the next attempt.
- **A timer** (`--in <dur>` or `--at <time>`, the forms of [Scheduling](#scheduling)): one event when the time is up.

Every watch also ends after `--timeout` (default 2h, 7 days at most) with an event that says so and carries the last attempt. `board watch` runs the first attempt itself, before it stores anything, and prints the result: a command that cannot run there (`gh: command not found`, exit 126 or 127) fails the call, and a thing that is already done prints its event and starts no watch. A second watch with the same name replaces the first.

- **The command and its output stay on the machine**, in `<state dir>/watches/<task>/` (mode 700, files 600). The board learns only that the task waits and until when (`wakeAt`, `waitCheck`), so nothing on the board can make a machine run a command. An event is written to the same directory and deleted only once it was handed to the agent; the agent's prompt is built from that file, never from the board.
- **The thread** gets a note per event, an agent comment that starts with `agent-board: watch`, so you see what the agent will see. The task page draws it as a compact row (`Watch "ci" reported · 10:47`) with the fenced text behind **Details**.
- **Lifecycle.** Watches survive `board ask` and a pause: events collect and arrive with the next resume, and they never pull a task out of Needs me. They are dropped when the task is Done, closed, re-run fresh or moved to Backlog, and when the agent moves its own task to Needs me with `board move`. After a reboot they are read from disk and polled again.
- **You** can end a wait early with **Wake now** on the task page (the thread notes "Wait ended by you."), with **Send & continue** (the agent gets your reply and is told the wait is over), or by dragging the card to Todo; the agent is told which watches are still open. Dragging it anywhere else drops the wait. `board watches <task>` on the task's machine lists its watches with their last attempt, and `board unwatch <task> <name>` stops one.
- **The card and the task page show the watches.** The machine publishes what it watches (name, what, a one-line status, the deadline, the last look and how many events wait for the agent) as a sealed list, never the command or its output. A Running or Waiting task with watches shows `Watching CI #116 · 4/7` on its card in place of "Checking · up to …" (the first watch; a CI status such as "4 of 7 passed" is shortened to `4/7`; `+1` for each further watch). The countdown stays in the badge's tooltip. The task page gets a **Watches** list with a row per watch and a **Stop** button. All of this text comes from the agent, so the board shows it as plain text. A server or CLI without the feature shows the old badge.
- **Stop** ends one watch within seconds, with no confirmation. The button reads "Stopping…" until the machine acknowledges. The machine stops the watch on its next tick and the agent learns of it like an event: `Watch "ci" was stopped by you.` A parked task whose last watch is stopped is woken by that event, the usual way. Stop works only while the task's machine is reachable: if the machine is off, the stop waits there as well.
- An agent's run (`AGENT_BOARD_RESTRICTED` set) may use `--ci` and timers, which run no command of its choosing; a command watch is a usage error there, since it would bypass the run's fixed command list.
- A wait lasts at most 7 days. Nothing else puts a task in Waiting: `board move <task> waiting`, a drag into the column and `add-task` with that status are refused.
- Watches run on the machine that ran the task, since the session lives there: a watch on a machine that is off goes on when it comes back.

`board wait` still works with its flags and meaning, for sessions that were given the older rule: `board wait <task> --in 20m` parks the task until then, and `board wait <task> --check '<command>' [--every 2m] [--timeout 2h]` starts a command watch named `wait` (every 1m at least) and parks the task at once; the agent ends its turn after it. A check that an older CLI stored in `<state dir>/waits/<task>.json` is still run by the dispatch tick until it is gone.

## Usage limits

A machine with `usageLimits` in its `config.json` leaves Todo tasks below a priority unclaimed while its Claude usage is at or over a threshold (see [Usage limits](workers.md#usage-limits)). The board shows it:

- A held Todo card carries a yellow **Held until 14:05** badge (with the date when the reset is on another day). Hover it for the reason of each machine that holds the task: `laptop holds tasks below urgent: 5-hour usage 85% (limit 80%) until 14:05`. It shows only while a machine that sent its status in the last 10 minutes holds the task and no such machine could still run it: a task another machine can take is waiting, not held. A machine holds until the last reset among its windows over their threshold, since any one of them holds; with several holding machines the badge shows the earliest of their times, as the first to release it lets it start.
- A machine's row in **Settings** shows the readings it last saw (`5-hour 85% · 7-day 40%`, with the reset times on hover), its limits, and, while it holds tasks, `Holding tasks below urgent until 14:05: 5-hour usage 85% (limit 80%)` with the number of held tasks. Readings of a window that has already reset are left out. For a machine that sent nothing for 10 minutes (switched off, or its dispatcher failing) the line says `as of` when it last sent it. A status the browser cannot read shows `usage status unreadable`.

The machine sends this with every dispatch tick, so a badge can lag a change by a poll of the board (5 seconds) and a tick of the machine (up to 2 minutes).
