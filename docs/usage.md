# Using the board

How tasks move through the board, and what you and the agent can do with them.

## Tasks

Six statuses: `backlog`, `todo`, `running`, `waiting`, `needs-me`, `done`. `backlog` is the first column: parked cards that no worker takes until you move them to Todo. `waiting` holds tasks whose agent waits for something outside, such as CI (see [Waiting](#waiting)); on the board it is a box above Todo, sharing its column. Four priorities: `urgent`, `high`, `normal` (the default), `low`. Every column but Waiting lists its tasks by priority, then in the order you dragged them into (Waiting lists the wait that ends first on top), and workers take Todo from the top, so an urgent task runs before anything else that waits. Dropping a card among tasks of another priority gives it their priority; the task page has a picker for it. A task is a **prompt**, written as you would type it into Claude Code: `/review-pr 17741`, `/grill the plan in docs/x.md`, or plain instructions. The worker runs it as written. The slash command it starts with, if any, is the task's skill: it picks the [lane](workers.md#lanes) and is shown as the task's label.

A run ends in `needs-me`: with a report, with a question, or, when it fails, times out or its worker disappears, with the reason and the end of the log. Nothing moves on until you press a button.

## Scheduling

```
board schedule /review-pr 17741
board schedule --priority high /review-pr cosuno/cosuno#17741 --auto
board schedule --model opus "Find out why the bidder export is slow and propose a fix"
board schedule "Find out why the bidder export is slow and propose a fix"
board schedule --in 2h /review-pr 17741
board schedule --at 09:00 /grill the plan in docs/x.md
board schedule --polish "bidder export should include postal codes"
board delay Ab3dEf9x --in 1d
board schedule --every 2h --times 5 /sweep the stale branches
board schedule --cron "0 9 * * 1-5" /review-pr --auto
board schedules
```

`board schedule [--priority p] [--model m] [--title t] [--hold | --backlog] [--in <dur> | --at <time>] [--every <dur> | --cron "<expr>"] [--times <n> | --until <time>] [--polish] [--new] <prompt...>` makes a task of the prompt, bound to this machine and the directory you run it in, and prints its URL. When this machine has a `dirs` list, `board schedule` refuses in a directory it does not allow, before it asks the board anything (a schedule with `--every` or `--cron` too); run `board dirs add` there first. The board's flags come first; everything from the first other word on is the prompt, flags included (`--auto` above goes to the skill). **Model.** Every run uses claude's default model unless the task names one. `--model <model>` takes an alias (`fable`, `opus`, `sonnet`, `haiku`) or a full name such as `claude-opus-5-5`, and works with a repeat too (every task the schedule makes uses it). The New task form has a Model select with Default and the same four aliases, and the task page shows the model when one is set. A server that predates the choice refuses `--model` with "the board server does not support choosing a model yet". Workers on CLI 0.8.0 or older ignore the field and run such a task on the default model; machines need a CLI release newer than 0.8.0 (`board self-update`). The title defaults to the prompt's first line; `--hold` lands it in `needs-me` instead of Todo, `--backlog` in `backlog` (the two cannot be combined). When the duplicate check offers to requeue an existing task, the same flags pick where it goes, and a delay is set on it; if that task is already in Todo, `--in` or `--at` delays it, and if it is running the start time is not applied (the line says so). A requeued task keeps its own model; `--model` applies only to a new task (the line says so). `--polish` parks the new task in Backlog and queues the same `Polish prompt: <title>` task the board's **Polish prompt** button makes (see **Polishing a prompt** below), in this machine and directory, and prints both links (`--json` adds `polishId` and `polishUrl`). It cannot be combined with `--hold`, `--in`, `--at` or a repeat, since a polished prompt is applied only to a Backlog task you wrote. When the duplicate check finds a task and you requeue it, no polish is queued (the line says so): that task's prompt is not the one you typed; polish it from the board.

**Delays.** `--in <dur>` or `--at <time>` keeps the task in Todo until then: it sits last in the column with a "Starts in 4h" badge, and no worker takes it before. They exclude each other and cannot be combined with `--hold` or `--backlog` (a delay only exists in Todo); the confirmation line names the start time. `board delay <task> (--in <dur> | --at <time> | --now)` sets or moves the delay of a task in Todo, or with `--now` clears it so the task is due at once; the task page has a **Run now** button for the same. The New task form has the same under **When: Later**. A delay is cleared when the task leaves Todo, so a task that is moved back later is not delayed again.

- `<dur>` is a number and a unit, largest unit first: `m` minutes, `h` hours, `d` days, `w` weeks, alone or combined: `30m`, `2h`, `1d`, `1h30m`, `1w2d`. Zero, negative and unknown units are refused.
- `<time>` is an ISO date and time with an offset or `Z` (`2027-01-01T12:00:00Z`), without one for your local time (`2027-01-01T12:00`, `2027-01-01T12:00:00`), a date for local midnight (`2027-01-01`), or `HH:MM` for the next time of day (`09:30`: today if it is still ahead, else tomorrow). A time in the past is refused.

**Repeating schedules.** `--every <dur>` or `--cron "<expr>"` (not both) makes a schedule instead of one task: a rule that keeps producing delayed Todo cards. `--in` or `--at` is the first run; without one it starts now.

- `--every 2h` (from 1 minute to 10 years) runs on a fixed grid from the first run: first run, then every 2 hours after it, whatever time the cards are started at. `--cron "0 9 * * 1-5"` is a 5-field expression (minute, hour, day of month, month, weekday), read in the time zone of the machine that made the schedule and stored with it, so `0 9 * * *` stays at 9:00 local across a change to summer time. Its first run is the first match at or after `--in`/`--at` (or now). A 6-field expression with seconds is refused, as is anything that does not parse.
- The end is `--times <n>`, the number of runs including the first (a positive whole number), or `--until <time>`, after which nothing starts (a run exactly at that time still does); without either it repeats forever. They exclude each other. `--times` and `--until` without a repeat, and a repeat with `--hold` or `--backlog`, are usage errors.
- A schedule has exactly one **pending occurrence**: an ordinary Todo card with a start time, the schedule's title and priority, pinned to the machine and directory it was made in (a schedule from the New task form is not pinned yet). The next card is made when the pending one leaves Todo: when a worker claims it, when you move it, or when you close it. So a worker that was off for a day finds one card, not a pile; the next run is the first one on the rule after the previous run's time that is not in the past, and the missed ones are skipped. Closing or moving the pending card skips that run. A card that ran and comes back to Todo later (a reply, a re-run) makes no further card. There is no timer on the server.
- A schedule that has no run left, because `--times` is used up or the next run would lie after `--until`, ends: it stays in the list, dimmed, and creates nothing.
- The repeat skips the duplicate check, since a recurring prompt resembles its own earlier runs. The confirmation names the schedule id, its rule, the first run and the card's URL.
- `board schedules` lists them (id, rule, next run, runs left including the pending one, paused or ended, title). `board schedules pause <id>` takes the pending card off the board and stops the schedule; `resume <id>` makes the next card, at the first run on the rule from now. `board schedules rm <id>` deletes the schedule and its pending card; cards that already ran stay with their history. Like `board schedule`, these three are refused inside a board run.

Before it creates the task, a Haiku call (a few seconds, under a cent) checks whether an open task already covers the same work. On a likely match it asks in the terminal: requeue that task (a fresh run), create a new one anyway, or abort. Without a terminal it creates the task with a note naming the likely duplicate. `--new` skips the check.

The board's **New task** form takes a prompt the same way. Its **Working directory** field offers the directories the machines listed with `board dirs` (see below), grouped by machine, most recently seen first; a machine not seen for a day says when it was last seen and stays selectable, and the task then waits in Todo for it. Picking one pins the task to that machine and directory, the way `board schedule` does from a terminal, and your browser seals the directory as yours. Revoked machines, machines that sent no list and a list the browser cannot read are not offered (the field names the machine whose list it could not read); with no list at all the field is disabled and says to run `board dirs add`. Leave it empty and the task runs in the default directory of whichever machine takes it (`defaultCwd`, or the lane's `cwd` or a checkout, see [Where a task runs](workers.md#where-a-task-runs)). A repeating schedule cannot be pinned from the form yet: with **Repeating** the field is disabled and the occurrences run wherever a machine takes them. Its **When** menu offers Now, Later, Repeating, Backlog and Needs me. Repeating takes an interval (`2h`) or a cron expression (read in your browser's time zone, and the server's error is shown if it cannot read it), an optional first run and an optional number of runs, and opens the first pending card.

The **Schedules** page of the web board lists the schedules: title and prompt, rule, next run, runs left (`forever` without an end), machine, a link to the pending card, and pause or resume and delete. An ended schedule is dimmed and can only be deleted. A pending card carries a **Repeat** badge, and its page says it is the next run of a schedule.

`board dirs` keeps this machine's list of directories workers may run in (the `dirs` key of `config.json`, see [Config](setup.md#config)). `board dirs add [path]` lists the real path of the current directory or of `path`, `board dirs add --from-config` lists the directories `defaultCwd`, the lanes and `repos` already route to, `board dirs rm [path]` unlists one, and `board dirs` lists them, marking a missing directory. `rm` refuses while an open task or schedule of this machine runs only there, or when the board cannot be asked, unless `--force`. `add` and `rm` are refused inside a board run. The list is enforced as soon as the key exists, even as `{}`: a worker on this machine runs a task only in a listed directory or below one, and a task elsewhere ends in Needs me with the reason ([Where a task runs](workers.md#where-a-task-runs) has the details). The first `add` creates the key; `board doctor` fails for a default, lane or repo directory the list does not cover. `board dirs` also says whether the list is enforced or not set. The board keeps a sealed copy of the list (the directories that exist) for the New task form, which does not use it yet: `add` and `rm` send it, with a warning and no failure when the board cannot be reached, and every dispatch tick sends it again when it changed. Workers never read that copy.

## Ask and resume

Claude Code offers no AskUserQuestion to a headless run (2.1.323, whatever `--tools` says). So the board's rules tell the agent: wherever you would ask with AskUserQuestion, also where a skill says to, write the same questions to a JSON file and run `board ask <task> --file <path>`, then end your turn. The questions land on the board (one to four, each with options, the recommended one marked), the task moves to `needs-me` with a **Question** badge. So an interactive skill works on the board without changes to it. The run's hook would also turn a real AskUserQuestion call into a board question, should a later Claude Code offer the tool headless.

On the task page you pick options (number keys work), add text where none fits, and press **Answer & continue**. On a task without a question, write a reply and press **Send & continue**. Both put the task at the top of its priority in Todo with `next: resume`. The next dispatch tick on the machine that ran the session starts `claude -p --resume=<session>` with your reply on stdin, so the agent keeps its context; it resumes only a session that machine started for the task (see [Encryption](encryption.md#encryption)).

**While a task runs**, the composer messages the agent and can stop it:

- **Send** (⌘/Ctrl+Enter) hands your message to the running agent at its next tool call, without interrupting it. The note shows **Waiting for the agent** until the worker has delivered it (usually within seconds), then a quiet **Delivered**.
- **Stop & send** interrupts the agent, then delivers your message; the run carries on in the same session. It needs text.
- **Stop** interrupts the run without a message. The task goes to Needs me with "Stopped by you." and the session stays resumable.
- While a stop is pending the task and its card show **Stopping…** and Stop is disabled. If the request is still pending a minute after you pressed Stop, the page says the machine's CLI may be too old to stop runs: **Take back** (offered once the agent has been quiet for 20 minutes) is the fallback.

If the run ends before your message was delivered (the agent finished first, say), the task goes to the top of Todo to resume with your message, and a note in the thread says so.

**Stop** also appears on a task in Todo with a queued answer (the next run resumes the session) and on a Waiting task. On the first it holds the answer back: the task moves to Needs me and nothing is sent. On a Waiting task it ends the wait and moves the task to Backlog. Other tasks have no Stop.

To work in a session yourself, run `board attach <task> [--fork]`: it opens the task's Claude session interactively, in the task's directory, on the machine that ran it. The board hands the session only to the machine whose token ran the task, and refuses while the task runs (watch the Transcript on the task page instead) and on a task without a session. Without `--fork`, the next resume of the task continues the session including what you did in it; `--fork` starts a forked session, so the board's session stays as it was.

**Pull requests on the card.** A task with a pull request shows a GitHub icon before its title on the board, and a link to the PR at the top of its page. That is the PR the prompt names (the URL in the prompt's first line, as for a review task), else the PR its agent reports with `board pr <task> <url>`, which the board's rules tell the agent to run right after it opens one; a later call replaces the earlier URL. When the prompt names one PR and the agent reports another, the card shows the icon once and the page links both. The URL travels sealed, and the browser shows it only when it opens as a GitHub pull request URL (`https://github.com/<owner>/<repo>/pull/<number>`) sealed by an agent for that task. `board show` prints it as a `pr:` line.

**Merged and closed PRs.** The icon shows where the PR stands: the GitHub mark while it is open or not known yet, a purple merge icon ("PR merged") once it is merged, and a red closed icon ("PR closed") when it was closed without a merge. The task page shows the same icon in its PR link, for the PR the agent reported, else the one the prompt names. This covers agent-opened PRs and review tasks alike. A worker's intake looks the state up on GitHub, so it changes at the next intake run (every 10 minutes with the shipped timer) after the PR changes, and only while a machine whose `config.json` has an `intake` block runs intake (the state refresh and **Move merged to Done** need one). When the Needs me column holds a task whose PR is merged, its header shows **Move merged to Done (n)**, which marks each of those tasks done, like the Done button on the task page does (a proposal or a task with an open question is left in place). A new PR reported with `board pr` resets the state until the next intake run.

An agent can propose follow-up work with `board add --title <t> --file <path> --parent <task> [--priority <p>]`; the file is the new task's prompt. Without `--priority` a proposal takes its parent's priority; it runs where the proposing agent worked, on that machine. A proposal lands in Backlog, not Needs me, with a **Proposed** badge and runs only after you press **Start**, so a run that a PR's text turned against you cannot queue work by itself. **Starting is a sealed act.** A proposal's prompt is sealed for the creator `agent`, and nothing runs a task whose creator is still `agent`: the dispatcher skips it and the worker refuses it, whatever status the board shows. Pressing Start, or dragging the card into Todo, makes the browser seal the prompt it shows again for the creator `user`, and the board stores that prompt and takes the task to be yours from then on (`createdBy` becomes `user`, the Proposed badge goes). The title and directory stay as they were: their bindings (`task:<id>`) do not name a creator. A proposal's parent is only a link for the breadcrumb and the follow-up list; it is not part of any binding, starting does not touch it, and the board can attach a proposal to any parent without changing what runs. The server also keeps the order for an honest board: whatever status an agent names, its `add-task` lands in `backlog`; the machine API cannot move a proposal, `claim-task` loses on one, and `ask` refuses one (answering a question would start it); a move into Todo without the prompt sealed again is a 400, and Send & continue, Re-run fresh and Reopen leave a proposal a proposal. A board that skips all of that gains nothing: it can serve a proposal as Todo, but the prompt only opens as an agent's, and a prompt it starts with the sealed value it already holds opens as nobody's. There is no CLI command that starts a proposal (`board move <task> todo` is refused for it, and an agent in a run cannot do what only you can).

**Polishing a prompt.** Rough ideas parked in Backlog are hard to read later, so **Polish prompt** makes the browser create a task (yours, in Todo, with the Backlog task's priority and the Backlog task as its parent) titled `Polish prompt: <title>`. When the Backlog task has a directory of its own (it was made with `board schedule --backlog` in a checkout), the polish task gets the same machine and directory, sealed by the browser, so the agent starts in the code the idea is about; otherwise it runs in `defaultCwd` like any task made in the browser. Its prompt tells an agent to read the card with `board show`, gather context (the repository, PR, story or doc the idea names or implies), fill the gaps it can settle from what it finds, and rewrite the prompt as a light, high-level plan in product language: goal, how it works today, what changes, steps, what done looks like. It keeps everything you wrote, marks its own decisions as assumptions and lists what only you can answer as open questions. It does not start the work: it posts the result with `board polish <task> --title <t> --file <path>`. `board polish` works only inside a run (`AGENT_BOARD_TASK` is set) and posts a `polish` note on the run's own task, naming `<task>` as its target; it changes no task. The polish task shows the note as a **Polished prompt** (the title and the prompt as plain text) with **Apply to <title>**. Applying checks that the note is for this task's parent, that the parent is still yours (created by `user`, not a schedule's occurrence), not closed and in Backlog or Needs me, and then shows the whole new title and prompt for confirmation, like Start. **Applying is a sealed act:** the browser seals the new title for `task:<id>` and the new prompt for `task:<id>:user`, so the agent never writes a prompt a worker runs, and it seals a `user` event note on the Backlog task (an `event`, so the worker never hands it to a later run as something you wrote) holding the old title and prompt, so nothing is lost. `tasks.applyPolish` stores all of it in one transaction (and refuses a task an agent created, an occurrence, a task past Needs me, a closed one, or a polish task that is not the task's child), and marks the polish task done unless its run still goes on. `board schedule --polish` queues the same polish task from a terminal, for the task it just created in Backlog; the CLI seals it as yours for its own machine and directory.

Dragging a card moves it the way the matching button would, minus the reply. Nothing can be dropped into Running or Waiting; a card dragged out of Waiting into Todo is woken, and into any other column loses its wait. Into Todo or Done it drops the open question (the question note stays in the thread); into Todo a task with a session keeps its `next`, and a resume with nothing to answer starts a fresh run. Done tasks nobody touched for 14 days are closed, with a note in the thread; they stay readable under Closed. Intake's tasks are left open: intake treats a closed task as "never again", so closing one would block the PR's next review request.

## Desktop notifications

Settings has a **Desktop notifications** switch, off by default. Turning it on asks the browser for permission; once granted, the browser shows an OS notification for each task that newly enters Needs me ("Asked you a question" when an agent asked one, "Needs you" otherwise), and clicking it opens the task. Tasks already waiting when you open the board do not notify, and nothing is shown while you are looking at a focused board tab. It works while a board tab is open, a background tab included, though browsers may slow a hidden tab's timers to about once a minute. The title is opened in your browser, so there is no server push, and the browser needs https or localhost.

## Waiting

An agent that has to wait for something outside the run (CI, a deploy, a review bot) parks its task instead of sleeping in its slot:

```
board wait <task> --check 'gh pr checks 17741 --required' --reason "CI on #17741"
board wait <task> --check 'curl -fsS https://staging.example.com/health' --every 5m --timeout 1h
board wait <task> --in 20m --reason "the deploy settles"
```

and then ends its turn. The board's rules tell it to (an intake review is not told, see below). The task leaves Running for **Waiting**, its slot goes to the next task, and its card shows "Wakes in 20m" or "Checking · up to 1h 50m". When the wait ends, the task goes to the top of Todo, like a pause, and the next run resumes the session on the same machine and in the same directory, with the prompt "Your wait on board task … is over: <why>". The end of a check's output goes into the thread, not into the prompt: it can come from text you did not write (job names from a PR's workflow files).

- **A timer** (`--in <dur>` or `--at <time>`, the forms of [Scheduling](#scheduling)) ends at that time.
- **A check** (`--check '<command>'`) is a shell command that exits 0 once the wait is over. The dispatcher of the machine that runs the task runs it with `bash -c` in the directory the agent was in, every `--every` (default 2m, at least 1m, so in practice at every timer tick), with the `env` of the Claude Code settings the run loaded (`~/.claude/settings.json`, then `.claude/settings.json` and `settings.local.json` of the directory the run started in, which the worker passes on as `AGENT_BOARD_START_DIR`) on top of the dispatcher's environment. One attempt may take 45 seconds; checks run side by side at the end of a tick, and a passing one wakes its task, whose start the listener then triggers. Exit 0 wakes the task with "its check passed"; anything else is kept for the next attempt. After `--timeout` (default 2h) the task wakes anyway, told the check did not pass, with the last attempt's exit code and output.
- **The command stays on the machine**, in `<state dir>/waits/<task>.json` (mode 600). The board learns only that the task waits for a check, and until when (`wakeAt`, `waitCheck`), so nothing on the board can make a machine run a command. A check whose file is gone (the state dir was wiped) wakes its task at the next tick and says so. A check is refused for an intake review (`board wait --check` on an intake task is a usage error), whose fixed command list a check would bypass; intake's allow list does not include `board wait` at all.
- A wait lasts at most 7 days. Only a running task can wait, and nothing else puts a task in Waiting: `board move <task> waiting`, a drag into the column and `add-task` with that status are refused.
- **You** can end a wait early with **Wake now** on the task page (the thread notes "Wait ended by you."), with **Send & continue** (the agent gets your reply and is told the wait is over), or by dragging the card to Todo. Dragging it anywhere else drops the wait; the next tick of its machine deletes the check.
- Waits are woken by the machine that ran the task, since the session lives there: a timer on a machine that is off ends when it comes back, or when you wake it.

## Slack

Slack sends you nothing (see [Desktop notifications](#desktop-notifications) for the board's own). What the Slack app gives you is a way in: `/board` in Slack, from an optional [Slack app](operations.md#the-slack-app), puts a task idea in a **From Slack** box above the columns.

1. **Link once.** `/board link` answers, only to you, with a one-time link that works for 15 minutes. Open it while signed in to the board and confirm. The page names the Slack user it would link, so confirm only a link you asked for. One Slack user belongs to one board user. **Settings** shows the linked account and an Unlink button, and `/board unlink` does the same from Slack.
2. **Send text.** `/board look at the flaky bidder test` (at most 4000 characters) adds an item to your box. Without a link the command answers "run `/board link` first" and stores nothing.
3. **Turn it into a task or drop it.** **Create task** opens the New task form with the text filled in. Check it and create the task the normal way: your browser seals it, so the task runs as yours. **Dismiss** deletes the item. Items nobody touches are deleted after 30 days.

The text of an item is stored on the server in clear, because the server cannot seal it, and it passed through Slack on the way. Read an item before you create a task from it, since a task runs with your permissions. The box says so too. No worker ever sees an item.
